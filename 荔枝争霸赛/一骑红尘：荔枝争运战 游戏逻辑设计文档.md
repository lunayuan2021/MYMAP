# 1. 游戏概述

## 1.1 游戏定位

《一骑红尘：荔枝争运战》是一场双队伍限时贡运策略对抗赛。

红方、蓝方各控制一支贡运队。两队在 600 秒内从岭南出发，将荔枝运抵长安兴庆宫。比赛围绕路线选择、鲜度管理、站点资源、节点设卡、攻坚破关、窗口争夺、皇榜任务、宫门验核和终局交付展开。

服务端负责权威规则结算。参赛 Agent 只根据服务端下发状态提交动作。

------------------------------------------------------------------------

## 1.2 游戏目标

每支队伍的目标为：

``` text
在 600 秒内完成长安交付，并获得更高总分。
```

总分由以下内容构成：

- 是否完成交付；
- 交付好果数量；
- 交付鲜度；
- 交付用时；
- 皇榜任务得分；
- 惩罚扣分。

------------------------------------------------------------------------

## 1.3 初始状态

| 项目       |      固定值 |
|------------|------------:|
| 好果       |      100 篓 |
| 坏果       |        0 篓 |
| 鲜度       |         100 |
| 小分队人手 |        8 人 |
| 护卫行动点 |        4 点 |
| 比赛时长   |      600 秒 |
| 逻辑 Tick  | 1 秒 / Tick |

说明：

- 好果用于交付计分，也用于设卡、攻坚、献贡、清障、终局急策。
- 坏果由好果腐坏转化而来，不计入交付分，只用于破防。
- 小分队人手用于远程战术：SCOUT、CLEAR、REINFORCE、WEAKEN。
- 护卫行动点用于窗口争夺中的 BING_ZHENG 牌，不代表小兵死亡。

------------------------------------------------------------------------

## 1.4 得分公式

采用 1000 分制。

``` text
总分 =
送达基础分
+ 好果数量分
+ 鲜度品质分
+ 用时分
+ 皇榜任务分
- 惩罚项
```

| 得分项     | 上限 | 规则                         |
|------------|-----:|------------------------------|
| 送达基础分 |  300 | 成功交付获得 300 分          |
| 好果数量分 |  220 | 按交付好果数量计算           |
| 鲜度品质分 |  220 | 按交付鲜度计算               |
| 用时分     |  140 | 按交付时间计算               |
| 皇榜任务分 |  120 | 普通皇榜任务和破关悬赏共用   |
| 惩罚项     | 扣分 | 非法动作、失联、恶意利用规则 |

普通设卡、普通攻坚、普通窗口争夺、普通资源获取和普通资源使用不直接给分。

------------------------------------------------------------------------

## 1.5 一局比赛流程

``` text
开局携带好果、小分队人手、护卫行动点
→ 选择路线
→ 主车队移动
→ 鲜度损耗
→ 好果转坏果
→ 到达站点
→ 执行资源、设卡、攻坚、窗口争夺、皇榜任务
→ 执行小分队探路、清障、增援、削弱
→ 触发宫宴冲刺
→ 在朱雀门完成宫门验核
→ 获得【已验核】状态
→ 到达兴庆宫
→ 执行 DELIVER
→ 结算总分
```

------------------------------------------------------------------------

## 1.6 Tick 规则

``` text
1 Tick = 1 秒
1 round = 1 Tick
round 从 1 开始
tick = round - 1
```

每个 Tick 由服务端统一结算。客户端画面使用插值动画表现，不参与权威规则计算。

------------------------------------------------------------------------

## 1.7 Tick 结算顺序

服务端每个 Tick 按固定顺序执行：

``` text
1. 收集双方 action
2. 判定超时、失联、退赛
3. 基于 Tick 开始状态同时校验双方动作
4. 处理上一个 Tick 到期的小分队战术
5. 冻结本 Tick 新读条动作成本
6. 处理 0 防守值瞬发攻坚
7. 推进移动进度、读条进度、强制通行进度
8. 生成并推进窗口争夺
9. 结算窗口出牌即时成本
10. 结算设卡、攻坚、资源领取、任务完成、宫门验核
11. 结算天气和鲜度损耗
12. 结算好果转坏果和冻结成本破产
13. 生成公开事件日志
14. 生成下一 Tick 状态
```

同一 Tick 内，服务端不得按红方、蓝方、playerId、players 数组顺序分配资源、任务、船班、通行权和宫门验核权益。

------------------------------------------------------------------------

## 1.8 宫宴冲刺触发

宫宴冲刺不得早于第 390 秒触发。

满足以下任一条件时，服务端立即进入宫宴冲刺阶段：

``` text
1. 比赛时间达到第 450 秒；
2. 比赛时间 ≥ 390 秒，且任一主车队到达 S14 朱雀门；
3. 比赛时间 ≥ 390 秒，且任一主车队与 S14 朱雀门的切比雪夫距离 ≤ 15 格；
4. 比赛时间 ≥ 390 秒，且任一主车队理论最短剩余交付时间 ≤ 60 秒。
```

S11 潼关驿、S12 关中平原、S13 灞桥驿属于终段交锋区，不触发宫宴冲刺。

宫宴冲刺触发后：

- 双方同时进入 RUSH 阶段；
- 服务端刷新终局倾向皇榜任务；
- 服务端开放终局急策；
- 服务端禁止新提交远程小分队战术；
- 触发前已经进入延迟队列的小分队战术继续落地结算；
- 队伍仍然允许在窗口争夺中提交 BING_ZHENG，前提是 guardActionPoint ≥ 1。

# 2. 地图、路线、站点与资源

## 2.1 地图逻辑方式

地图显示为 80 × 60 网格。规则层采用：

``` text
路线图 + 坐标图
```

规则：

- 站点拥有固定坐标；
- 站点之间通过路线边连接；
- 每条路线边拥有路线类型和距离；
- 主车队沿路线边移动；
- 小分队距离使用站点坐标的切比雪夫距离；
- Excel 网格负责地图显示与对象配置；
- 实际移动耗时以 edges Sheet 为准；
- 参赛程序不需要实现自由网格寻路。

``` text

```


- WAIT 在 S15 固定解释为原地静止；

## 2.11 天气规则

每局固定触发 4 次天气事件。

天气组成固定为：

``` text
HOT ×2
HEAVY_RAIN ×1
MOUNTAIN_FOG ×1
```

天气顺序由服务端隐藏随机种子生成。连续两次天气事件不得为同一类型。

天气开始时间由服务端在固定时间窗口内生成：

| 次序        | 开始时间窗口 |
|-------------|--------------|
| 第 1 次天气 | 80-120 秒    |
| 第 2 次天气 | 200-240 秒   |
| 第 3 次天气 | 320-360 秒   |
| 第 4 次天气 | 440-480 秒   |

每次天气持续 60 秒。\
每次天气开始前 30 秒，服务端向双方同时下发天气预告。\
实时协议不下发完整天气序列。\
实时协议不下发隐藏随机种子。\
Replay 文件记录完整天气时间、天气类型、作用区域和随机种子。

天气效果：

| 天气         | 作用范围        | 鲜度倍率 | 其他影响                              |
|--------------|-----------------|---------:|---------------------------------------|
| HOT          | 全图            |     ×1.5 | 冰鉴价值提升                          |
| HEAVY_RAIN   | 水路 / 码头     |     ×1.3 | 水路通行成本 ×1.3，码头处理时间 +3 秒 |
| MOUNTAIN_FOG | 山路 / 山区节点 |     ×1.3 | 山路通行成本 ×1.2，SCOUT 延迟 +3 秒   |
| CLEAR        | 非天气事件状态  |     ×1.0 | 无附加影响                            |

## 2.13 主车队碰撞规则

主车队之间不存在物理碰撞体积。

规则：

- 双方主车队允许同时位于同一节点；
- 双方主车队允许同时位于同一路线边；
- 车队重叠不产生阻挡效果；
- 只有设卡、窗口争夺、道路障碍和规则读条产生通行影响。

## 3.3 移动规则

移动采用进度累加制。

``` text
当前路线边通行时间 = edge.distance × routeTypeCost × weatherMultiplier × buffMultiplier
```

每个 Tick 推进 1 秒进度。

当累计进度达到当前路线边通行时间后，主车队进入下一节点。

若参赛程序改变 targetNodeId，服务端清空当前未完成移动进度。\
移动进度不得跨不同目标路线继承。

------------------------------------------------------------------------

## 3.4 鲜度损耗

每个 Tick 结束时结算鲜度损耗。

``` text
每 Tick 鲜度损耗 =
当前状态基础损耗
× 天气倍率
× 保鲜修正
```

| 当前状态       | 每秒基础鲜度损耗 |
|----------------|-----------------:|
| 官道移动       |             0.06 |
| 水路移动       |             0.04 |
| 山路移动       |             0.08 |
| 支路移动       |             0.07 |
| 站点处理       |             0.05 |
| WAITING        |             0.05 |
| RESTING        |             0.05 |
| FORCED_PASSING |             0.05 |

------------------------------------------------------------------------

## 3.5 好果转坏果

鲜度历史首次跌破以下阈值时触发好果转坏果：

``` text
90
80
70
60
50
40
30
20
10
```

每触发一个阈值：

``` text
好果总量 -1
坏果 +1
```

好果总量定义：

``` text
好果总量 = 可支配好果 + 冻结好果
```

扣除顺序：

``` text
1. 优先扣除可支配好果；
2. 可支配好果不足时，扣除冻结好果；
3. 多个冻结成本同时存在时，按冻结发生 Tick 从小到大扣除；
4. 同 Tick 冻结时，按服务端内部动作序号从小到大扣除。
```

冻结好果被扣除后，对应读条动作进入 COST_BANKRUPT 状态：

- 读条中断；
- 动作失败；
- 已被鲜度清算扣除的好果不返还；
- 剩余冻结成本释放；
- 不产生动作收益。

FAST_HORSE 与 SHORT_HORSE 不叠加。新提交马类资源时，若已有马类效果生效，服务端拒绝动作并返回 ACTION_REJECTED。

## 3.7 小分队战术

每队初始小分队人手为 8。

每个 round 中，小分队动作数量上限为 1。超过 1 个时，本 round 所有小分队动作均无效，服务端记录 INVALID_ACTION_CONFLICT。

战术表：

| SQUAD_WEAKEN    |        2 | 敌方设卡防守值 -2    |

小分队延迟：

``` text
D = max(|x1 - x2|, |y1 - y2|)
delay = max(3, ceil(D / 3))
delay 上限 = 15 秒
```

山雾影响山路区域 SCOUT：

``` text
delay = min(15, delay + 3)
```

## 3.8 小分队落地校验

|-----------------|------------------------|------------|
| SQUAD_SCOUT     | 目标节点存在           | 不返还人手 |

| SQUAD_WEAKEN    | 目标为敌方有效设卡节点 | 不返还人手 |

同 Tick 多个小分队战术作用同一节点时，固定结算顺序为：

``` text
SQUAD_REINFORCE
SQUAD_WEAKEN
SQUAD_CLEAR
SQUAD_SCOUT
```

## 3.9 护卫行动点

# 4. 争斗规则

## 4.1 争斗类型

争斗类型固定为两类：

``` text
设卡攻坚
窗口争夺
```

设卡攻坚处理先到后到的路线阻断。\
窗口争夺处理双方争夺同一处理权益。

------------------------------------------------------------------------

## 4.2 固定处理动作成本结算

以下动作采用冻结成本机制：

``` text
SET_GUARD
CLAIM_RESOURCE
CLAIM_TASK
VERIFY_GATE
主车队 CLEAR
码头 BOARD
水驿 WATER_TRANSFER
```

流程：

``` text
开始校验
→ 冻结成本
→ 读条推进
→ 完成前二次校验
→ 扣除冻结成本
→ 结算效果
```

中断情况：

``` text
窗口争夺打断
极端平局
主动取消
状态非法
成本破产
退赛
```

中断后：

- 读条进度清零；
- 剩余冻结成本释放；
- 不产生动作收益。

------------------------------------------------------------------------

## 4.3 SET_GUARD 设卡

规则：

``` text
处理时间 = 4 秒
基础防守值 = 2
基础成本 = 1 篓好果
extraGoodFruit 取值范围 = 0、1、2
每 1 篓 extraGoodFruit 增加 2 点防守值
```

防守值上限：

| 节点类型 | 防守值上限 |
|----------|-----------:|
| NORMAL   |          6 |
| KEY_PASS |          7 |
| GATE     |          4 |
| OBSTACLE |          5 |

每队有效设卡节点上限为 2。

当新设卡完成后，若本队有效设卡数量超过 2，服务端淘汰最老设卡。

淘汰顺序：

``` text
1. completeRound 最小者先淘汰；
2. completeRound 相同时，nodeId 字典序最小者先淘汰。
```

SET_GUARD 在第 T Tick 完成时，防守状态写入服务端状态；阻挡效果从第 T+1 Tick 开始生效。第 T Tick 已经进入该节点的敌方主车队不被本次新设卡追溯阻挡。

------------------------------------------------------------------------

## 4.4 BREAK_GUARD 攻坚

投入上限：

| 资源      | 单次投入上限 |
|-----------|-------------:|
| goodFruit |            2 |
| badFruit  |            2 |

攻坚值：

``` text
attackValue =
goodFruit × 2
+ badFruit × 4
+ BREAK_ORDER_BONUS
```

BREAK_ORDER_BONUS 在绑定破关令时取 3，否则取 0。

结算：

| 条件 | 结果 |
|----|----|
| defense = 0 | 0 投入瞬发攻坚成功 |
| attackValue ≥ defense | 攻坚成功，防守值清零 |
| 0 \< attackValue \< defense | 攻坚失败，防守值减少 attackValue，攻方 RESTING 5 秒 |
| attackValue = 0 且 defense \> 0 | 攻坚不生效，攻方保持当前节点状态 |

0 防守值瞬发攻坚不触发窗口争夺。

------------------------------------------------------------------------

## 4.5 FORCED_PASS 强制通行

强制通行时间税：

``` text
timeTax = baseTax + currentDefense × 5
timeTax 不超过 taxCap
```

| 节点类型 | baseTax | taxCap |
|----------|--------:|-------:|
| NORMAL   |   10 秒 |  40 秒 |
| KEY_PASS |   15 秒 |  50 秒 |
| GATE     |   12 秒 |  32 秒 |
| OBSTACLE |   10 秒 |  35 秒 |

timeTax 在提交 FORCED_PASS 的 Tick 锁定。读条期间防守值变化不改变本次 timeTax。

同一队伍在同一节点连续使用 FORCED_PASS 的次数上限为 1。完成一次 FORCED_PASS 后，若该队伍未离开该节点，再次提交 FORCED_PASS 判定为 INVALID_ACTION_TYPE。

------------------------------------------------------------------------

## 4.6 节点风化

每个有效设卡节点每 30 秒执行一次风化：

``` text
defense = max(0, defense - 1)
```

defense 降至 0 后，该节点不产生阻挡效果。

------------------------------------------------------------------------

## 4.7 窗口争夺触发

窗口争夺固定为 3 拍。

``` text
每拍 1 Tick

```

触发对象：

``` text
DOCK

OBSTACLE
```

当双方在同一 Tick 对同一资源、任务、船班、宫门验核、障碍清理、通行处理提交动作时，服务端生成窗口争夺。

双方同 Tick 对同一资源提交 CLAIM_RESOURCE 时，服务端必须生成 RESOURCE 类型窗口争夺，不得按 playerId 顺序分配。

出牌成本：

|----|----|----|

# 6. 结算规则

## 6.1 DELIVER 条件

DELIVER 必须满足全部条件：

``` text
currentNodeId = S15
verified = true
state 不属于 MOVING、CONTESTING、RESTING、FORCED_PASSING、PROCESSING、VERIFYING
```

未满足条件时，服务端拒绝 DELIVER，记录 DELIVER_NOT_VERIFIED 或 INVALID_ACTION_TYPE。

------------------------------------------------------------------------

## 6.2 分项得分

送达基础分：

``` text
delivered = true 时获得 300 分
delivered = false 时获得 0 分
```

好果数量分：

``` text
floor(deliveredGoodFruit / 100 × 220)
```

鲜度品质分：

``` text
floor(deliverFreshness / 100 × 220)
```

用时分：

``` text
floor((600 - deliverSecond) / 600 × 140)
```

皇榜任务分：

``` text
min(taskScoreRaw, 120)
```

未完成交付时：

``` text
taskScore = min(taskScoreRaw, 40)
deliveryScore = 0
goodFruitScore = 0
freshnessScore = 0
timeScore = 0
```

最终展示分：

``` text
max(0, deliveryScore + goodFruitScore + freshnessScore + timeScore + taskScore - penalty)
```

------------------------------------------------------------------------

## 6.3 惩罚项

非法动作计数规则：

``` text
前 5 次非法动作不扣分；
第 6 次起，每次扣 1 分；
非法动作扣分上限为 20 分。
```

已交付后提交以下动作，每次扣 5 分，扣分上限为 30 分：

``` text
SET_GUARD
BREAK_GUARD
FORCED_PASS
SQUAD_SCOUT
SQUAD_CLEAR
SQUAD_REINFORCE
SQUAD_WEAKEN
WINDOW_CARD
CLAIM_TASK
```

------------------------------------------------------------------------

## 6.4 失联与退赛

单 Tick 未提交 action，服务端按 WAIT 处理。

连续 10 秒无有效 action，服务端记录 DISCONNECT_WARNING。

连续 60 秒失联，服务端将该队伍置为 RETIRED。

RETIRED 处理：

- 主车队从地图移除；
- 未完成动作注销；
- 读条注销；
- 窗口争夺注销；
- 小分队在途队列注销；
- 本方所有设卡 defense 归 0；
- 队伍不再获得后续分数；
- 另一方继续比赛。

窗口争夺期间退赛时，未退赛方获得本次窗口权益。

------------------------------------------------------------------------

# 7. 公平性与兜底规则

## 7.1 同 Tick 公平结算

服务端在当前 round 截止前收集双方 action。截止后，服务端基于 Tick 开始状态同时校验双方动作。

同 Tick 争夺同一资源、任务、船班、宫门验核窗口、障碍清理、通行处理时，服务端必须生成对应窗口争夺。

服务端禁止按以下顺序直接分配权益：

``` text
camp 顺序
playerId 顺序
players 数组顺序
action 到达顺序
TCP 包到达顺序
```

------------------------------------------------------------------------

## 7.2 同类动作冲突

同一 round 内动作类别上限：

| 类别         | 上限 |
|--------------|-----:|
| 主车队动作   |    1 |
| 小分队动作   |    1 |
| 窗口出牌动作 |    1 |

同一类别动作数量超过 1 时，该类别全部判定为非法。服务端不从中挑选合法动作。

处理：

``` text
主车队类别冲突：主车队本 round 按 WAIT 处理，并记录 INVALID_ACTION_CONFLICT；
小分队类别冲突：本 round 不执行小分队动作，并记录 INVALID_ACTION_CONFLICT；
窗口出牌类别冲突：本拍按 ABSTAIN 处理，并记录 INVALID_ACTION_CONFLICT。
```

------------------------------------------------------------------------

## 7.3 隐藏信息错误码

对隐藏信息相关的非法试探，服务端统一返回：

``` text
ACTION_REJECTED
```

以下情况不得返回具体资源信息：

``` text
未侦察节点资源库存；
未公开破关悬赏剩余信息；
敌方未公开动作；
未公开任务内部候选列表；
未来天气完整序列。
```

只有当信息已经对该队伍公开时，服务端才返回具体错误码。

## 7.4 Replay 可见性

实时比赛期间，参赛 Agent 不得读取 replay.txt。服务端不得通过实时接口下发完整 Replay。

正式比赛实时状态只通过 inquire 下发。

inquire 中禁止包含：

``` text
完整随机种子
完整天气序列
完整皇榜刷新结果
隐藏资源库存
敌方未公开动作
未来 Replay 帧
```

正式比赛结束后，服务端生成 replay.txt。replay.txt 包含本局 seed、完整天气、完整事件和最终结算。

本地调测包中的示例 replay.txt 用于开发和回放验证。正式比赛使用的 seed、天气序列、任务序列不得与公开示例 replay.txt 相同。

本地运行模式固定为三类：

| 模式            | replay.txt 生成规则                           |
|-----------------|-----------------------------------------------|
| DEBUG_MODE      | 边跑边写 replay.txt                           |
| SIMULATION_MODE | 比赛结束后写 replay.txt                       |
| OFFICIAL_MODE   | 比赛结束后写 replay.txt，Agent 进程无读取权限 |

------------------------------------------------------------------------

## 7.5 随机种子可见性

实时 start 消息不下发 seed。

实时 start 消息下发：

``` text
seedHash
```

seedHash 只用于赛后校验，不用于实时推算。

Replay start 帧下发完整 seed。

## 7.6 防死锁规则

- 路线型节点必须允许 FORCED_PASS；
- 道路障碍必须允许 CLEAR、SQUAD_CLEAR、FORCED_PASS；
- 窗口争夺平局必须一次性结算；
- 同一 contestId 关闭后不得重复触发；
- 设卡只产生延误，不产生永久阻塞；
- 兴庆宫只允许 DELIVER、WAIT、MOVE_TO_S14；
- 未验核队伍进入兴庆宫后，允许 MOVE_TO_S14；
- 0 防守值节点不阻挡通行；
- 退赛不提前结束比赛；
- 主车队重叠不产生碰撞阻挡。

# 12. 验收标准

## 12.1 后端验收

后端必须满足：

- 加载 map_config.xlsx；
- 校验地图；
- 创建比赛；
- 接收 registration；
- 下发 start；
- 接收 ready；
- 每 Tick 下发 inquire；
- 接收 action；
- 执行权威结算；
- 拒绝非法动作；
- 生成 replay.txt；
- 生成 over；
- 同一 seed 下结果完全一致。

------------------------------------------------------------------------

## 12.2 Cocos 验收

Cocos 必须满足：

- 播放 replay.txt；
- 连接实时服务；
- 渲染地图、路线、节点；
- 渲染主车队移动；
- 渲染天气；
- 渲染窗口三拍；
- 渲染小分队事件；
- 渲染宫门验核；
- 渲染交付结算；
- 不参与权威规则计算。

------------------------------------------------------------------------

## 12.3 Agent 验收

示例 Agent 必须满足：

- 连接 TCP 服务；
- 处理 5 位长度前缀；
- 发送 registration；
- 接收 start；
- 发送 ready；
- 接收 inquire；
- 提交 action；
- 处理 actionResults；
- 接收 over；
- 完成一局无异常运行。

------------------------------------------------------------------------

# 附录 A. 动作空间

| 类别 | 动作 |
|----|----|
| 主车队 | MOVE、WAIT、DELIVER、SET_GUARD、BREAK_GUARD、FORCED_PASS、CLAIM_RESOURCE、USE_RESOURCE、CLAIM_TASK、VERIFY_GATE |
| 小分队 | SQUAD_SCOUT、SQUAD_CLEAR、SQUAD_REINFORCE、SQUAD_WEAKEN |
| 窗口 | WINDOW_CARD |
| 终局急策 | RUSH_SPEED、RUSH_PROTECT、BREAK_ORDER |

# 附录 B. 术语表

| 术语             | 定义                                         |
|------------------|----------------------------------------------|
| Tick             | 服务端 1 秒结算周期                          |
| round            | 通信协议中的回合号，从 1 开始                |
| 好果             | 交付计分资源                                 |
| 坏果             | 腐坏产物，用于破防                           |
| 鲜度             | 荔枝品质指标                                 |
| 冻结成本         | 读条动作期间锁定的成本                       |
| 成本破产         | 冻结成本被鲜度清算扣除导致动作失败           |
| 设卡             | 节点防守行为                                 |
| 攻坚             | 破除敌方设卡行为                             |
| 强制通行         | 支付时间税通过设卡点                         |
| 窗口争夺         | 双方争夺同一处理权益的三拍博弈               |
| 兵争             | 消耗护卫行动点的窗口牌                       |
| 小分队           | 远程战术资源                                 |
| 宫宴冲刺         | 第 390 秒后满足触发条件进入的终局阶段        |
| 已验核           | 朱雀门验核完成后下一 Tick 生效的交付前置状态 |
| replay.txt       | 赛后公开回放文件                             |
| debug_replay.txt | 裁判审计文件                                 |
