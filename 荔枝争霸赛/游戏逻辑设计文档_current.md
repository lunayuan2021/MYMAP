# 1. 游戏概述

## 1.1 游戏定位

《一骑红尘：荔枝争运战》是一场双队伍、600 个结算帧限时的贡运策略对抗赛。红方和蓝方各控制一支贡运队，从岭南出发，将荔枝运抵长安兴庆宫；胜负由交付结果、鲜度、交付帧、任务与悬赏等规则统一计分。

参赛程序只根据服务端下发的当前公开状态提交动作；比赛按服务端结算结果推进，前端负责观战与回放表现。

| 边界 | 说明 |
|---|---|
| 当前可见 | 帧编号、队伍位置与状态、资源、设卡、障碍、当前天气、已进入预告期的天气预告、任务、悬赏、窗口争夺、本帧事件 |
| 当前不可见 | 完整未来天气排期、未进入预告期的未来天气、未来任务刷新、隐藏随机种子、对方尚未提交的本帧动作 |
| 动作约束 | 移动时只能选择当前合法相邻站点；不移动时可处理任务、资源、窗口、等待或心跳 |
| 结算约束 | 下一帧状态由服务端完成本帧结算后生成 |

## 1.2 游戏目标

每支队伍的目标是在 600 个结算帧内完成长安交付，并获得更高总分。

总分由以下内容构成：

- 是否完成交付；
- 交付好果数量；
- 交付鲜度；
- 交付用时；
- 皇榜任务得分；
- 破关悬赏得分；
- 惩罚扣分。

## 1.4 得分公式

本节是第 6 章的概述，列出结算顺序、分项来源和核心公式；公式边界、取整说明和示例以 6.2 为准。

整局胜负只看退赛状态和最终总分（totalScore）：

| 结束情况 | 胜负结果 | 分数用途 |
|---|---|---|
| 只有一方退赛 | 退赛方判负，未退赛方获胜 | 双方仍生成分项和最终总分，只用于展示、回放和统计 |
| 双方同一结算帧退赛 | 本局无胜方 | 双方仍生成分项和最终总分，只用于展示、回放和统计 |
| 双方都未退赛 | 比较最终总分；分高者获胜，分数相同则平局 | 最终总分决定本局胜负 |

最终总分相同即平局，不比较阵营、playerId、交付先后、分项明细或 TCP 到达顺序。

最终总分由六项正向分数减去惩罚分，最低为 0：

```text
最终总分 = max(0, 送达基础分 + 好果数量分 + 鲜度品质分 + 用时分 + 皇榜任务分 + 破关悬赏分 - 惩罚分)
```

成功交付会锁定交付帧、交付好果和交付鲜度。队伍未交付时，送达基础分、好果数量分、鲜度品质分和用时分都为 0，只保留受上限限制的皇榜任务分和破关悬赏分。

后续公式使用两个中间量。括号中的英文名是字段名，读规则时先看中文名：

| 中间量 | 含义 | 来源 |
|---|---|---|
| 普通任务基础分累计（finalTaskScoreRaw） | 已完成普通皇榜任务的基础分合计；它本身不是最终分项 | T01、T02、T04、T06、T08、T11 每个 30 分；T12、T13、T14 每个 15 分 |
| 破关悬赏原始分（bountyScoreRaw） | 已获得破关悬赏的基础分合计；未包含“完成任意悬赏后额外 +20” | 普通悬赏 10 分，关键关隘悬赏 18 分 |

分项公式速览：

| 分项 | 已交付时 | 未交付时 |
|---|---|---|
| 送达基础分 | `min(240, 120 + floor(普通任务基础分累计 × 4 / 3))` | `0` |
| 好果数量分 | `floor(交付好果 / 100 × 180)` | `0` |
| 鲜度品质分 | `floor(交付鲜度 / 100 × 180)` | `0` |
| 用时分 | `原始用时分 = floor((600 - 交付帧) / 600 × 70)`<br/>`用时分 = floor(原始用时分 × min(普通任务基础分累计, 90) / 90)` | `0` |
| 皇榜任务分 | `min(180, 普通任务基础分累计 + 里程碑奖励)` | `min(普通任务基础分累计, 80)` |
| 破关悬赏分 | `破关悬赏原始分 > 0 ? min(破关悬赏原始分, 80) + 20 : 0` | `min(破关悬赏原始分, 25)` |

分项上限速览：

| 分项 | 已交付上限 | 未交付上限 |
|---|---:|---:|
| 送达基础分 | 240 | 0 |
| 好果数量分 | 180 | 0 |
| 鲜度品质分 | 180 | 0 |
| 用时分 | 69 | 0 |
| 皇榜任务分 | 180 | 80 |
| 破关悬赏分 | 100 | 25 |
| 正向分合计 | 950 | 105 |
| 惩罚分 | 最多扣 50 | 最多扣 20 |
| 最终总分 | 0-950 | 0-105 |

最终总分先把正向分相加，再扣惩罚分；扣到负数时按 0 记分。退赛局仍生成分数，但胜负先按退赛状态处理。

皇榜任务分的里程碑奖励只在已交付时生效：

| 普通任务基础分累计 | 里程碑奖励 |
|---:|---:|
| 小于 60 | 0 |
| 60-89 | 15 |
| 90-109 | 35 |
| 110 及以上 | 50 |

惩罚分来自两类动作：

| 惩罚类型 | 扣分规则 | 上限 |
|---|---|---:|
| 普通非法动作惩罚（INVALID_ACTION） | 前 5 次不扣分；第 6 次起每次扣 1 分 | 20 |
| 交付后违规惩罚（POST_DELIVER_PENALTY） | 队伍已交付后，提交等待、空动作心跳、系统等待、重复交付以外的动作，每次扣 5 分 | 30 |

普通设卡、普通攻坚、普通窗口争夺、普通资源获取和普通资源使用不直接给分；它们只通过交付结果、任务、悬赏或惩罚影响最终总分。

## 1.5 一局比赛流程

这是宏观比赛流程，不代表单个结算帧的实际执行顺序。

```mermaid
flowchart TD
  A["开局准备：好果、小分队人手、护卫行动点"] --> B["路上经营：选路线、移动、资源和任务"]
  B --> C["对抗博弈：设卡、攻坚、窗口争夺、小分队战术"]
  C --> D{"是否进入宫宴冲刺阶段"}
  D -- "否" --> B
  D -- "是" --> E["终局阶段：急策开放，小分队新动作关闭"]
  E --> F{"是否到达 S14 朱雀门"}
  F -- "否" --> B
  F -- "是" --> G["提交宫门验核：仅宫宴冲刺阶段可提交"]
  G --> H["验核生效后才可进入 S15"]
  H --> I["兴庆宫交付：锁定交付快照"]
  I --> J{"双方是否都已交付"}
  J -- "否" --> B
  J -- "是" --> K["比赛结束：最终总分统一结算"]
```

宫门验核固定在 S14 朱雀门提交，但只有进入宫宴冲刺后才开放。已完成验核的队伍不能重复提交宫门验核。宫门验核本身不发任务分，只标记为已验核并解锁前往 S15。

交付发生在 S15 兴庆宫。交付成功只让该队伍进入已交付（DELIVERED）状态，并锁定交付帧、交付好果和交付鲜度；单方交付不结束整局比赛。若双方都已交付，服务端在当前结算帧生成 `over`，不再继续后续结算帧。最终总分在比赛结束时统一结算，届时会合并皇榜任务分、悬赏分和惩罚项。

## 1.6 结算帧口径

比赛按结算帧推进。实时规则协议使用结算帧编号（round），从 1 开始。第 N 结算帧表示第 N 次比赛结算；比赛规则只按结算帧推进，不按墙钟换算。比赛上限为 600 个结算帧。

结算帧口径如下：

| 规则 | 说明 |
|---|---|
| 1 个结算帧 | 比赛推进的最小单位；每帧处理本帧动作并更新比赛状态 |
| 结算帧编号（round） | 从 1 开始；第 1 结算帧就是比赛开始后的第一帧 |
| 兼容定位编号（tick） | 仅用于兼容或回放定位；实时 `start.tick = 0`，实时 `inquire.tick = max(0, round - 1)`；规则判断仍只使用 `round` |
| 第 N 个结算帧触发 | 在第 N 帧处理本帧动作和状态更新时生效 |
| 比赛结束 | 双方都完成交付、单方退赛、双方同时退赛，或第 600 结算帧上限到达时结束；比赛结束帧记录为 overRound |

规则触发统一使用结算帧编号（round）判断，不直接使用真实墙钟。

兼容定位编号（tick）会随实时协议下发，但不作为实时规则判断字段。游戏规则、任务刷新、天气窗口、宫宴冲刺和比赛结束，都以结算帧编号（round）为准。

每个结算帧由服务端统一结算。客户端画面使用插值动画表现服务端结算结果。

## 1.7 每帧结算顺序

每个结算帧可以先按五段理解：

| 阶段 | 做什么 |
|---|---|
| 1. 系统状态 | 刷新持续效果，处理探路标记过期，结算本帧开始时已有设卡的风化，并判定宫宴冲刺、任务过期和破关悬赏 |
| 2. 校验与争夺 | 处理上一帧到期的小分队和窗口出牌，再按本帧开始状态识别公共对象争夺；资源领取可在流程未结束时被另一方打断 |
| 3. 动作推进 | 对未进入窗口的队伍执行本帧主动作、移动、处理流程、强制通行、验核、交付和交付后违规惩罚 |
| 4. 结果与环境 | 按动作结果扣除成本、结算资源、任务、宫门验核，并计算本帧鲜度损耗 |
| 5. 收尾 | 刷新普通任务，生成公开事件日志和下一帧状态 |

下面的明细是服务端执行顺序，主要用于处理同帧边界和回放校验：

| 顺序 | 结算内容 |
|---:|---|
| 1 | 收集双方提交的动作 |
| 2 | 推进已存在的持续效果，例如马类、疾行令、护果令等剩余帧数 |
| 3 | 清理已过期的探路标记 |
| 4 | 记录本帧开始时已有设卡的风化前防守快照 |
| 5 | 结算本帧设卡风化；本帧新提交的设卡、攻坚、增援、削弱和清除不会反向影响这一步 |
| 6 | 判定是否进入宫宴冲刺；触发时开放终局急策、S14 宫门验核和终段压力 |
| 7 | 结算本帧开始时已经到期的普通任务 |
| 8 | 按风化前快照和风化后仍存活状态判定破关悬赏 |
| 9 | 处理本帧到达生效帧的在途小分队战术 |
| 10 | 处理已有窗口的出牌 |
| 11 | 受理本帧提交的小分队战术 |
| 12 | 识别公共对象争夺并创建窗口，包括同帧争抢；若发生资源领取打断，也在本步中断原领取流程 |
| 13 | 对未进入窗口的普通处理动作锁定本帧成本，并拒绝同帧同对象冲突 |
| 14 | 按服务端主动作结算顺序逐队执行本帧主动作；每队执行前先判定该队是否缺动作、是否触发失联警告或退赛；已交付队伍只做交付后违规惩罚判断 |
| 15 | 每队主动作处理后，立即对未交付且未退赛队伍结算本帧鲜度损耗 |
| 16 | 若本帧是普通任务刷新帧，尝试刷新普通任务 |
| 17 | 生成公开事件日志和下一结算帧状态 |

同一结算帧内，服务端不得按阵营、玩家编号或玩家列表顺序分配资源、任务、公开处理点、通行窗口和宫门验核权益。需要从多个同帧候选中选择普通结算顺序时，服务端使用本局随机种子、结算帧、结算阶段、争用对象键和无序玩家集合生成可复现的公平槽位顺序；`playerId` 只用于身份标识、集合去重、日志和回放展示，不得作为单个玩家的排序盐或升降序依据。若双方反复发生会产生独占收益的真实争用，服务端还会使用三层公平账本：先看玩家对全局历史胜出次数，再看同阶段历史胜出次数，再看同对象历史胜出次数；次数更少的一方优先，同次数时再使用普通稳定裁决兜底。

破关悬赏和设卡风化落在同一结算帧时，按下表处理：

| 顺序 | 处理内容 |
|---:|---|
| 1 | 先记录本帧开始时已有设卡的风化前防守快照 |
| 2 | 再结算本帧设卡风化 |
| 3 | 用风化前快照评估“同一归属设卡防守值大于 0 连续存在 30 个结算帧”悬赏条件 |
| 4 | 若风化后的设卡仍有效且防守值（defense）仍大于 0，创建新悬赏 |

风化后防守值已经降到 0 的设卡，不会创建悬赏。

本帧动作造成的设卡创建、攻坚、削弱、增援和清除，从后续结算帧开始参与设卡风化和破关悬赏判定。客户端如果希望设卡或小分队影响天气/悬赏，需要提前一帧部署。

公共对象争抢按下表处理：

| 场景 | 结果 | 是否扣非法动作分 |
|---|---|---|
| 双方同一结算帧争抢同一任务、资源、前段交接、登船处理、水路换运、入关交接、宫前交接、宫门验核、障碍或通行目标 | 进入窗口争夺 | 否 |
| 该资源第 1 次发生资源领取打断 | 触发窗口争夺；原领取流程中断，双方进入窗口争夺 | 否 |
| 该资源第 2 次发生资源领取打断 | 返回对象忙，不再创建窗口争夺 | 否 |
| 双方同一结算帧在同一空节点设卡 | 不生成窗口；服务端按独占冲突公平账本选出一方进入设卡读条，其余方返回对象忙 | 否 |
| 双方同帧争抢同一不可窗口化对象，且该场景规则允许选出处理方 | 服务端按三层公平账本选出本帧处理方；另一方返回对象忙 | 否 |
| 一方已经开始处理非资源对象，另一方后续再抢同一对象 | 已开始处理的一方继续原处理；后抢的一方被拒绝，提示对象忙，不扣成本、不占对象、不影响对方 | 否 |

对象忙只表示目标已被占用：本次动作不生效、不扣惩罚、不排队、不打断对方，也不会自动改成移动或等待。队伍本帧仍按原状态结算；下一结算帧能做什么，按当时状态和对应动作规则重新判断。

处理占用规则：

| 问题 | 规则 |
|---|---|
| 处理流程是什么 | 服务端把动作登记为持续若干结算帧的处理中状态，并按结算节奏推进剩余帧数 |
| 处理期间锁什么 | 锁定对应对象，例如资源、任务、设卡、障碍、宫门或处理点 |
| 什么时候释放 | 处理完成、失败、中断、冻结好果被清算、目标丢失或退赛清理 |
| 处理期间，别人再抢同一非资源对象 | 不创建新窗口，返回对象忙拒绝；本次动作不生效、不扣成本、不计非法动作、不打断原处理，下一结算帧按当时状态重新判断 |
| 资源领取流程未结束时，另一方提交领取同一资源 | 第 1 次打断创建窗口争夺；第 2 次起返回对象忙拒绝 |
| 什么时候拿收益 | 处理完成后才结算动作收益 |

瞬发动作顺位规则：

| 动作 | 生效时点 | 特殊限制 |
|---|---|---|
| 使用资源（USE_RESOURCE） | 第 15 步主动作结算时瞬发 | 第 15 步动作校验未通过时不结算 |
| 使用冰鉴（ICE_BOX） | 第 15 步立即提高鲜度 | 鲜度小于等于 0 时不能使用；本次使用被拒绝且不消耗冰鉴 |
| 使用马类资源（FAST_HORSE / SHORT_HORSE） | 第 15 步立即生效 | 本帧及后续移动结算使用覆盖后的单帧移动量 |
| 使用情报（INTEL） | 第 15 步立即添加探路标记 | 只影响后续适用处理流程 |
| 交付（DELIVER） | 第 15 步成功后进入已交付（DELIVERED） | 不再参与本帧天气鲜度损耗和好果转坏果；若双方均已交付，本帧生成 over |

## 1.8 宫宴冲刺触发

宫宴冲刺（RUSH）是终局阶段。触发后开放终局急策和 S14 宫门验核，禁止新提交远程小分队战术，不生成额外得分任务。

触发规则：

- 对局已结束时不再判定。
- 第 390 结算帧前一定不触发。
- 第 450 结算帧时，若对局尚未结束，必定触发。
- 第 390-449 结算帧内，满足以下任一条件时触发：
  1. 任一队伍已经到达 `S14 朱雀门`。
  2. 任一队伍已经接近终点，且不位于终段交锋节点。终段交锋节点固定为 `S11`、`S12`、`S13`；接近终点指到 `S14` 的最短路线距离不超过 15，或按基础最快路线估算 60 个结算帧内可到达兴庆宫。

调测地图示例中，宫宴冲刺通常由“到达 S14”触发；接近终点判定用于覆盖不同路线距离下的终局提前进入情况。

判定方式：

每个结算帧开始时，系统先判断本帧是否进入 RUSH，再处理双方动作。只有本帧开始前已经满足触发条件，才会在本帧进入 RUSH；如果队伍是在本帧移动推进后才到达 `S14` 或进入触发范围，最早从下一结算帧开始进入 RUSH。这样可以保证双方在同一结算帧里使用同一套阶段规则。双方已交付并生成 `over` 后不再判定。

接近判定使用路线边距离 `edge.distance` 和基础路线到达帧数，不使用坐标距离，也不计入天气、马类、疾行令、干扰、设卡、障碍、窗口争夺、处理流程或任务处理。

宫宴冲刺触发后：

- 双方 `phase = RUSH`，持续到双方交付、退赛结束或第 600 结算帧。
- 开放终局急策；每队获得 1 次终局急策使用资格，可在疾行令、护果令、破关令中选择一种。
- 开放 S14 宫门验核；未进入宫宴冲刺前不能提交宫门验核。
- 禁止新提交远程小分队战术，已在途小分队继续按原到达帧结算。
- 双方围绕宫门窗口、终点交付和终局急策做最后决策；窗口争夺仍按原规则可提交兵争牌。

## 2.3 路线类型

路线耗时系数不是墙钟单位，也不是每帧新增移动量。它用于计算主车队到站所需移动量：`到站所需移动量 = 向上取整（路线距离 × 路线耗时系数）`。系数越高，同样路线距离需要积累的移动量越多，通常到站越慢；完整移动结算见 3.3。
文档表格使用千分展示值，服务端 JSON 配置使用小数值：官道 `1380` 对应配置 `1.38`。计算口径为 `到站所需移动量 = 向上取整（路线距离 × JSON 路线耗时系数 × 1000）`，等价于使用下表千分展示值计算。

| 路线 | 路线耗时系数（千分展示） | 每结算帧鲜度损耗 | 规则 |
|---|---:|---:|---|
| 官道 | 1380 | 0.055 / 结算帧 | 稳定主线，风险最低但高任务收益必须付出客观成本 |
| 水路 | 1250 | 0.045 / 结算帧 | 速度快、保鲜强，必须承担码头处理、暴雨和转线成本 |
| 山路 | 1780 | 0.07 / 结算帧 | 绕开部分主交锋点，任务补偿更集中，但通行仍慢 |
| 支路 | 1550 | 0.065 / 结算帧 | 用于转线和改变交锋地点，不作为第四条主收益路线 |

每结算帧鲜度损耗表示主车队处于该路线类型时，每经过 1 个结算帧减少多少鲜度。例：官道鲜度损耗为 `0.055 / 结算帧`，在官道上行驶 10 个结算帧，基础鲜度损耗为 `10 × 0.055 = 0.55`。若当时存在天气或急策倍率，再在这个基础上乘倍率。

配置文件、实时协议和回放中的路线类型（routeType）统一如下：

| 路线类型 | 协议枚举 |
|---|---|
| 官道 | 官道（ROAD） |
| 水路 | 水路（WATER） |
| 山路 | 山路（MOUNTAIN） |
| 策略支路 | 策略支路（BRANCH） |

当前地图的水路处理以本局 `gameplay.processNodes` 为准：

| 地图 | S04 处理 | S05 处理 |
|---|---|---|
| 调测图 `map_config.json` | 登船处理（BOARD）7 个结算帧 | 水路换运（WATER_TRANSFER）6 个结算帧 |
| A/B/C | 水路换运（WATER_TRANSFER）6 个结算帧 | 登船处理（BOARD）7 个结算帧 |

暴雨期间，本结算帧暴雨生效且命中水路移动时，水路路线成本倍率为 1.35，移动变慢；命中登船或水路换运处理时，对应处理帧数 +4 个结算帧。

路线收益目标：

| 项目 | 目标 |
|---|---|
| 三条主路线稳定任务链 | 原始任务分（taskScoreRaw）约 75 |
| 高阶路线组合 | 通过转线、清障、资源检查、关键关口处理或窗口争夺，可冲 90+ 原始任务分 |
| 水路速度与保鲜红利 | 按最终结算约 +6 到 +10 分估算，上限不超过 +12 分 |
| 支路转线成本 | 调测图、A、C 当前为 5 条支路，B 当前为 6 条支路；支路端点、距离、类型和方向以本局 `edges[]` 为准 |
| S07 / S08 / S09 转线收益 | 调测图中 S07、S08、S09 构成中后段资源争夺带；A/B/C 的资源投放以本局 `gameplay.resources` 为准 |
| 官道高收益约束 | 想拿 80+ 原始任务分，必须付出规则可结算的处理帧数、资源或路径成本 |

无对手时，成本可以来自清障、处理帧数、资源检查、路线绕行、关键关口处理或天气压力；有对手时，还可以来自窗口争夺。

路线均衡不依赖参赛程序自觉分流。ROAD / WATER / MOUNTAIN 都是可稳定完成比赛的主路线，BRANCH 只作为转线和交锋位置调整使用，不作为第四条独立主收益路线。普通任务刷新通过 `gameplay.routeTaskBuckets` 为 ROAD / WATER / MOUNTAIN 三条主路线稳定提供任务目标：每批默认刷新 3 个普通任务，并按 ROAD、WATER、MOUNTAIN 各 1 个路线桶尝试生成。

路线均衡由地图配置、任务供给和验收脚本保证；比赛进行中，系统不按路线自动补收益，也不按路线自动调低收益。

三条主路线的平衡口径如下：

| 路线 | 核心优势 | 必须承担的代价 | 调整目标 |
|---|---|---|---|
| 官道（ROAD） | 路线直观、处理稳定、天气波动小 | 高任务收益必须绑定清障、读条、资源检查、路线绕行、关键关口处理或窗口争夺等客观成本 | 不能和平白拿 80+ 原始任务分 |
| 水路（WATER） | 基础速度最快、保鲜压力最低 | 通常需要经过 S04/S05 的水路相关处理；具体处理类型、转线成本和暴雨压力看本局 `gameplay.processNodes` 与 `edges[]` | 不能同时拥有最快、最稳、最低成本转线 |
| 山路（MOUNTAIN） | 可绕开部分主交锋点，任务和资源补偿更集中 | 基础移动慢、鲜度损耗高；山雾只增加通行和探路延迟，不额外放大鲜度损耗 | 不能成为陷阱路线，也不能无代价反超 |

换地图或调参时，可以通过路线边清单（含数量、端点、类型、距离和双向标记）、S02-S13 坐标、路线显示路径、地图总览格子、地形格子、站点对象格子、天气区域格子、流程节点绑定、资源投放清单、任务候选点、路线任务桶和道路障碍候选点调整本局体验；不得为了补平衡新增动作、协议字段、资源效果、状态类型、天气类型、窗口牌型或新的结算阶段。

本章只说明路线读法和调测地图示例。移动公式、天气路线成本倍率和加速结算规则见 3.3。

## 2.9 兴庆宫终点

S15 兴庆宫是终点节点。交付前必须先在 S14 完成宫门验核（VERIFY_GATE）；验核成功后队伍获得 `verified = true`，之后才能进入 S15 并提交交付（DELIVER）。

| 队伍在 S15 的状态 | 可以做什么 |
|---|---|
| 未验核 | 不能交付；只能等待（WAIT）或返回 S14 重新验核 |
| 已验核但未交付 | 可以交付（DELIVER）；也可以等待（WAIT） |
| 已交付 | 允许提交等待（WAIT）、空动作心跳；重复交付（DELIVER）只作容错处理，不重复计分、不处罚；其他动作按交付后违规处理 |

S15 不挂载设卡、攻坚、资源、任务、小分队、窗口出牌或道路障碍。未验核队伍已经位于 S15 时，只能等待（WAIT）或通过 `S15 → S14` 返回朱雀门重新验核；该返回移动不清除 S14 上的设卡或障碍。

## 2.11 天气规则

每局固定触发 4 次天气事件。

服务端内部天气池分布为：

| 天气 | 池中数量 |
|---|---:|
| 酷暑（HOT） | 2 |
| 暴雨（HEAVY_RAIN） | 1 |
| 山雾（MOUNTAIN_FOG） | 1 |

该表是服务端实现配置，对参赛选手不可见；不通过实时协议下发，也不作为客户端可见信息。

天气类型中文含义：

| 天气类型 | 中文含义 | 说明 |
|---|---|---|
| 酷暑（HOT） | 酷暑 | 全图天气，提升鲜度损耗，使冰鉴（ICE_BOX）策略价值上升 |
| 暴雨（HEAVY_RAIN） | 暴雨 | 水路 / 码头天气，增加水路通行和码头处理成本 |
| 山雾（MOUNTAIN_FOG） | 山雾 | 山路 / 山区天气，降低山路本帧新增移动量并增加小分队探路延迟 |
| 无天气事件 | 无特殊天气 | 实时协议中不下发 `CLEAR` 天气枚举；没有生效天气时，`weather.active` 为空 |

天气生成与结算帧读法：

| 项目 | 规则 |
|---|---|
| 天气池 | 服务端内部配置：`HOT, HOT, HEAVY_RAIN, MOUNTAIN_FOG`；对参赛选手不可见 |
| 顺序生成 | 服务端用隐藏随机种子洗牌生成 4 次天气事件 |
| 相邻限制 | `avoidConsecutiveSame = true`，相邻两次天气不得同类 |
| 不确定性 | 开始结算帧窗口公开；天气池数量、完整顺序和精确 startRound 仅服务端提前可见，进入预告期后才同时告知双方 |
| 结算帧字段 | `startRound` 表示开始生效；`durationRound` 表示持续帧数，当前为 60 个结算帧 |
| 生效区间 | `startRound <= round < startRound + durationRound`；例如 200-259 生效，260 起结束 |

天气开始结算帧窗口是公开规则；具体 startRound 由服务端在窗口内生成，进入预告期后同时告知双方。

| 次序 | 公开的 startRound 取值窗口 | 赛中可见性 |
|---|---|---|
| 第 1 次天气 | 80-120 | 精确 startRound 进入预告期后可见 |
| 第 2 次天气 | 200-240 | 精确 startRound 进入预告期后可见 |
| 第 3 次天气 | 320-360 | 精确 startRound 进入预告期后可见 |
| 第 4 次天气 | 440-480 | 精确 startRound 进入预告期后可见 |

天气生命周期与可见性：

| 项目 | 规则 |
|---|---|
| 生成 | 按 `weatherPolicy.pool` 洗牌；相邻天气不得同类 |
| 预告 | `warningRound = 30`，提前 30 个结算帧同时告知双方 |
| 实时可见 | 实时协议只下发当前天气和已进入预告期的天气，不下发完整序列和隐藏随机种子 |
| 回放可见 | 回放文件记录完整天气序列、作用区域和随机种子 |

天气展示与规则影响：

| 天气 | 展示配置 | 主要规则影响 |
|---|---|---|
| 酷暑（HOT） | `1 / FULLSCREEN_OVERLAY`，全屏覆盖 | 未交付队伍鲜度损耗 ×1.5；不降低每帧新增移动量 |
| 暴雨（HEAVY_RAIN） | `2 / REGION_OVERLAY`，水路区域覆盖 | 暴雨区域命中移动位置时，本帧鲜度损耗 ×1.3；暴雨通行减速只作用于水路移动，命中水路移动时路线成本倍率为 1.35，移动变慢；命中登船或水路换运处理时，处理鲜度损耗 ×1.3、处理帧数 +4 个结算帧 |
| 山雾（MOUNTAIN_FOG） | `3 / REGION_OVERLAY`，山区区域覆盖 | 本结算帧山雾生效且命中山路移动时，山路路线成本倍率为 1.10，移动变慢；命中小分队探路处理时，小分队探路（SQUAD_SCOUT）延迟 +2 个结算帧；不额外放大鲜度损耗 |
| 无天气事件 | 无特殊覆盖 | 无附加影响；实时协议中表现为 `weather.active = []` |

同一结算帧最多只有 1 个天气事件生效；配置重叠时服务端拒绝加载。前端展示只看天气区域配置，规则结算看天气作用区域（region）、路线类型（routeType）和处理类型。

天气事件生效不代表一定影响某支队伍。每个结算帧，系统按队伍当前移动点或处理目标判断天气是否实际命中。路线成本倍率要求命中天气区域且路线类型匹配；天气鲜度系数按 3.4 的鲜度规则单独判断；处理加时要求处理对象和处理类型匹配。未命中时，本帧路线成本倍率为 1，天气鲜度系数为 1，处理加时为 0。

存在生效天气时，系统每帧记录天气命中日志。日志记录该队伍是否命中天气、命中的路线边或处理点、实际路线成本倍率、鲜度倍率和处理加时，用于解释为什么同一天气事件只影响部分队伍。

移动推进只看本结算帧正在生效且实际命中的天气。天气结束后的结算帧按无天气影响的路线成本倍率计算，已经走过的移动量不回算。

正式地图必须配置 `layers.weatherRegionData` 和 `weatherRegionRule`，服务端按天气区域格子判断暴雨、山雾等区域天气是否命中当前移动点或处理节点。地图输入字段统一使用 `weatherRegionData`；服务端内部对象、回放或调试示例中如出现 `weatherData`，表示同一天气区域数据的运行态别名，不代表存在第二套天气系统。旧版地图缺失天气区域时，服务端保留按路线类型或节点类型判断的兼容兜底；该兜底只用于历史地图兼容，不作为正式比赛地图的规则依赖。

## 2.12 道路障碍

道路障碍类型、影响对象与发生场景：

| 障碍类型 | 程序字段 | 具体影响对象 | 发生场景 | 可用处理方式 |
|---|---|---|---|---|
| 落石 | ROCKFALL | 山路沿线站点、栈道站点、关隘附近站点；进入这些站点的相邻路线 | 山路、栈道、关隘附近道路被落石阻塞 | 主车队清障、小分队清障、强制通行 |
| 水涨 / 洪水 | FLOOD | 水路沿线站点、码头、水驿；进入这些站点的水路路线 | 水位上涨或洪水导致水路通行受阻 | 主车队清障、小分队清障、强制通行 |
| 泥泞 | MUD | 官道、山路、策略支路沿线站点；进入这些站点的相邻路线 | 雨后、低洼地、湿地道路泥泞，导致普通移动无法进入目标站点 | 主车队清障、小分队清障、强制通行 |
| 码头阻塞 | DOCK_BLOCK | 码头站点、登船站点、水路换运站点；进入这些站点的相邻路线 | 码头入口、登船点或换运点被阻塞 | 主车队清障、小分队清障、强制通行 |
| 关口拥堵 | PASS_CROWD | 普通关隘、关键关隘、入关交接站点；进入这些站点的相邻路线 | 关隘前通行拥堵，影响车队进入关口站点 | 主车队清障、小分队清障、强制通行 |
| 断桥 | BROKEN_BRIDGE | 含桥梁语义的站点；进入该站点的相邻路线 | 桥梁损坏，导致对应站点无法普通进入 | 主车队清障、小分队清障、强制通行 |
| 山体滑坡 | LANDSLIDE | 山路入口、山道、栈道等山路沿线站点；进入这些站点的相邻路线 | 山体滑坡覆盖山路入口、山道或山路边道路 | 主车队清障、小分队清障、强制通行 |

道路障碍生效方式：

| 规则点 | 说明 |
|---|---|
| 挂载方式 | 道路障碍按站点挂载 |
| 生成时机 | 比赛开局时生成；中途不会随机新增道路障碍 |
| 移动影响 | 障碍存在时，普通移动（MOVE）不能直接进入对应站点 |
| 主车队清障代价 | 处理帧数固定为 6 个结算帧；消耗 1 个好果，提交时先冻结，完成后扣除；完成后清除目标障碍 |
| 小分队清障等待 | 按本队起算位置到目标站点的切比雪夫距离计算，详见 3.7 小分队战术 |
| T04 刷新 | T04 清障任务只能刷新到当前仍存在道路障碍的站点 |

小分队清障等待帧数按 3.7 小分队战术中的“小分队延迟”规则计算。本节只说明清障结果，不重复展开距离公式。

主车队普通清障（CLEAR）需要至少 1 个可支配好果；好果不足时返回资源不足，不能启动清障读条。T04 清障任务使用 CLAIM_TASK 处理，不等同于普通 CLEAR 的收益和成本。

道路障碍处理路径：

```mermaid
flowchart TD
  A["目标站点存在道路障碍"] --> B{"选择处理方式"}
  B --> C["普通清障：CLEAR / SQUAD_CLEAR"]
  B --> D["T04 清障任务：CLAIM_TASK"]
  B --> E["强制通行：FORCED_PASS"]
  B --> F["改走其他路线"]
  C --> C1["完成清障后障碍消失，不获得 T04 分"]
  C1 --> C2["记录清障方和清障帧"]
  C2 --> C3["清障方免残留税；非清障方 30 个结算帧内通过加 6 个结算帧"]
  D --> D1["完成处理后获得 T04 分"]
  D1 --> D2["同步清除目标障碍"]
  E --> E1["本队本次通过"]
  E1 --> E2["障碍仍存在，不创建清障残留"]
  F --> F1["障碍状态不变"]
```

处理结果说明：

| 处理路径 | 触发动作 | 障碍结果 | T04 结果 | 后续通行影响 |
|---|---|---|---|---|
| 普通清障 | 主车队清障（CLEAR） | 完成 6 个结算帧清障处理后，目标障碍消失；消耗 1 个好果，提交时先冻结，完成后扣除 | 不获得 T04 分；如果这个障碍已经被某个 T04 任务选为目标，但队伍没有用处理皇榜任务完成 T04，而是用普通清障把障碍清掉，则该 T04 作废，不给分，不重新刷新 | 记录清障方和清障帧，用于残留通行税 |
| 远程普通清障 | 小分队清障（SQUAD_CLEAR） | 消耗 2 名小分队人手；派出后按小分队等待帧数生效：按本队起算位置到目标站点的切比雪夫距离计算，最短 3 个结算帧、最长 15 个结算帧；等待结束时视为小分队抵达并完成清障，目标障碍消失，没有额外清障处理帧数 | 不获得 T04 分；如果这个障碍已经被某个 T04 任务选为目标，但被小分队清障清掉，则该 T04 作废，不给分，不重新刷新 | 记录清障方和清障帧，用于残留通行税 |
| T04 清障任务 | 处理皇榜任务（CLAIM_TASK，taskId 为 T04） | 完成处理后同步清除目标障碍 | 获得 T04 分；这是获得 T04 分的唯一方式 | 主车队可以停在障碍所在站点，也可以停在与该站点直接相连的相邻站点处理 T04。若从相邻站点完成，只代表隔着相邻路线把障碍清掉，不自动把主车队移动到目标站点，后续仍需按普通移动进入 |
| 强制通行 | 强制通行（FORCED_PASS） | 不清除障碍 | 不获得 T04 分 | 只允许本队本次通过，不创建清障残留 |

清障残留只由普通清障和小分队清障创建。T04 清障任务完成后不创建清障残留，后续队伍不会因为该障碍额外支付 6 个结算帧残留通行税。普通清障或小分队清障成功后，清障方后续通过该站点不支付残留通行税；非清障方在清障后 30 个结算帧内提交进入该站点的普通 MOVE 时，额外支付 6 个结算帧残留通行税。是否支付残留税按提交本次 MOVE 的结算帧判断；残留税在 MOVE 开始时直接加入本次路线总耗时。残留通行税不恢复障碍，也不改变 T04 已完成或失败状态。

| 挂载站点 | 默认障碍类型 | 相邻站点 | 设计作用 |
|---|---|---|---|
| S06 五岭山道 | 山体滑坡（LANDSLIDE） | S01、S03、S08 | 山路入口压力点，也是 T04 清障候选 |
| S08 秦岭栈道 | 落石（ROCKFALL） | S06、S07、S09、S10 | 山路中段压力点，连接武关和 E22 转线方向 |
| S10 武关 | 关口拥堵（PASS_CROWD） | S08、S09、S11 | 关键关隘压力点，也是 T11 / T14 候选 |
| S11 潼关驿 | 关口拥堵（PASS_CROWD） | S10、S12 | 终段入关压力点，多数路线都会接近 |

同一结算帧内 T04 与其他清障的冲突说明：

同一个道路障碍如果已经是 T04 任务目标，队伍可以选择做 T04，也可以选择普通清障，但二者不是同一个收益：做 T04 才有 T04 分；普通清障只清障。

本段只列同一结算帧内的清障冲突。这里有两类情况，不能混用：

1. 到期同帧：动作此前已经启动，本帧正好进入结果结算。用于“小分队清障到达”撞上“主车队 T04 / CLEAR 处理到期”。
2. 提交同帧：双方本帧才新提交同一障碍的 T04 / CLEAR。此时处理还没有开始，按窗口争夺处理。

小分队清障（SQUAD_CLEAR）提交时，只是把人派出去并扣除小分队人手；这一帧不会占住目标障碍，也不会立刻拉双方进入障碍窗口。等小分队到达那一帧，服务端再按 3.7 的到达校验规则检查目标是否仍然是道路障碍。

| 类型 | 同帧情况 | 结论 |
|---|---|---|
| 到期同帧 | 小分队清障本帧到达，主车队 T04 或 CLEAR 处理也在本帧到期 | 按 1.7 先处理小分队清障到达；该帧内障碍由小分队清除，主车队随后做完成检查时目标已不存在 |
| 提交同帧 | A 队本帧新提交 T04，B 队本帧新提交同一障碍的主车队清障 | 进入同一障碍窗口争夺；不按提交顺序或动作类型直接判胜 |

主车队普通清障（CLEAR）与 T04：

| 场景 | A 队结果 | B 队结果 | 说明 |
|---|---|---|---|
| A 队本帧新提交 T04，B 队本帧新提交同一障碍的主车队清障 | 不立即得分，进入同一障碍的窗口争夺 | 不立即清障，进入同一障碍的窗口争夺 | 窗口胜方按自己的动作继续：A 队胜出则处理 T04，完成后拿 T04 分；B 队胜出则普通清障，完成后只清障、不拿 T04 分 |

窗口失败方没有自动通行权，也不会因为失败立刻支付通行税。窗口结束后只由胜方继续原动作；败方后续要进入该站点时，按障碍最终状态重新移动或重新选择动作。

| 窗口胜方 | 障碍最终结果 | 失败方后续通行 |
|---|---|---|
| T04 方胜出 | 胜方完成 T04 处理后清除障碍，不创建清障残留 | 失败方后续可按普通移动进入，不支付清障残留通行税 |
| 普通清障方胜出 | 胜方完成主车队清障处理后清除障碍，并创建清障残留 | 失败方属于非清障方；若在清障后 30 个结算帧内通过该站点，额外支付 6 个结算帧残留通行税 |

小分队清障（SQUAD_CLEAR）与 T04：

| 场景 | A 队结果 | B 队结果 | 说明 |
|---|---|---|---|
| A 队 T04 处理在本帧到期；B 队小分队清障也在本帧到达 | A 队 T04 目标已被清掉，本次 T04 作废，不获得 T04 分 | B 队小分队完成普通清障，不获得 T04 分，并成为本次清障方 | 本帧内先处理小分队清障落地，再处理 T04 完成检查 |

主车队普通清障（CLEAR）与小分队清障（SQUAD_CLEAR）：

| 场景 | A 队结果 | B 队结果 | 说明 |
|---|---|---|---|
| A 队主车队清障处理在本帧到期；B 队小分队清障也在本帧到达 | A 队目标障碍已被清掉，本次主车队清障不再产生清障结果，不获得 T04 分 | B 队小分队完成普通清障，不获得 T04 分，并成为本次清障方 | 本帧内先处理小分队清障落地，再处理主车队清障完成检查 |

## 2.13 主车队碰撞规则

主车队之间不存在物理碰撞体积。

调测地图示例：红蓝双方可以同时停在 S10 武关，也可以同时位于 E05（S09 → S10）这条路线边上。普通移动是否被阻挡只看敌方有效设卡、道路障碍、宫门验核等移动规则；窗口争夺和处理占用只影响对应的处理或出牌动作。

规则：

- 双方主车队允许同时位于同一节点；
- 双方主车队允许同时位于同一路线边；
- 车队重叠不产生阻挡效果；
- 只有设卡、窗口争夺、道路障碍和规则处理流程产生通行影响。

## 2.14 策略支路

策略支路是 `routeType = BRANCH` 的路线边。它的作用不是新增主路线，而是把队伍从当前路线转向另一条路线，导向不同的资源、任务、关隘或障碍站点。

策略支路的逻辑：

| 规则 | 说明 |
|---|---|
| 从站点进入 | 主车队必须先到达支路起点站 |
| 按路线边移动 | 进入后按该边的距离和到站所需移动量移动到终点站 |
| 改变后续选择 | 到达终点站后，队伍按终点站的相邻路线继续选择 |
| 改变目标站点 | 支路会把队伍带向另一个资源、任务、关隘或障碍站点 |
| 不改通行规则 | 策略支路不新增动作类型，也不改变移动、处理、设卡、障碍和窗口争夺规则 |

策略支路清单以本局地图 `edges[]` 中 `routeType = BRANCH` 的路线边为准。地图可以增减或改接 BRANCH 边，只要仍通过地图校验、使用正式路线类型、不新增动作和结算机制即可。

当前地图策略支路摘要：

| 地图文件 | BRANCH 边 | 设计作用 |
|---|---|---|
| `map_config.json` | E13、E17、E18、E21、E22 | 调测图保留 5 条跨路线支路，提供水路、山路、官道之间的有限转线和关键节点争夺 |
| `map_config_variant_a.json` | E13、E17、E18、E21、E22 | 仍为 5 条支路，E18 改接 S02-S06，并拉长多条转线成本 |
| `map_config_variant_b.json` | E13、E17、E18、E20、E21、E22 | E20 从山路改为支路，当前为 6 条支路 |
| `map_config_variant_c.json` | E13、E17、E18、E21、E22 | E21 改为 S03-S05；E22 改为单向 S08 -> S11 |

调测地图示例的支路明细：

| 边 | 端点 | 距离 | 设计作用 |
|---|---|---:|---|
| E13 | S05 - S07 | 46 | 水路中段转入 S07 资源点和官道中段 |
| E17 | S08 - S10 | 46 | 山路关键点转入武关，服务 T11 / T14 和关口攻防 |

玩家判断“是不是支路”时，不看路线边编号的历史含义，只看本局 `edges[].routeType`。

# 3. 队伍、状态与运输

## 3.1 队伍结构

每支队伍包含以下内容：

| 组成 | 用途 | 消耗说明 | 后续变化说明 |
|---|---|---|---|
| 主车队 | 执行运输、移动、站点处理和交付 | 不消耗主车队本体 | 不涉及 |
| 小分队人手池 | 执行远程战术 | 远程战术会消耗人手池数量 | 消耗后不返还 |
| 护卫行动点 | 支付窗口争夺中的兵争牌（BING_ZHENG） | 兵争牌会消耗护卫行动点 | 消耗后不返还 |
| 资源库存 | 保存冰鉴、马类、过所、官凭、情报等资源 | 使用资源时消耗对应资源数量 | 已消耗资源不自行返还；新增资源按领取或规则结算进入库存 |
| 状态标签 | 标记当前是否移动、处理、休整、交付等 | 不消耗，只记录当前状态 | 按动作提交和结算结果切换 |

## 3.2 主车队状态枚举

主车队状态中文含义：

| 状态 | 说明 |
|---|---|
| 空闲（IDLE） | 停在节点上，可按当前位置提交合法主车队动作 |
| 移动中（MOVING） | 正在路线边上向下一目标节点前进 |
| 主动等待（WAITING） | 队伍在路线边上主动提交等待（WAIT）后，留在当前位置，已走移动量不增不减 |
| 休整中（RESTING） | 争夺平局、攻坚失败等规则导致的短暂休整 |
| 处理中（PROCESSING） | 正在执行资源、任务、清障、换运等处理流程 |
| 窗口争夺中（CONTESTING） | 正在参与三拍窗口争夺 |
| 强制通行中（FORCED_PASSING） | 正在通过强制通行穿越设卡或障碍 |
| 宫门验核中（VERIFYING） | 正在 S14 朱雀门进行验核 |
| 冻结好果被清算（COST_BANKRUPT） | 冻结好果在处理完成前被鲜度清算扣掉，本次处理失败、不产生收益；下一次动作包按所在节点的空闲规则提交 |
| 已交付（DELIVERED） | 已在 S15 兴庆宫完成交付结算 |
| 已退赛（RETIRED） | 连续缺动作达到退赛条件后不再参与正常结算 |

## 3.3 移动规则

主车队位置字段如下：

| 中文名 | 协议字段 | 单位 / 取值 | 停靠在节点时 | 移动中 |
|---|---|---|---|---|
| 当前节点 | currentNodeId | 节点编号 | 当前停靠节点，例如 S07 | 本段路线起点 |
| 下一目标节点 | nextNodeId | 节点编号或空 | 空，表示当前没有在路上的目标节点 | 本段路线终点 |
| 当前路线边 | routeEdgeId | 路线边编号或空 | 空，表示当前不在路线边上 | 本段正在走的路线边 |
| 推进方向 | moveDirection | 方向枚举 | 未移动（NONE） | 前进或暂停 |
| 当前路线边位置 | edgeProgressPermille | 0 到 1000 | 0 | 按已走移动量换算，只用于显示 |
| 已走移动量 | edgeProgressMs | 移动量 | 0 | 前进增加，暂停不变；改道时清零 |
| 到站所需移动量 | edgeTotalMs | 移动量 | 0 | 本段路线到站需要达到的移动量 |

移动中，位置只按当前路线边计算，不表示整张地图的进度。已走移动量（edgeProgressMs）达到到站所需移动量（edgeTotalMs）时，车队到达下一目标节点（nextNodeId）；当前路线边位置（edgeProgressPermille）只用于显示车队在本段路线上的位置。

路线推进方向（`moveDirection`）表示当前路线边上的推进方向：

| 方向 | 含义 |
|---|---|
| 未移动（NONE） | 未在路线边上移动，通常停靠在节点 |
| 前进（FORWARD） | 沿当前节点（currentNodeId）到下一节点（nextNodeId）前进，已走移动量（edgeProgressMs）增加 |
| 暂停（PAUSED） | 主动等待（WAITING）停在路线边上，已走移动量（edgeProgressMs）暂不变化 |

移动按累计进度结算：移动开始时确定到站所需移动量；主车队前进时，每个结算帧把本帧新增移动量加到已走移动量；已走移动量达到到站所需移动量时到站。

| 项目 | 规则 |
|---|---|
| 到站所需移动量（edgeTotalMs） | 移动（MOVE）通过校验后确定，计算方式为：向上取整（路线边距离 × JSON 路线耗时系数 × 1000） |
| 已走移动量（edgeProgressMs） | 当前路线边上已经累计的移动量；前进时增加，主动等待暂停时不变；这不是地图距离 |
| 每帧新增移动量 | 使用下方千分展示值时，计算为：向下取整（速度增益后的单帧移动量 × 1000 ÷ 天气路线成本倍率） |
| 天气路线成本影响 | 每个结算帧只看本帧正在生效且实际命中的天气；本帧暴雨命中水路时影响水路，本帧山雾命中山路时影响山路，酷暑不影响移动推进；天气未命中当前移动点或路线类型不匹配时，按无天气影响的路线成本倍率计算；天气结束后的结算帧按无天气影响的路线成本倍率计算，已经走过的移动量不回算 |
| 目标节点 | 移动开始时锁定，途中不因天气或加速改变 |
| 额外通行帧 | 清障残留通行税、设卡时间税、障碍时间税单独结算，不放进到站所需移动量公式里相乘 |

| 路线类型 | 路线耗时系数（千分展示） |
|---|---:|
| 官道（ROAD） | 1380 |
| 水路（WATER） | 1250 |
| 山路（MOUNTAIN） | 1780 |
| 策略支路（BRANCH） | 1550 |

| 天气 | 天气路线成本倍率（千分展示） |
|---|---:|
| 无影响天气 | 1000 |
| 暴雨作用于水路 | 1350 |
| 山雾作用于山路 | 1100 |
| 酷暑 | 1000 |

| 状态 | 速度增益后的单帧移动量（tickProgressMs） |
|---|---:|
| 无加速 | 1000 |
| 快马（FAST_HORSE） | 1200 |
| 短程马（SHORT_HORSE） | 1150 |
| 疾行令（RUSH_SPEED） | 1300 |

快马、短程马和疾行令会增加速度增益后的单帧移动量；暴雨和山雾只在本结算帧天气生效、命中当前移动点且路线类型匹配时提高本帧路线成本倍率，减少单帧移动量。天气鲜度系数另按 3.4 结算。二者都只影响本帧新增移动量，不回算已经走过的移动量。

例：一段路线的到站所需移动量为 60000。晴天、无加速时每帧新增移动量为 1000，约 60 帧到站；本结算帧暴雨影响水路时，本帧新增移动量为向下取整（1000 × 1000 ÷ 1350）。

当已走移动量（edgeProgressMs）大于等于到站所需移动量（edgeTotalMs）时，主车队进入目标节点（nextNodeId）。到站所在结算帧的鲜度损耗仍按本帧实际完成的路线类型计算，不因到站后路线类型被清空而回退为默认移动损耗。

到站当帧完成位置更新，目标节点动作从下一结算帧开始提交。

```mermaid
flowchart TD
  A["本结算帧开始"] --> B["校验本帧已提交动作"]
  B --> C["第 15 步执行主动作并推进移动"]
  C --> D{"本帧是否到达目标节点"}
  D -- "否" --> E["继续留在路线边上"]
  D -- "是" --> F["本帧进入目标节点"]
  F --> G["下一结算帧可提交目标节点动作"]
```

到站当帧的结算结果是进入目标节点。目标节点上的任务、验核、交付、处理或清障，从下一结算帧开始提交和结算。

主车队在路线边上时，本次主动动作只支持继续前进、主动等待暂停，或放弃旧边进度后从当前节点改道。

| 提交目标 | 本次结算结果 |
|---|---|
| 目标节点（targetNodeId）等于下一目标节点（nextNodeId） | 从当前位置继续前进 |
| 主动提交等待（WAIT） | 停在当前路线边上，已走移动量保持不变，moveDirection 为 PAUSED |
| 缺失动作或空动作心跳 | 服务端按系统等待续行，继续向 nextNodeId 前进 |
| 目标节点（targetNodeId）不是下一目标节点，但从 currentNodeId 存在合法相邻边 | 放弃当前路线边已走进度，从 currentNodeId 改道到新目标节点，edgeProgressMs 从 0 重新累计 |
| 目标节点（targetNodeId）无合法相邻边 | 动作结果为非法或拒绝，位置和当前目标保持不变 |

主动等待会停在当前路线边上；下一次移动可继续前进，也可以改道重新出发，但不能原路返回递减 edgeProgressMs。

```mermaid
flowchart TD
  A["路线边上前进"] --> B{"提交等待（WAIT）"}
  B -- "是" --> C["停在当前位置，已走移动量保持不变"]
  C --> D{"下一次提交移动"}
  B -- "缺失动作 / 空动作心跳" --> E["系统等待续行，继续向 nextNodeId 前进"]
  D -- "目标为下一目标节点" --> F["从当前位置继续前进"]
  D -- "目标为 currentNodeId 的其他相邻节点" --> G["放弃旧进度并从 currentNodeId 改道"]
  D -- "目标无合法相邻边" --> H["返回非法或拒绝结果，位置和目标保持不变"]
```

路线边是否双向由本局 `edges[].bidirectional` 决定；车队在路线边上不能原路返回递减 `edgeProgressMs`。

| 场景 | 规则 |
|---|---|
| 双向边（bidirectional = true） | 停靠在任一端点时，可向另一端点发起普通移动 |
| 单向边（bidirectional = false） | 停靠在起点时可向终点发起普通移动；反向不属于合法相邻目标 |
| 推导合法目标 | 参赛程序根据当前停靠节点、相邻路线边端点和双向配置，判断可提交的目标节点 |
| 路线边上改道 | 车队已经在路线边上时，若提交 currentNodeId 的其他合法相邻节点，服务端清空旧路线边进度并从 currentNodeId 重新出发 |

## 3.4 鲜度损耗

每个结算帧结束时扣除鲜度。

本帧鲜度扣除值 = 基础鲜度扣除值 × 天气鲜度系数 × 急策鲜度系数。

| 对战阶段 | 当前状态 | 基础鲜度扣除值 |
|---|---|---:|
| 停靠 | 空闲（IDLE） | 0.05 |
| 路线移动 | 官道移动 | 0.055 |
| 路线移动 | 水路移动 | 0.045 |
| 路线移动 | 山路移动 | 0.07 |
| 路线移动 | 支路移动 | 0.065 |
| 路线移动 | 主动等待（WAITING） | 0.05 |
| 强制通行 | 为穿过设卡或障碍额外等待 | 0.05 |
| 强制通行 | 未到达目标节点前实际走路线边 | 按官道、水路、山路或支路移动取值 |
| 节点行动 | 站点处理 | 0.05 |
| 节点行动 | 宫门验核中（VERIFYING） | 0.05 |
| 窗口与休整 | 窗口争夺中（CONTESTING） | 0.05 |
| 窗口与休整 | 休整中（RESTING） | 0.05 |
| 失败提示 | 冻结好果被清算（COST_BANKRUPT） | 不单独扣鲜度 |

| 天气情况 | 天气鲜度系数 |
|---|---:|
| 无影响天气 | ×1 |
| 酷暑（HOT） | ×1.5 |
| 暴雨区域内移动、登船处理、水路换运 | ×1.3 |
| 山雾（MOUNTAIN_FOG） | ×1 |

天气鲜度系数只在本帧天气实际命中队伍状态时生效。移动鲜度按天气区域命中判断；队伍移动位置落在暴雨区域内时，本帧鲜度系数按暴雨规则生效，不额外要求当前路线类型必须是水路。处理鲜度仍要求处理对象和处理类型匹配。

| 急策状态 | 急策鲜度系数 |
|---|---:|
| 疾行令（RUSH_SPEED）生效中 | ×1.25 |
| 护果令（RUSH_PROTECT）生效中 | ×0.2 |
| 其他情况 | ×1 |

鲜度结算后限制在 0-100。低于 0 记为 0，高于 100 记为 100。

## 3.5 好果转坏果

鲜度只表示好果品质。坏果只记录数量，不记录鲜度。

鲜度第一次低于 90、80、70、60、50、40、30、20、10 中任一数值时，触发好果转坏果。每个数值整局最多触发一次。

冰鉴（ICE_BOX）提高当前鲜度，但不重置已经触发过的转坏记录。鲜度先跌破 90 并触发转坏后，即使通过冰鉴回升到 90 以上，后续再次跌破 90 也不重复触发该数值。

本节的好果总量指可支配好果和冻结好果之和。

| 情况 | 处理 |
|---|---|
| 鲜度第一次低于 90、80、70、60、50、40、30、20 或 10 | 每首次低于一个数值，1 篓好果转为坏果 |
| 好果转坏果时 | 先扣可支配好果，不足时扣冻结好果 |
| 扣到冻结好果 | 对应处理进入冻结好果被清算（COST_BANKRUPT） |
| 好果总量变为 0 | 鲜度记为 0，坏果保留 |
| 本帧鲜度降为 0 后仍有好果 | 剩余好果全部报废，不增加坏果 |

冻结好果被鲜度清算扣掉时，进入冻结好果被清算（COST_BANKRUPT）。本次处理失败，不产生收益。已扣掉的好果不返还，剩余冻结成本释放。下一次动作包按所在节点的空闲规则提交。

## 3.6 资源使用

资源用途如下：

| 资源 | 用途 |
|---|---|
| 冰鉴（ICE_BOX） | 鲜度 +10，上限 100；鲜度小于等于 0 时不能使用；不影响坏果 |
| 快马（FAST_HORSE） | 使用后持续 20 个结算帧，基础推进量提升 20%；也可支付强行（QIANG_XING）的出牌成本 |
| 短程马（SHORT_HORSE） | 使用后持续 14 个结算帧，基础推进量提升 15%；也可支付强行（QIANG_XING）的出牌成本 |
| 船权（BOAT_RIGHT） | 码头资源标记；可以领取入库，不支持主动使用（USE_RESOURCE） |
| 过所（PASS_TOKEN） | 支付验牒（YAN_DIE）的出牌成本 |
| 官凭（OFFICIAL_PERMIT） | 支付验牒（YAN_DIE）的出牌成本 |
| 情报（INTEL） | 给近距离目标节点添加己方探路标记，本队后续适用处理帧数 -3 个结算帧，最低 2 个结算帧 |

过所和官凭的结算功能相同，有效用途是支付验牒（YAN_DIE）的出牌成本。二者可能出现在不同站点，代表不同获取路线和资源点位；支付验牒时，系统自动消耗 1 个可用文书资源。若参赛程序在可使用资源的状态下主动提交 `USE_RESOURCE` 使用过所或官凭，系统会自动扣除对应资源，但不产生主动效果，已扣资源不返还。参赛程序不应依赖过所和官凭的消耗先后。

窗口出牌成本见 4.8。本节只说明资源用途。

一次领取资源（CLAIM_RESOURCE）只领取目标节点上的一种资源类型。资源争夺对象由目标节点（targetNodeId）和资源类型（resourceType）共同决定。

资源有两处记录：节点资源库存表示还在地图上的资源，队伍资源库存表示队伍已经拿到手的资源。领取成功时，节点库存减少，队伍库存增加。

| 记录 | 字段 | 含义 | 变化 |
|---|---|---|---|
| 节点资源库存 | inquire.nodes[].resourceStock | 当前节点还剩哪些资源 | 领取成功时，对应资源 -1 |
| 队伍资源库存 | players[].resources | 队伍已持有、尚未消耗的资源 | 领取成功时，对应资源 +1；使用成功时，对应资源 -1 |

资源领取规则：

| 场景 | 处理 |
|---|---|
| 主车队停靠在目标资源节点，且目标节点等于当前节点 | 可以提交领取资源（CLAIM_RESOURCE） |
| 领取成功 | 目标节点该资源库存 -1，本队该资源 +1 |
| 位置不符 | 返回动作拒绝 / 不在目标节点（ACTION_REJECTED / NOT_AT_TARGET_NODE），不进入处理 |
| 库存不足 | 返回动作拒绝 / 资源不足（ACTION_REJECTED / RESOURCE_NOT_ENOUGH），不进入处理 |
| 同一队伍领取不同资源类型 | 每种资源类型分别提交领取动作；领取开始和读条完成时都要求该站该资源仍有库存，读条完成时库存不足则本次领取失败并返回资源不足 |
| 背包上限 | 没有额外背包上限；持有数量由地图库存、领取结果和使用消耗决定 |

资源领取争夺规则：

| 场景 | 处理 |
|---|---|
| 同一节点同一资源类型 | 争夺同一资源，触发资源窗口 |
| 同一节点不同资源类型 | 分别处理，不互相争夺 |
| 一方正在领取某资源，另一方后续到达同一节点并领取同一资源类型 | 当前领取中断，进入资源窗口；胜方从头开始领取 |
| 同一资源已经被打断过 1 次 | 第 2 次起返回对象忙（OBJECT_BUSY） |

情报（INTEL）用于在近距离公开节点放置本队探路标记。探路标记的持续帧数、消耗和减时规则见 3.8。

| 规则点 | 说明 |
|---|---|
| 提交要求 | 使用情报必须填写目标节点（targetNodeId），目标节点必须公开存在 |
| 提交状态 | 只能在主车队停靠在节点时使用；路线边移动中或路线边主动等待时不能使用 |
| 从哪算起 | 从当前停靠节点算 |
| 距离算法 | 按当前公开路线图的最短路线距离计算，只累计路线距离（edge.distance），不看坐标直线距离 |
| 距离上限 | 当前上限为 15。超过时返回动作拒绝 / 目标不可达（ACTION_REJECTED / TARGET_NOT_REACHABLE），不消耗情报 |
| 成功效果 | 目标节点获得本队探路标记。本队后续在该节点处理时，处理帧数减少 3 个结算帧，最低 2 个结算帧 |
| 可见性 | 探路标记是公开节点状态。对方能看到标记归属，但不能使用本队标记 |
| 信息范围 | 不揭示隐藏信息，不改变资源库存可见性 |

马类增益覆盖规则：

| 场景 | 规则 |
|---|---|
| 当前没有马类增益 | 使用快马或短程马时，消耗 1 个对应资源，获得对应增益 |
| 当前已有马类增益 | 再使用快马或短程马时，消耗新资源，替换为新马类增益。旧增益失效，旧资源不返还 |
| 生效时机 | 使用成功后，若本帧有移动结算，就使用新的单帧移动量；后续移动也使用新的单帧移动量 |
| 与疾行令关系 | 马类增益和疾行令不能同时生效。已有其中一种时，使用另一种会失败，且不消耗对应成本 |

马类资源数值：

| 资源 | 持续帧数 | 移动推进加成 |
|---|---:|---:|
| 快马（FAST_HORSE） | 20 个结算帧 | +20% |
| 短程马（SHORT_HORSE） | 14 个结算帧 | +15% |

## 3.7 小分队战术

每队初始小分队人手池为 8。战术表里的 1、2、2、2 是单次提交成本，不是把 8 人分成 4 份。

每个结算帧最多提交 1 个小分队动作。提交 2 个及以上时，本帧小分队动作都不执行，不消耗小分队人手，并记录同类动作冲突（INVALID_ACTION_CONFLICT）。

提交成功后立即扣除小分队人手，并进入在途状态。人手不足时返回资源不足（RESOURCE_NOT_ENOUGH），不扣人手，也不进入在途队列。

单次战术规则：

| 战术 | 消耗人手 | 到达时必须满足 | 成功结果 |
|---|---:|---|---|
| 小分队探路（SQUAD_SCOUT） | 1 | 目标节点存在 | 目标节点获得本队探路标记 |
| 小分队清障（SQUAD_CLEAR） | 2 | 目标仍为道路障碍 | 目标道路障碍被清除，本队成为清障方。对方 30 个结算帧内通过该节点，加 6 个结算帧残留通行税 |
| 小分队增援（SQUAD_REINFORCE） | 2 | 目标为本队有效设卡节点 | 目标本队有效设卡防守值 +2，不超过该节点防守值上限 |
| 小分队削弱（SQUAD_WEAKEN） | 2 | 目标为敌方有效设卡节点 | 目标敌方有效设卡防守值 -2。不足 2 时降为 0，设卡不再阻挡通行 |

增援、削弱只作用于防守值大于 0 的有效设卡。小分队提交成功时就按下表确定几帧后生效，派出小分队不会移动主车队。

计算方式：

| 项目 | 规则 |
|---|---|
| 可派范围 | 不设额外距离上限。目标节点满足对应战术条件即可提交 |
| 起算位置 | 停靠时用当前节点坐标，移动中用本段路线起点坐标 |
| 目标位置 | 目标节点坐标 |
| 距离 D | 切比雪夫距离公式：横向差 `dx = abs(x1 - x2)`，纵向差 `dy = abs(y1 - y2)`，`D = max(dx, dy)` |
| 基础延迟 | min(15, max(3, ceil(D / 3)))。距离超过 45 时仍按 15 帧计算 |
| 山雾影响 | 提交时目标节点处于山雾作用区域，且战术是小分队探路（SQUAD_SCOUT）时，基础延迟 +2 帧，仍不超过 15 帧 |
| 其他天气 | 暴雨、酷暑和晴朗不影响小分队生效帧 |
| 生效帧 | 提交帧 + 最终延迟。提交成功后，后续天气变化不重算 |

下表为调测地图示例，只说明小分队延迟计算，不代表固定点位：

| 提交位置 | 目标节点 | 坐标差 | 距离 D | 锁定延迟 | 读法 |
|---|---|---:|---:|---:|---|
| S10 武关 (62,26) | S11 潼关驿 (66,22) | 横向 4，纵向 4 | 4 | 3 | 公式算出 2 帧，低于下限，最终按 3 帧生效 |
| S07 荆襄大驿 (40,36) | S08 秦岭栈道 (42,24) | 横向 2，纵向 12 | 12 | 4 | 公式算出 4 帧，最终按 4 帧生效 |
| S01 岭南果园 (5,50) | S10 武关 (62,26) | 横向 57，纵向 24 | 57 | 15 | 公式算出 19 帧，高于上限，最终按 15 帧生效 |

到达生效帧时，按“单次战术规则”表重新校验目标。目标不满足时，本次战术失败，已消耗人手不返还。

已经在途的小分队落地，不占用本帧新提交小分队动作名额。某帧有小分队落地时，本帧仍可新提交 1 个小分队动作。

同一结算帧有多个已在途小分队在同一节点生效时，按以下顺序处理：

| 顺序 | 战术 |
|---:|---|
| 1 | 小分队增援（SQUAD_REINFORCE） |
| 2 | 小分队削弱（SQUAD_WEAKEN） |
| 3 | 小分队清障（SQUAD_CLEAR） |
| 4 | 小分队探路（SQUAD_SCOUT） |

小分队落地校验早于本帧主车队处理完成。因此，本帧才完成的设卡不能被同帧小分队增援。设卡完成后的下一结算帧起，才可作为增援目标。

## 3.8 探路标记

探路标记可以由情报（INTEL）或小分队探路（SQUAD_SCOUT）生成。

| 规则点 | 规则 |
|---|---|
| 持续帧数 | 标记生成后保留 45 个结算帧。期限内主车队到达该节点并开始适用动作，本次动作处理帧数减少 |
| 减时效果 | 适用动作处理帧数减少 3 个结算帧，最低 2 个结算帧。宫门验核绑定破关令时按 5.5 处理 |
| 多个标记 | 同队同节点可保留多个探路标记。一次动作只使用 1 个，只减 3 个结算帧，多个标记不会累加减时。剩余标记可用于后续适用动作，45 个结算帧内未使用则过期 |
| 使用顺序 | 适用动作成功完成时，消耗最早获得的 1 个探路标记 |
| 未成功完成 | 动作失败、中断或平局时不消耗探路标记。标记未过期时，后续适用动作仍可使用 |
| 标记到期 | 到期后移除。已经开始并获得减时的动作，不因标记中途到期变长 |
| 可见性 | 只减少动作处理帧数，不揭示隐藏信息，不改变资源库存可见性 |

适用范围：

| 适用动作 / 处理类型 | 说明 |
|---|---|
| 领取资源（CLAIM_RESOURCE） | 领取节点资源 |
| 处理皇榜任务（CLAIM_TASK） | 处理指定皇榜任务 |
| 宫门验核（VERIFY_GATE） | 宫宴冲刺后在 S14 朱雀门验核 |
| 主车队清障（CLEAR） | 清理道路障碍 |
| 通用处理（PROCESS） | 执行当前节点公开处理流程 |
| 前段交接（TRANSFER） | 通用处理（PROCESS）的处理类型 |
| 登船处理（BOARD） | 通用处理（PROCESS）的处理类型 |
| 水路换运（WATER_TRANSFER） | 通用处理（PROCESS）的处理类型 |
| 入关交接（PASS_TRANSFER） | 通用处理（PROCESS）的处理类型 |
| 宫前交接（PALACE_TRANSFER） | 通用处理（PROCESS）的处理类型 |

## 3.9 护卫行动点

每队初始护卫行动点为 4，协议字段为护卫行动点（guardActionPoint）。护卫行动点只用于窗口出牌中的兵争牌（BING_ZHENG）。

| 规则项 | 处理 |
|---|---|
| 兵争牌成本 | 每提交 1 次兵争牌（BING_ZHENG），消耗 1 点护卫行动点 |
| 护卫行动点不足 | 兵争牌失效，本拍按弃权（ABSTAIN）处理 |
| 已消耗护卫行动点 | 不会恢复 |
| 和小分队人手的区别 | 护卫行动点只支付兵争牌，小分队人手只支付小分队战术，二者不能互相替代 |

# 4. 争斗规则

## 4.1 争斗类型

争斗入口分为两类：

| 类型 | 处理方式 | 规则 |
|---|---|---|
| 设卡争斗 | 攻坚破卡（BREAK_GUARD） | 攻坚值大于等于防守值时清除设卡。清除相邻节点设卡后，车队仍停在原节点；要进入该节点，之后还要提交移动。 |
| 设卡争斗 | 强制通行（FORCED_PASS） | 不清除设卡，只争取本队本次通过。遇到敌方有效设卡时进入通行窗口（PASS）；攻方胜出后自动支付时间税并继续走路线，守方胜或平局时留在原节点并休整。 |
| 普通窗口争夺 | 同帧争抢 / 资源打断 | 双方同一结算帧争抢同一资源、任务、处理点、宫门验核或障碍清理时生成窗口。资源领取流程未结束时，第 1 次领取打断也生成资源窗口；第 2 次起返回对象忙。 |

边界说明：

- 攻坚破卡只处理设卡本身，不移动车队。
- 强制通行遇到敌方有效设卡时，先进入通行窗口；攻方胜出后继续通行，守方胜或平局时留在原节点并休整。
- 资源领取是唯一可被后续动作打断的处理流程；任务、宫门、码头或障碍开始处理后，另一方不能打断。

## 4.2 固定处理动作成本结算

以下动作开始处理后，会先占用本次目标；有成本的，同时冻结对应成本：

| 动作 | 占用目标 | 冻结成本 |
|---|---|---|
| 设卡（SET_GUARD） | 目标节点的设卡位 | 节点基础好果 + 强化投入好果 |
| 领取资源（CLAIM_RESOURCE） | 目标资源 | 无 |
| 处理皇榜任务（CLAIM_TASK） | 任务实例 | 按任务规则 |
| 宫门验核（VERIFY_GATE） | 宫门验核对象 | 绑定破关令时冻结急策次数和对应果品 |
| 主车队清障（CLEAR） | 目标障碍 | 无 |
| 通用处理（PROCESS） | 当前节点处理点 | 按处理点规则 |

参赛程序只提交通用处理（PROCESS）。具体处理内容由当前节点的处理类型（processType）决定。

锁定成本的含义：

动作开始处理时，系统占用本次目标，并冻结本次成本。处理期间，目标不能被重复处理，冻结成本也不能用于其他动作；处理完成、失败、中断或释放时，再按结果扣除或解除冻结。

```mermaid
flowchart TD
  A["动作启动前校验成本和状态"] --> B{"是否通过"}
  B -- "否" --> R["拒绝，不占用目标，不冻结成本"]
  B -- "是" --> C["创建处理流程，占用目标并冻结成本"]
  C --> D["按结算节奏推进处理进度"]
  D --> E{"完成前二次校验"}
  E -- "通过" --> F["正式扣除冻结成本"]
  F --> G["结算动作效果"]
  E -- "失败 / 中断" --> H["解除目标占用和剩余成本冻结"]
  H --> I["处理失败，不产生收益"]
```

锁定期间，公开状态里的可支配好果（goodFruit）只表示还能使用的好果；冻结好果（frozenGoodFruit）表示已经被当前处理流程占用的好果。

主车队处于处理、验核或强制通行读条中时，提交新的主车队动作不会打断当前读条；本次提交不生效、不扣成本、不计非法动作，当前读条继续推进。休整中提交非等待动作时，不生效、不扣成本、不计非法动作，休整倒计时继续。

| 情况 | 处理 |
|---|---|
| 处理成功完成 | 正式扣除冻结成本 |
| 处理被打断、平局、状态非法、目标丢失或退赛清理 | 解除目标占用；未正式扣除的成本解除冻结 |
| 冻结好果在处理期间被鲜度清算转坏或报废 | 本次处理进入冻结好果被清算（COST_BANKRUPT）；已损失的好果不返还 |
| 坏果、资源或急策次数作为绑定成本 | 按该动作自己的规则冻结或预留；窗口失败或平局时解除，胜出并正式开始处理时扣除 |

完成前二次校验检查：

| 检查项 | 要求 |
|---|---|
| 目标对象 | 仍然存在 |
| 队伍状态 | 仍允许完成该处理 |
| 位置 | 仍满足本动作的位置要求 |
| 成本 | 冻结成本仍可扣除；若成本是好果，冻结好果仍能支付本次处理 |
| 对象匹配 | 任务、资源、障碍、宫门、处理点等对象仍与本次处理匹配 |

中断情况：

| 中断原因 | 中断后处理 |
|---|---|
| 窗口争夺打断、窗口平局、状态切换中断、状态非法、冻结好果被清算、退赛 | 处理进度清零；解除目标占用和剩余成本冻结；不产生动作收益 |

公共对象占用表：

| 动作 | 占用对象（objectKey） | 含义 |
|---|---|---|
| 处理皇榜任务（CLAIM_TASK） | 任务对象（TASK:{taskId}） | 对应任务实例 |
| 领取资源（CLAIM_RESOURCE） | 资源对象（RESOURCE:{targetNodeId}:{resourceType}） | 目标节点上的对应资源 |
| 宫门验核（VERIFY_GATE） | 宫门对象（GATE:{targetNodeId}） | 目标节点的宫门验核 |
| 通用处理（PROCESS） | 处理点对象（PROCESS:{targetNodeId}:{processType}） | 目标节点的对应处理点 |
| 主车队清障（CLEAR） | 障碍对象（OBSTACLE:{targetNodeId}） | 目标节点障碍 |
| 强制通行（FORCED_PASS）穿过设卡 | 通行对象（PASS:{targetNodeId}:{guardOwnerTeamId}） | 目标节点的敌方设卡通行权 |
| 强制通行（FORCED_PASS）穿过道路障碍 | 障碍通行对象（PASS:{targetNodeId}:OBSTACLE:{teamId}） | 本队本次障碍通行权 |

T04 占用补充：

T04 属于处理皇榜任务（CLAIM_TASK）；当 T04 目标是道路障碍时，本次处理同时占用任务对象和目标障碍。

## 4.3 设卡（SET_GUARD）

设卡提交与生效规则：

| 项目 | 规则 |
|---|---|
| 基础成本 | 按目标节点类型支付好果 |
| 强化投入（extraGoodFruit） | 提交时可额外投入 0、1 或 2 篓好果 |
| 参数范围 | extraGoodFruit 只能为 0、1、2；越界返回 ACTION_REJECTED / PARAM_OUT_OF_RANGE，不截断、不扣成本、不进入处理 |
| 设卡读条帧数 | 提交后等待 4 个结算帧，完成后生成设卡 |
| 完成后防守值 | 基础防守值 2 + 强化投入 × 2 |

道路障碍和主动设卡是两种阻挡：

| 类型 | 来源 | 处理方式 |
|---|---|---|
| 道路障碍 | 地图或系统生成，例如落石、泥泞、关口拥堵 | 清障、强制通行或绕路 |
| 主动设卡 | 队伍提交设卡（SET_GUARD）生成 | 攻坚破卡、强制通行，或等待防守值随风化降到 0 后失效 |

主动设卡规则：

| 站点情况 | 调测地图示例触发位置 | 是否允许设卡 | 基础成本 |
|---|---|---|---:|
| 普通可设卡站点 | 沿途非关键关隘、非宫门、非终点的站点 | 允许 | 0 篓好果 |
| 关键关隘 | S10 武关 | 允许 | 1 篓好果 |
| 宫门 | S14 朱雀门 | 允许 | 1 篓好果 |
| 终点 | S15 兴庆宫 | 禁止 | - |

设卡提交规则：

- 设卡目标必须是主车队当前所在节点。
- 道路障碍不算已有设卡；有道路障碍的站点仍可主动设卡。
- 每个节点同一时刻最多有 1 个有效设卡；目标节点已有有效设卡时，本次设卡返回对象忙，不扣成本，不进入处理。
- 双方同一结算帧在同一空节点设卡时，不生成窗口；服务端按独占冲突公平账本选出一方进入设卡读条，其余方返回对象忙（OBJECT_BUSY）。该裁决不按阵营、playerId、连接顺序或包到达顺序选边。

防守值上限：

| 主动设卡位置 | 设卡防守值上限 |
|---|---:|
| 普通可设卡站点设卡 | 6 |
| 关键关隘设卡 | 7 |
| 宫门设卡 | 4 |
| 已有道路障碍的站点设卡 | 5 |

每队有效设卡节点上限为 2。

新设卡完成后，若本队有效设卡数量超过 2，系统移除本队最早完成的有效设卡；被移除设卡已扣除的设卡成本不返还。

设卡完成当帧不拦截敌方，从下一结算帧开始阻挡敌方；完成当帧进入该站点的敌方车队不会被本次设卡拦停，设卡仍生成并扣除成本。

防守值 = min(节点类型防守上限, 基础防守值 2 + extraGoodFruit × 2)

普通移动（MOVE）遇到目标节点存在敌方有效设卡时，返回动作拒绝 / 设卡阻挡（ACTION_REJECTED / MOVE_BLOCKED_BY_GUARD），不计非法动作。普通移动被设卡挡住不累计破关悬赏的有效防守事件；普通悬赏只统计攻坚值大于 0 且未攻破的攻坚，或强制通行被守住 / 失败等规则指定事件。

## 4.4 攻坚破卡（BREAK_GUARD）

投入范围：

| 资源 | 单次可投入数量 | 不满足时 |
|---|---|---|
| 好果 | 0-2 篓整数 | ACTION_REJECTED / PARAM_OUT_OF_RANGE，不计算攻坚值，不扣资源 |
| 坏果 | 0-2 篓整数 | ACTION_REJECTED / PARAM_OUT_OF_RANGE，不计算攻坚值，不扣资源 |

攻坚值：

攻坚值 = 好果投入 × 2 + 坏果投入 × 3 + 破关令攻坚加成。

| 来源 | 计入方式 |
|---|---:|
| 本次攻坚投入的好果 | 好果投入 × 2 |
| 本次攻坚投入的坏果 | 坏果投入 × 3 |
| 本次攻坚绑定破关令（BREAK_ORDER），且破关令成本可支付 | +3 |
| 本次攻坚未绑定破关令 | +0 |

绑定破关令但成本不足时，整个攻坚动作返回资源不足，不计算攻坚值。

破关令在哪些场景可以使用、使用后分别产生什么效果，归 5.6 终局急策 / 破关令（BREAK_ORDER）定义。

攻坚提交校验：

| 检查项 | 规则 | 不满足时 |
|---|---|---|
| 投入成本 | 当前可用好果、坏果必须足够支付本次声明投入 | 返回资源不足（RESOURCE_NOT_ENOUGH），不扣资源，不改变设卡，不进入休整 |
| 攻坚距离 | 目标节点必须是相邻节点 | 动作拒绝 |
| 攻坚目标 | 目标节点必须存在敌方有效设卡 | 动作拒绝 |

攻坚进入结算后，投入的好果、坏果正式扣除；无论攻坚成功、失败或只扣掉部分防守值，已扣成本都不返还。

结算结果：

| 条件 | 结果 |
|---|---|
| 攻坚值 ≥ 防守值 | 攻坚成功，清除目标设卡；主车队仍停留在原位置 |
| 0 < 攻坚值 < 防守值 | 攻坚失败，目标设卡防守值减少攻坚值，攻方休整 5 个结算帧 |
| 攻坚值 = 0 且防守值 > 0 | 攻坚没有造成效果；目标设卡防守值不变，攻方仍停留在原位置 |

攻坚失败会持续削减目标设卡防守值。休整结束后，只要目标设卡仍有效且位置合法，攻方可以按剩余防守值继续攻坚。

防守值为 0 的设卡不是有效设卡，不能作为攻坚破卡（BREAK_GUARD）的目标，也不触发窗口争夺。

## 4.5 强制通行（FORCED_PASS）

强制通行（FORCED_PASS）用于强行进入相邻节点。只有相邻节点存在敌方有效设卡或道路障碍时，才能提交强制通行。

基础规则：

| 规则点 | 规则 |
|---|---|
| 目标要求 | 目标节点必须是相邻节点，且存在敌方有效设卡或道路障碍 |
| 通行窗口 | 目标有敌方有效设卡时，先进入通行窗口（PASS）；目标只有道路障碍时，不创建通行窗口 |
| 阻挡保留 | 强制通行不清除设卡或道路障碍，只解决本队本次能否进入目标节点 |
| 通行总需求 | 强制通行开始或通行窗口攻方胜出时，按当帧路线耗时和时间税算出本次总需求帧数 |
| 移动结果 | 总需求帧数倒计时结束后，主车队进入目标节点 |

强制通行必须从目标节点的相邻节点发起。强制通行是整体倒计时，不拆成必须分别完成的“时间税段”和“路线段”。

普通任务处理要求主车队位于任务目标节点。若任务目标节点存在敌方有效设卡或道路障碍，主车队必须先处理阻挡，再进入任务目标节点，之后才能提交任务处理。攻坚破卡只清除设卡、不移动车队；强制通行完成后，车队进入目标节点。任务本身不产生时间税。

提交判定顺序：

| 顺序 | 处理 | 结果 |
|---:|---|---|
| 1 | 校验目标节点 | 必须是相邻节点，否则动作拒绝 |
| 2 | 识别目标阻挡 | 必须存在敌方有效设卡或道路障碍，否则动作拒绝 |
| 3 | 记录本次阻挡对象 | 记录提交时目标节点上的敌方有效设卡和 / 或道路障碍 |
| 4 | 计算初始时间税 | 按下方时间税公式计算；同时存在设卡和道路障碍时，取较大值 |
| 5 | 判断是否进入通行窗口 | 有敌方有效设卡则创建通行窗口（PASS）；目标只有道路障碍时，直接开始强制通行 |

通行窗口中，守方因自己的有效设卡被强制通行而被动参战。守方不能出牌或未为该窗口提交有效 `WINDOW_CARD` 时，该拍按弃权（ABSTAIN）处理。攻方胜出后继续强制通行；守方胜出时，本次强制通行失败，攻方留在发起节点并休整 `min(8, max(3, ceil(通行窗口创建时时间税 × 0.25)))` 个结算帧；平局时，本次强制通行失败，攻方留在发起节点并休整 3 个结算帧。

时间税（timeTax）是强制通行在正常路线移动之外增加的等待帧数，按结算帧计算；1 点时间税 = 1 个结算帧。

时间税公式：

| 场景 | 时间税 |
|---|---|
| 通过主动设卡 | min(时间税上限, 基础时间税 + 当前防守值 × 5) |
| 通过道路障碍 | min(时间税上限, 障碍基础时间税) |
| 同时存在主动设卡和道路障碍 | 分别计算主动设卡时间税和道路障碍时间税，取较大值 |

主动设卡时间税参数：

| 主动设卡位置 | 基础时间税 | 时间税上限 |
|---|---:|---:|
| 普通可设卡站点设卡 | 10 个结算帧 | 40 个结算帧 |
| 关键关隘设卡 | 15 个结算帧 | 50 个结算帧 |
| 宫门设卡 | 12 个结算帧 | 32 个结算帧 |
| 已有道路障碍的站点设卡 | 8 个结算帧 | 28 个结算帧 |

道路障碍时间税参数：

| 阻挡类型 | 障碍基础时间税 | 时间税上限 |
|---|---:|---:|
| 道路障碍 | 8 个结算帧 | 28 个结算帧 |

强制通行不是普通移动。强制通行开始时，系统一次算出本次需要多少结算帧；之后只按这个帧数倒计时。倒计时期间，后续天气变化、马类效果结束或新的速度效果生效，都不会改变本次强制通行的剩余帧数。

强制通行期间，不再提交 MOVE。提交 MOVE 或其他主车队动作时，该提交不生效、不扣成本、不计非法动作；系统继续推进强制通行读条。

倒计时结束的这一帧，车队已经到达目标节点。本帧鲜度按空闲状态扣除，即基础鲜度扣除值为 0.05；不再按道路、山路、水路或支路的路线移动鲜度扣除。

阻挡失效后的重算规则：

| 变化 | 处理 |
|---|---|
| 锁定设卡仍有效，只是防守值变化 | 本次时间税不重算 |
| 锁定设卡失效或障碍被清除 | 按剩余仍有效的锁定阻挡重新计算时间税 |
| 已经支付的时间税 | 不返还 |
| 新出现的阻挡对象 | 不能抬高本次时间税 |
| 所有锁定阻挡都失效 | 取消尚未支付的时间税；已经过的结算帧继续抵扣本次强制通行总需求 |

连续强制通行限制：成功强制通行并进入目标节点后，该目标节点成为本队的强制通行限制节点。只要主车队当前停在该节点，就不能发起强制通行；普通移动离开后再回到该节点，仍按强制通行重复（FORCED_PASS_REPEAT）处理。若之后从其他节点完成新的强制通行，限制节点更新为新的强制通行目标。失败留在发起节点时，不触发该限制。

## 4.6 节点风化

每个有效主动设卡按固定节奏风化。每次风化时，设卡防守值减少 1 点：

风化后防守值 = max(0, 当前防守值 - 1)。

风化帧数：

| 主动设卡位置 | 首次风化 | 后续风化间隔 |
|---|---|---|
| 普通可设卡站点设卡 | 设卡完成后 30 个结算帧 | 每 30 个结算帧 |
| 关键关隘设卡，且完成时防守值 ≥ 4 | 设卡完成后 45 个结算帧 | 每 30 个结算帧 |
| 关键关隘设卡，且完成时防守值 < 4 | 设卡完成后 30 个结算帧 | 每 30 个结算帧 |
| 宫门设卡 | 设卡完成后 30 个结算帧 | 每 30 个结算帧 |
| 已有道路障碍的站点设卡 | 设卡完成后 30 个结算帧 | 每 30 个结算帧 |

防守值降至 0 的结算帧，该设卡失效并移除：不再阻挡通行，不累计悬赏创建计数，不能作为小分队增援或削弱的目标，也不能被后续增援重新激活。

若小分队增援或削弱到达的同一结算帧，目标设卡先因风化降至 0，本次小分队动作失败，已消耗人手不返还。

## 4.7 窗口争夺触发

窗口类型：

| 窗口类型 | 含义 | 适用场景 |
|---|---|---|
| 资源窗口（RESOURCE） | 资源争夺 | 双方争抢同一节点资源 |
| 任务窗口（TASK） | 任务处理权争夺 | 双方争抢同一皇榜任务处理权 |
| 宫门窗口（GATE） | 宫门验核争夺 | 双方同时争夺宫门验核处理 |
| 路线处理窗口（DOCK） | 公开处理点争夺 | 双方同时争夺同一公开处理点；固定处理点包括前段交接、登船处理、水路换运、入关交接和宫前交接 |
| 通行窗口（PASS） | 设卡通行争夺 | 强制通行遇到敌方有效设卡；守方因自己的设卡被强制通行而被动参战 |
| 障碍窗口（OBSTACLE） | 道路障碍处理争夺 | 双方同时争夺同一道路障碍处理 |

窗口触发速查：

| 对象 / 场景 | 是否生成窗口 | 处理结果 | 是否扣非法动作分 |
|---|---|---|---|
| 双方同一结算帧争抢同一任务、资源、公开处理点、宫门验核或道路障碍清理 | 是 | 生成对应窗口争夺，不按阵营、玩家编号或动作到达顺序分配权益 | 否 |
| 同一节点、同一资源类型的库存被争抢 | 是 | 可争夺库存固定为 1，不存在“双方各取一份”的分支 | 否 |
| 资源领取中被另一方第 1 次打断 | 是 | 原领取流程中断，资源库存进入窗口保护 | 否 |
| 同一资源第 2 次被打断 | 否 | 返回对象忙，不再创建窗口争夺 | 否 |
| 已开始处理的非资源对象被后续再抢 | 否 | 后提交方返回对象忙；原处理继续推进 | 否 |
| 已验核队伍再次提交宫门验核 | 否 | 返回已验核拒绝（ALREADY_VERIFIED），不创建宫门窗口，不锁宫门对象 | 否 |
| 同一空节点同帧设卡（SET_GUARD） | 否 | 不生成窗口；服务端按独占冲突公平账本选出一方进入 SET_GUARD 读条，其余方返回对象忙，不按提交顺序选边 | 否 |
| 同一道路障碍上 T04 与 CLEAR 同帧提交 | 是 | 按同一障碍争夺处理；窗口胜方继续自己的原动作 | 否 |
| 强制通行遇敌方有效设卡 | 是 | 创建通行窗口（PASS），守方为设卡归属方；守方因自己的设卡被强制通行而被动参战 | 否 |
| 强制通行目标只有道路障碍 | 否 | 不创建 PASS 窗口；按本队本次强制通行处理，不清除障碍 | 否 |
| 破关悬赏 | 否 | 不作为直接争抢对象；只随攻坚破卡结算是否完成悬赏 | 否 |

窗口争夺固定为 3 拍，每拍 1 个结算帧，总时长 3 个结算帧。

窗口拍数起算：

| 时点 | 处理 |
|---|---|
| 第 T 帧 | 窗口创建，并下发窗口开始事件（WINDOW_CONTEST_START） |
| 第 T+1 帧 | 第 1 拍出牌 |
| 第 T+2 帧 | 第 2 拍出牌 |
| 第 T+3 帧 | 第 3 拍出牌，并在亮牌结算后产生窗口结果 |

窗口结算与保护：

| 场景 | 处理 |
|---|---|
| 任务进入窗口 | 暂停过期判定；窗口结束后按胜负结果处理 |
| 资源进入窗口 | 本次争夺库存锁定；窗口结束前不归属任何一方 |
| 窗口产生胜方 | 胜方不需要重新提交原动作；窗口结束当帧只记录胜方，下一结算帧自动开始或继续对应处理 |
| 资源领取打断窗口产生胜方 | 胜方从头开始领取资源 |
| 任务窗口产生胜方 | 胜方只获得任务处理权；任务处理完成后才获得任务分 |
| 其他队伍再抢同一对象 | 返回对象忙（OBJECT_BUSY）；任务保护期间返回任务保护中（TASK_PROTECTED） |
| 窗口结束时已到达任务原截至帧，且任务窗口产生胜方 | 胜方获得一次胜方保护（CLAIM_PROTECTED）处理机会 |
| 保护处理成功 | 胜方获得任务分 |
| 保护处理失败、中断、目标丢失、胜方离开合法站位或退赛 | 任务进入保护期中断后过期（EXPIRED_AFTER_PROTECTION_INTERRUPT） |

胜方续接处理时，普通任务、资源、公开处理点和宫门要求主车队位于目标节点；T04 清障任务和主车队清障要求主车队位于目标障碍节点或相邻节点。续接处理期间离开合法站位时，处理失败；若是任务保护处理，任务进入保护期中断后过期。

普通窗口平局与冷却（不含 PASS / GATE）：

| 场景 | 处理 |
|---|---|
| 普通窗口平局 | 双方均不获得保护机会 |
| 任务窗口平局 | 先结算本次平局次数 |
| 平局时任务已到达原截至帧 | 任务过期，不进入平局冷却 |
| 平局时任务未到达原截至帧 | 可以因重复平局达到上限进入平局冷却 |
| 任务进入平局冷却 | 冷却期间暂停过期判定；冷却结束后按冷却开始时记录的剩余帧数恢复 |
| 资源窗口平局 | 本次争夺结束，资源库存继续留在对应节点 |

若在结算帧 R 触发平局冷却，冷却从下一结算帧开始，持续 `drawRepeatSuppressRound` 个结算帧；冷却结束后的下一个结算帧，该对象恢复为新的连续争夺周期。

通行窗口（PASS）是强制通行遇到敌方有效设卡时生成的特殊争夺。攻方为提交强制通行的队伍；守方为目标设卡归属方。守方的参战原因是自己的有效设卡被强制通行，这是被动参战，不要求守方本帧也提交动作或停在目标节点。目标只有道路障碍时，没有守方，不创建通行窗口。

守方被动进入通行窗口时，守方本帧已提交动作照常结算，下一次实时查询（inquire）同时返回动作结果和窗口信息；窗口信息由事件列表（events）中的 WINDOW_CONTEST_START 和窗口列表（contests）中的 `contestId`、`contestType`、`targetNodeId`、`roundIndex`、`totalRounds`、`deadlineRound`、`redPlayerId`、`bluePlayerId` 确认。允许出牌的一方按 `contestId` 提交 `WINDOW_CARD`，未为该 `contestId` 提交有效窗口牌时按弃权（ABSTAIN）处理。

通行窗口按创建时的有效设卡快照保留参战关系；窗口三拍期间即使设卡后续失效，已创建的通行窗口也不取消。

通行窗口守方出牌规则：

| 守方情况 | 本拍处理 |
|---|---|
| 空闲、等待中、移动中、窗口争夺中 | 可以提交窗口出牌（WINDOW_CARD） |
| 处理中、宫门验核中、强制通行中、休整中、已交付、已退赛 | 固定按弃权（ABSTAIN）处理；即使提交本窗口出牌，也不生效、不扣成本、不计非法动作，不增加失联计数 |
| 允许出牌但未为该 contestId 提交有效 WINDOW_CARD，或提交 actions: [] | 按弃权（ABSTAIN）处理；actions: [] 计为有效心跳，不增加失联计数 |
| 同一出牌拍参与多个窗口 | 本队最多提交 1 张 WINDOW_CARD。只提交 1 张时，该牌绑定的 contestId 生效，其他本队参与的窗口按弃权（ABSTAIN）处理；提交 2 张及以上时，全部窗口牌不生效，本队在相关窗口均按弃权处理，并记录窗口出牌类别冲突 |

通行窗口结果：

| 结果 | 处理 |
|---|---|
| 攻方胜利 | 强制通行原动作继续推进；继续前按锁定阻挡对象当前有效性重算时间税，并按当帧状态确定本次通行路线耗时 |
| 守方胜利 | 攻方强制通行失败，留在发起节点并休整 `min(8, max(3, ceil(通行窗口创建时时间税 × 0.25)))` 个结算帧 |
| 平局 | 攻方本次强制通行注销，留在发起节点并休整 3 个结算帧；守方保持原状态，不暂停原移动、处理、强制通行、休整或原窗口；本次平局计入该通行对象的重复平局抑制 |
| 攻方胜利后全部锁定阻挡失效 | 取消尚未支付的时间税；已经过的结算帧继续抵扣本次强制通行总需求 |

## 4.8 窗口出牌

参赛程序只提交窗口牌，不指定成本来源；系统按下表规则自动扣除即时成本。

窗口牌出牌成本：

| 窗口牌 | 即时成本 |
|---|---|
| 验牒（YAN_DIE） | 消耗 1 个可用文书资源；过所（PASS_TOKEN）和官凭（OFFICIAL_PERMIT）都可支付验牒成本，二者没有消耗优先级差异 |
| 强行（QIANG_XING） | 若本队已有马类移动增益或疾行令（RUSH_SPEED）正在生效，本拍强行免消耗；否则依次消耗 1 个快马（FAST_HORSE）、1 个短程马（SHORT_HORSE） |
| 献贡（XIAN_GONG） | 鲜度 ≥ 80 且消耗 1 篓好果 |
| 兵争（BING_ZHENG） | 消耗 1 点护卫行动点（guardActionPoint） |
| 弃权（ABSTAIN） | 不消耗资源 |

弃权（ABSTAIN）不克制任何牌；参赛程序可以显式提交弃权，本拍未提交 WINDOW_CARD 或提交 actions: [] 也按弃权处理；一方出有效牌、另一方弃权时，有效牌方获得本拍胜点，双方都弃权时本拍为平点。

窗口出牌成本结算：

| 结算步骤 | 规则 |
|---|---|
| 出牌提交时 | 只记录本拍提交的 WINDOW_CARD，不预扣、不锁定成本 |
| 亮牌结算时 | 服务端校验并即时扣除该牌成本 |
| 成本不足时 | 该牌失效，本拍按弃权（ABSTAIN）处理 |
| 成本已扣除后 | 已扣成本不返还；已扣好果不参与本结算帧末尾好果转坏果清算 |
| 成本统计 | 弃权和强行免消耗时成本记为 0；只有实际扣除资源、好果或护卫行动点的窗口牌计入有效窗口成本统计 |

## 4.10 重复平局兜底

窗口争夺 3 拍结束后，双方拍胜点相同，本次窗口结果记为平局（DRAW）。平局没有胜方，不分配资源、任务、宫门、路线处理点、障碍处理权或通行结果。

平局固定处理：

| 窗口类型 | 队伍状态 | 对象结果 | 平局计数与冷却 |
|---|---|---|---|
| 普通窗口（RESOURCE / TASK / DOCK / OBSTACLE） | 双方主车队进入休整 3 个结算帧 | 本次争夺动作作废；已锁定但尚未正式扣除的成本按规则释放；资源不发放，任务不完成，路线处理点 / 障碍处理不结算 | 计入重复平局；达到 `maxDrawRepeatsPerObject = 2` 后，对象进入 `drawRepeatSuppressRound = 18` 个结算帧平局冷却 |
| 通行窗口（PASS） | 攻方强制通行失败并休整 3 个结算帧；守方不休整，也不暂停原动作 | 本次强制通行失败 | 计入重复平局；达到 `maxDrawRepeatsPerObject = 2` 后，通行对象进入 `drawRepeatSuppressRound = 18` 个结算帧平局冷却 |
| 宫门窗口（GATE） | 双方主车队进入休整 3 个结算帧 | 本次宫门验核动作注销 | 计入重复平局；达到 `maxDrawRepeatsPerObject = 2` 后，宫门对象进入 `gateDrawRepeatSuppressRound = 6` 个结算帧短冷却 |

平局导致的休整不算非法动作，不扣分。

重复平局按“连续争夺周期”统计。一个连续争夺周期从该对象首次进入窗口争夺开始，到窗口产生胜方、对象被处理、对象过期，或平局冷却结束后重置。

平局冷却：

| 窗口对象 | 冷却长度 | 冷却期间 |
|---|---:|---|
| 任务（TASK） | `drawRepeatSuppressRound = 18` 个结算帧 | 不能处理或争夺；任务过期判定暂停，不占“可直接处理普通任务上限 10”名额 |
| 资源（RESOURCE） | `drawRepeatSuppressRound = 18` 个结算帧 | 不能领取或争夺该资源 |
| 路线处理点（DOCK） | `drawRepeatSuppressRound = 18` 个结算帧 | 不能处理该路线处理点 |
| 障碍（OBSTACLE） | `drawRepeatSuppressRound = 18` 个结算帧 | 不能清障或处理对应 T04；普通移动仍被挡；仍可绕路或强制通行，强制通行不清除障碍，也不产生清障残留 |
| 通行（PASS） | `drawRepeatSuppressRound = 18` 个结算帧 | 不能继续争夺该通行对象；队伍可以改做其他合法动作 |
| 宫门（GATE） | `gateDrawRepeatSuppressRound = 6` 个结算帧 | 不能提交宫门验核（VERIFY_GATE） |

对象进入平局冷却后，冷却只冻结该对象，不冻结队伍。冷却期内提交该对象动作，返回 ACTION_REJECTED / WINDOW_DRAW_RETRY_LIMIT，不创建窗口、不锁定对象，不计非法动作，不扣分，不消耗资源，不启动处理。对象本身不消失，不改归属；服务端不按玩家编号、阵营或行动顺序判给任何一方。

普通任务冷却结束后，按冷却开始时记录的剩余帧数恢复；若恢复后普通任务暂时超过 10 个，服务端不删除旧任务，后续刷新等数量低于 10 后再生成新任务。

冷却结束后，该对象连续争夺周期清零；之后单方提交按普通单方动作处理，双方同帧争夺则重新创建窗口，上一周期的平局次数不再沿用。

平局冷却如何公开：

| 选手看到什么 | 含义 |
|---|---|
| 对象仍在地图或任务列表里 | 对象没有消失，只是暂时不能处理 |
| 窗口列表中该对象显示平局冷却（SUPPRESSED） | 该对象正在平局冷却；若任务仍显示 ACTIVE，也必须以 SUPPRESSED 判断为不可处理 |
| 本帧事件出现窗口平局 | 本帧刚判出一次窗口平局 |
| 本帧事件出现重复平局抑制 | 本帧该对象进入或仍处于平局冷却 |
| 冷却期内提交该对象动作 | 收到 ACTION_REJECTED / WINDOW_DRAW_RETRY_LIMIT，不计非法动作 |
| 冷却结束 | 冷却记录移除，服务端按新的争夺周期重新判断 |

事件列表（events）只说明本帧发生了什么；持续中的冷却要看窗口列表（contests）。

# 5. 皇榜任务与宫宴冲刺

## 5.1 皇榜任务

皇榜任务默认只从 9 种普通任务模板刷新：T01、T02、T04、T06、T08、T11、T12、T13、T14。

T01、T02 等是任务模板编号（taskTemplateId）。每次刷新会生成全局唯一的任务实例编号（taskId）；同一模板可以在不同刷新批次重复出现，但同一个任务实例完成后，另一队不能再完成同一个实例。

固定项包括任务模板、统一完成动作、提交位置、完成结果和模板分值。普通任务统一由主车队提交处理皇榜任务（CLAIM_TASK(taskId)）完成。

动态项包括目标候选点和路线任务桶。目标候选点以本局 `gameplay.taskCandidates` 为准；路线任务桶以本局 `gameplay.routeTaskBuckets` 为准。两者都随地图配置动态变化。

下表只列 `map_config.json` 调测地图的目标候选点示例；其他地图以本局 `gameplay.taskCandidates` 为准：

| T02 | 抵驿催运 | 任务目标节点 | 获得任务分 | 30 | S07,S10 |

下表只列 `map_config.json` 调测地图示例的路线桶节点：

| 水路（WATER） | S04,S05,S09,S10,S12,S13 | 水路保留速度和保鲜优势，同时承担码头与天气风险 |

一局比赛不会一次性刷出全部普通任务。任务供给分为计划刷新和动态补位刷新两类：

| 类型 | 触发时机 | 默认数量 | 说明 |
|---|---|---|---|
| 计划刷新 | 第 1 / 100 / 200 / 300 / 360 / 400 帧 | 每次最多 3 个，默认面向官道、水路、山路各 1 个 | 用于保证三条主路线都有稳定任务入口；计划刷新总机会默认 18 个 |
| 动态补位刷新 | 非计划刷新帧，每 30 帧检查一次 | 每次最多 1 个，全局最多 6 个 | 当可直接处理任务不足、路线桶存在供给欠账，或有队伍任务分低于追赶档位时补位；宫宴冲刺前 60 帧停止补位 |

任务容量分为两层：

| 容量口径 | 默认值 | 统计方式 |
|---|---:|---|
| 当前任务池容量 | 18 | 只统计仍活跃且未完成、未失败的普通任务；已完成、失败、过期且非活跃的历史任务不再占用容量 |
| 可直接处理任务上限 | 10 | 只统计当前可被单方直接处理的普通任务；窗口争夺中、胜方保护中、平局休整冻结中、重复平局冷却中、已完成、已失败或已过期的任务暂时不计入 |

动态补位不会改变任务计分公式，也不会刷新额外宫宴冲刺任务。补位任务仍然必须通过任务目标公平校验，并优先填补任务供给不足的路线桶。没有路线欠账时，服务端按各路线桶当前可直接处理任务数量选择补位路线；保护、窗口、平局冻结或冷却中的旧任务不视为健康供给。

宫宴冲刺不刷新额外得分任务。

T06 需要快马或短马资源。若当前没有任何队伍持有可用快马或短马，服务端不会把 T06 视为绝对不可刷新，但会降低其刷新优先级，并优先选择无资源前置、可立即参与的替代任务。

任务供给均衡目标：

| 目标 | 说明 |
|---|---|
| 基础参与 | 完成 2 个普通任务通常获得 60 原始任务分，明显优于纯直冲 |
| 正常任务流 | 稳定路线完成 3 个普通任务通常约 75 原始任务分，送达基础分和用时分仍有折减 |
| 高任务流 | 完成 3 个高价值任务加 1 个轻量任务，或通过转线 / 清障 / 资源检查 / 窗口争夺补足任务链，通常可达到 90+ 原始任务分 |
| 供给节奏 | 第 1 / 100 / 200 / 300 / 360 / 400 帧各尝试刷新 3 个普通任务，默认面向官道、水路、山路各提供 1 个任务；非计划刷新帧可按动态补位规则少量补刷 |
| 路线覆盖 | 每个待刷任务会分配到一条路线；目标点必须同时属于该任务模板的目标候选点和该路线的路线桶节点，避免单一路线天然垄断任务收益 |
| 主线 90 分链路 | 三条主路线都应具备冲 90+ 原始任务分的高阶路线选择；官道不能平白拿高收益，水路和山路也必须有稳定任务桶与资源补偿；高收益仍需要支付任务处理帧数、资源检查、路线转换、清障或窗口争夺成本 |

普通任务完成规则：

| 规则点 | 规则结果 |
|---|---|
| 完成主体 | 皇榜任务必须由主车队到达合法提交位置，并完成处理皇榜任务（CLAIM_TASK(taskId)）后获得分数 |
| 小分队 | 小分队战术不直接获得皇榜任务分 |
| T04 特例 | 小分队清障可以破坏或清除 T04 清障任务目标，但不能领取 T04 的 30 分奖励 |
| 单方提交 | 只有一方提交可处理状态（ACTIVE）的普通任务时，按普通单方处理 |
| 同帧争抢 | 双方同一结算帧争抢同一普通任务时，进入任务窗口（TASK） |

T06、T08 的任务分只由处理皇榜任务（CLAIM_TASK(taskId)）触发；领取资源（CLAIM_RESOURCE）、通用处理（PROCESS）或码头登船（DOCK / dock，旧版小写兼容）本身不发任务分。

任务刷新帧只需要关注以下结果：

| 场景 | 规则结果 |
|---|---|
| 本帧新生成普通任务 | 最早下一结算帧才能提交处理 |
| 普通任务到达截至帧（expireRound） | 还没结算成功就过期（EXPIRED），不发任务分；任务有效期见 5.2 |
| 普通任务进入窗口争夺 | 任务有效期暂停；窗口胜方继续处理该任务，败方不能再抢这次任务；平局按下表处理 |
| 普通任务进入窗口平局 | 双方 RESTING 的 3 个结算帧内任务有效期暂停；若达到重复平局上限进入平局冷却，冷却期间继续冻结该任务剩余有效期 |

任务窗口平局处理规则：

| 平局情况 | 规则结果 |
|---|---|
| 未达到平局上限 | 本次争抢作废；双方 RESTING 3 个结算帧，RESTING 期间任务有效期暂停；任务仍有效时，休整后可以再次争夺 |
| 达到平局上限 | 任务进入重复平局冷却；本次 DRAW 触发的双方 RESTING 3 个结算帧和后续平局冷却期间，任务剩余有效期都暂停；冷却期间双方不能处理或争夺该任务 |
| 平局时任务已到截至帧 | 任务过期，不进入平局冷却 |

T04 清障任务目标丢失规则：

| 触发场景 | 结果 | 是否给分 | 是否补刷 |
|---|---|---|---|
| T04 处于可处理状态（ACTIVE）时，目标障碍被普通清障、小分队清障、系统事件或其他非 T04 任务方式清除 | 任务进入目标丢失失败（FAILED_TARGET_LOST） | 不给任何队伍加分 | 不重新刷新 |

最终结算统一使用最终任务基础分计算送达系数和用时分中的任务系数。当前配置下，最终任务基础分达到 90 后，送达基础分和用时分不再因任务参与被折减。具体计算见 6.2 分项得分。

## 5.2 任务目标公平校验

刷新普通任务目标时，服务端先做硬校验，再做软评分。硬校验用于排除明显不可用目标；软评分用于在多个可用候选中选择更公平、更有路线价值的目标。

| 规则点 | 刷新要求 |
|---|---|
| 不能刷在脚下 | 硬校验。目标站点不能等于任一队伍当前站点 |
| 不能太近 | 硬校验。任一队伍到目标站点的最短理论到达帧数必须 ≥ 10 个结算帧 |
| 截至前可完成 | 硬校验。双方都能在任务到期前到达并完成处理 |
| 同批目标不重复 | 硬校验。同一刷新批次内，两个任务不能使用同一目标站点 |
| 双方距离差 | 软评分。双方到目标站点的最短理论到达帧数差超过 30 个结算帧时不直接拒绝，但会降低该候选优先级；存在更公平候选时优先选择更公平候选 |
| 无合法候选 | 候选站点没有一个通过硬校验时，该任务本轮不刷新 |

T04 清障任务沿用同一套硬校验与软评分。T04 可以在目标障碍节点或相邻节点提交处理皇榜任务（CLAIM_TASK），所以刷新 T04 时，先把这些可提交位置合成合法处理站位集合：目标障碍节点 + 与目标障碍节点存在公开路线边的相邻节点。

T04 目标校验顺序如下：

```mermaid
flowchart TD
  A["候选障碍节点"] --> B["生成 T04 合法处理站位集合"]
  B --> C{"任一队伍是否已在集合内"}
  C -- "是" --> R["本轮不刷新该 T04"]
  C -- "否" --> D["计算双方到集合中最近站位的最短理论到达帧数"]
  D --> E{"任一队伍是否小于 10 个结算帧"}
  E -- "是" --> R
  E -- "否" --> F["计算双方到达帧数差软评分"]
  F --> G{"双方是否都能在任务到期前完成处理"}
  G -- "否" --> R
  G -- "是" --> H["进入候选评分并择优刷新"]
```

例如开局双方位于 S01 时，若 S06 是障碍节点且 S01 与 S06 相邻，T04@S06 不能刷新成开局即可直接处理的任务。

刷新任务时，公平校验使用最短理论到达帧数。该帧数由服务端计算；设计文档不定义具体路径算法，参赛选手无需关注这项规则。算出的帧数用于目标硬校验和候选软评分。

| 队伍位置 | 计算口径 |
|---|---|
| 停靠在节点 | 按当前停靠节点到目标站点的最短理论到达帧数计算 |
| 正在路线边上 | 按车队在当前路线边上的真实位置计算 |
| T04 清障任务 | T04 可以站在障碍所在节点处理，也可以站在旁边相连的节点处理。判断距离时，哪个可处理位置离队伍更近，就按哪个算 |

普通任务可处理时长：

| 任务出现批次 | 可处理时长 |
|---|---:|
| 第 1 / 100 / 200 / 300 帧出现的普通任务 | 220 个结算帧 |
| 第 360 帧出现的普通任务 | 180 个结算帧 |
| 第 400 帧出现的普通任务 | 200 个结算帧 |

普通任务到期前没有结算成功，就过期（EXPIRED），不发任务分。

窗口争夺和重复平局的通用机制见 4.7、4.10；普通任务到期、窗口争夺和平局冷却后的任务结果见 5.1。

## 5.4 破关悬赏

破关悬赏分为普通悬赏和关键关隘悬赏。悬赏类型、分值和生成条件是固定规则；普通可设卡节点和关键关隘节点以本局地图配置为准。

| 悬赏类型 | 适用节点 | 分值 |
|---|---|---:|
| 普通悬赏（NORMAL_BOUNTY） | 普通可设卡节点 | 10 |
| 关键关隘悬赏（KEY_BOUNTY） | 关键关隘节点 | 18 |

调测地图示例中，关键关隘节点为 S10 武关。

有效设卡指防守值 > 0 的设卡。防守值降到 0 后，该设卡不再阻挡通行，也不再累计悬赏生成条件；正在累计的条件立即清零。

下表中的 30 个结算帧、60 个结算帧、2 次、3 次都是固定规则，不由设卡方选择。任一条件满足时，该节点生成破关悬赏；多个条件同时满足时，同一节点也只生成 1 个悬赏。悬赏被领取（CLAIMED）或失效（EXPIRED）后，该节点进入 120 个结算帧冷却；冷却期间不生成新悬赏。冷却结束后，只有再次满足悬赏生成条件，才会生成新的悬赏。

| 触发情况 | 生成结果 |
|---|---|
| 某支队伍在该节点设卡后，连续 30 个结算帧没有被清除，且第 30 个结算帧结束时防守值仍 > 0 | 生成破关悬赏 |
| 某支队伍在该节点设卡后，连续 60 个结算帧没有被清除，且这 60 个结算帧内防守值始终 > 0 | 生成破关悬赏 |
| 某支队伍在该节点设卡后，敌方累计 2 次有效进攻失败 | 生成破关悬赏 |
| 某支队伍在关键关隘设卡后，敌方对该关隘累计完成 3 次合法攻坚破卡结算，或累计 3 次因强制通行触发通行窗口 | 生成关键关隘悬赏 |

有效进攻失败计数：

| 情况 | 计数结果 |
|---|---|
| 敌方对可设卡节点上的有效设卡发起攻坚破卡，攻坚值大于 0 且未攻破 | +1 |
| 敌方对可设卡节点上的有效设卡发起强制通行，守方胜出或平局导致敌方未通过 | +1 |
| 敌方成功攻破可设卡节点上的设卡 | 不计 |
| 敌方攻坚值为 0，设卡防守值不变 | 不计 |
| 敌方成功强制通行通过可设卡节点上的设卡 | 不计 |
| 普通移动（MOVE）被设卡挡住 | 不计 |

关键关隘攻防计数（keyPassCombatCount）：

| 情况 | 计数结果 |
|---|---|
| 对关键关隘有效设卡完成一次合法攻坚破卡结算 | +1，攻坚成功、攻坚失败、攻坚值为 0 都计 |
| 对关键关隘有效设卡发起合法强制通行，并创建通行窗口 | +1，窗口胜负不影响计数 |
| 非法动作、平局冷却拒绝、目标防守值为 0、目标不是关键关隘有效设卡 | 不计 |

这里的合法攻坚破卡结算，是指攻坚破卡（BREAK_GUARD）通过位置、目标、参数和资源校验；即使攻坚值为 0，也计入关键关隘攻防次数。

悬赏完成与得分：

设卡方只获得阻挡和拖慢收益，不直接获得悬赏分。敌方通过攻坚破卡（BREAK_GUARD）清零悬赏节点的有效设卡后，按下图判断是否发放悬赏分：

```mermaid
flowchart TD
  A["节点存在活跃破关悬赏<br/>或本次攻坚先触发并创建悬赏"] --> B["敌方提交 BREAK_GUARD"]
  B --> C{"攻坚前防守值 > 0<br/>且本次攻坚值足以清零？"}
  C -- "否" --> D["破卡失败<br/>设卡继续阻挡<br/>不发悬赏分"]
  C -- "是" --> E["设卡被清除<br/>攻破方仍停原位置"]
  E --> F{"本次 BREAK_GUARD 所在结算帧开始时<br/>攻破方公开总分 < 设卡方公开总分？"}
  F -- "是" --> G["攻破方获得悬赏分"]
  F -- "否" --> H["攻破方只清除设卡<br/>不获得悬赏分"]
```

关键关隘第 3 次合法攻坚可以同时触发悬赏和结算悬赏。若本次攻坚累计到第 3 次，并且本次攻坚又打破该设卡，系统会先生成关键关隘悬赏，再立即结算该悬赏。是否加悬赏分，按本帧开始时攻破方是否落后判断。

示例：蓝方在 S10 设卡，红方已经对该设卡完成过 2 次合法攻坚。本帧红方第 3 次提交 `BREAK_GUARD`，且本次攻坚值足以把设卡防守值打到 0。系统先记录这是第 3 次关键关隘攻坚，生成 S10 关键关隘悬赏；随后本次攻坚破卡成功，该悬赏立即结算。如果本帧开始时红方公开总分低于蓝方，红方获得悬赏分；否则只破卡，不获得悬赏分。

悬赏得分使用本次攻坚破卡（BREAK_GUARD）所在结算帧开始时锁定的分数预览（scorePreview[teamId]）判断攻破方是否落后，不使用破卡结算后或下一结算帧开始时的分数。该分数只用于本次悬赏发分判断，不是最终分。攻坚破卡成功只清除设卡，主车队仍停原位置；若要进入该节点，后续还要按移动规则提交移动。破关悬赏只发悬赏分，不发放随机资源。

悬赏结算事件口径如下：

- `BOUNTY_CLAIM` 表示活跃悬赏被成功结算并进入冷却，不等同于一定加分；事件 payload 中的 `scoreGranted = true` 表示本次满足落后发分条件并实际增加悬赏分，`scoreGranted = false` 表示悬赏被结算但不加分。
- 若悬赏对应设卡在被成功攻破前已经不存在，或防守值已经为 0，该悬赏立即失效并进入冷却；服务端记录 `BOUNTY_EXPIRE`，不发分，不转移给其他节点，也不生成替代奖励。

## 5.5 宫门验核

宫门验核是 S14 朱雀门的终局验核动作，对应宫门验核（VERIFY_GATE）。

提交宫门验核必须同时满足：

| 提交要求 | 规则结果 |
|---|---|
| 比赛阶段 | 只能在宫宴冲刺阶段提交；普通阶段提交会被拒绝，不进入处理，不创建宫门窗口，不消耗破关令或探路标记 |
| 队伍位置 | 主车队位于 S14 |
| 验核状态 | 队伍尚未完成验核 |
| 队伍状态 | 不在移动、窗口争夺、休整、强制通行、通用处理或宫门验核中 |

双方同一结算帧提交宫门验核时，进入宫门窗口（GATE）。宫门窗口按 4.7 的窗口争夺规则结算，固定 3 拍；平局和短冷却规则见 4.10。

调测地图示例的宫门验核（VERIFY）处理帧数为 6 个结算帧；本局实际验核处理帧数以 `gameplay.processNodes` 中的 VERIFY 配置为准。探路标记和破关令仍按本节减时规则生效。

宫门验核处理方式：

| 处理方式 | 规则结果 |
|---|---|
| 直接提交宫门验核（VERIFY_GATE） | 按基础处理帧数完成 |
| 提交宫门验核，且 S14 有本队可用探路标记 | 处理帧数 -3 个结算帧，最低 2 个结算帧 |
| 提交宫门验核，并绑定破关令（BREAK_ORDER） | 处理帧数 -3 个结算帧，最低 3 个结算帧 |
| 提交宫门验核，同时满足探路标记和破关令 | 两项减时同时生效，但最终处理帧数最低 3 个结算帧 |

因此，无减时为 6 个结算帧；只有探路标记为 3 个结算帧；只有破关令为 3 个结算帧；同时满足探路标记和破关令时仍为 3 个结算帧。

宫门验核完成后，已验核状态从下一结算帧生效；已验核生效后，才允许从 S14 前往 S15，并在 S15 提交交付。宫门验核不发任务分。

已验核队伍重复提交宫门验核（VERIFY_GATE）时，返回动作拒绝 / 已验核（ACTION_REJECTED / ALREADY_VERIFIED），并记录已完成验核事件（VERIFY_GATE_ALREADY_DONE）；该动作不创建宫门窗口（GATE）、不锁定宫门对象、不进入处理、不消耗破关令（BREAK_ORDER）或探路标记，也不计非法动作。

若宫门验核在第 600 结算帧完成，由于已验核需要下一结算帧才生效，而比赛在第 600 结算帧完成后结束，该队伍已无后续交付机会，最终按未交付结算。

## 5.6 终局急策

终局急策不是地图资源，不需要领取，也不会在资源点刷新。进入宫宴冲刺后，每队获得 1 次终局急策使用资格，可用于疾行令（RUSH_SPEED）、护果令（RUSH_PROTECT）或破关令（BREAK_ORDER）其中一种。

未进入宫宴冲刺时，不能提交终局急策。

疾行令和护果令按主车队动作提交，占用本帧主车队动作名额。同一结算帧同时提交疾行令 / 护果令和 MOVE、USE_RESOURCE、CLAIM_TASK 等其他主车队动作，会按主动作冲突处理。疾行令在移动中单独提交并成功时，本帧继续沿当前路线方向推进；护果令只能在主车队停靠状态提交。

终局急策次数状态：

| 状态 | 规则结果 |
|---|---|
| 未使用 | 可以在疾行令、护果令、破关令中选择 1 种使用；破关令只能绑定攻坚破卡（BREAK_GUARD）或宫门验核（VERIFY_GATE） |
| 锁定中 | 破关令绑定动作进入窗口争夺时，急策次数和破关令成本先锁定；锁定期间不能再提交其他终局急策 |
| 锁定解除 | 绑定动作窗口败北、平局、保护处理未开始、目标失效或正式开始前被拒绝时，返还急策次数和成本，可重新使用终局急策 |
| 已正式使用 | 疾行令 / 护果令生效，或破关令绑定动作正式开始后，本队不能再使用任何终局急策 |
| 重复提交 | 已正式使用后再次提交疾行令或护果令，返回非法动作类型（INVALID_ACTION_TYPE）；再次绑定破关令，返回急策绑定非法（RUSH_TACTIC_INVALID_BINDING） |

### 疾行令（RUSH_SPEED）

| 项目 | 规则结果 |
|---|---|
| 成本 | 2 篓好果 |
| 持续帧数 | 15 个结算帧 |
| 效果 | 基础推进量提升 30% |
| 代价 | 疾行令生效期间，鲜度损耗 ×1.25 |
| 与马类增益互斥 | 已有快马或短程马增益时提交疾行令，使用失败，不消耗终局急策次数和好果 |
| 疾行令生效中使用马类资源 | 使用快马或短程马失败，不消耗对应马类资源 |

### 护果令（RUSH_PROTECT）

| 项目 | 规则结果 |
|---|---|
| 使用状态 | 只能在主车队停靠在节点、且未处于其他读条或窗口状态时提交；正在路线边移动时不能提交 |
| 成本 | 不消耗果品，只消耗本队 1 次终局急策次数 |
| 持续帧数 | 30 个结算帧 |
| 效果 | 护果令生效期间，鲜度损耗 ×0.2 |

### 破关令（BREAK_ORDER）

破关令不能单独提交，只能绑定在攻坚破卡（BREAK_GUARD）或宫门验核（VERIFY_GATE）上使用。

| 规则点 | 规则结果 |
|---|---|
| 可绑定动作 | 攻坚破卡（BREAK_GUARD）、宫门验核（VERIFY_GATE） |
| 单独提交 | 单独提交破关令，返回非法动作类型（INVALID_ACTION_TYPE） |
| 绑定非法 | 窗口出牌（WINDOW_CARD）携带破关令；或在攻坚破卡 / 宫门验核上绑定破关令时，比赛尚未进入宫宴冲刺，或本队终局急策次数已用尽 |
| 绑定非法结果 | 返回急策绑定非法（RUSH_TACTIC_INVALID_BINDING），不消耗终局急策次数，不消耗果品成本 |
| 成本支付 | 坏果至少 2 篓时，必须消耗 2 篓坏果；坏果不足 2 篓且好果至少 1 篓时，消耗 1 篓好果 |
| 成本不足 | 返回资源不足（RESOURCE_NOT_ENOUGH） |
| 成本选择限制 | 坏果足够时，不能改用好果支付 |

破关令绑定后的效果：

| 绑定动作 | 规则结果 |
|---|---|
| 攻坚破卡（BREAK_GUARD） | 本次攻坚值 +3 |
| 宫门验核（VERIFY_GATE） | 本次验核处理帧数 -3 个结算帧，最低处理帧数为 3 个结算帧 |

破关令（BREAK_ORDER）成本扣除规则：

| 情况 | 规则结果 |
|---|---|
| 绑定校验失败或成本不足 | 动作不生效，不消耗急策次数和果品成本 |
| 不触发窗口，绑定动作可直接开始 | 进入攻坚结算或宫门验核处理时，扣除 1 次终局急策次数和对应果品成本 |
| 绑定动作进入窗口争夺 | 先锁定 1 次终局急策次数和对应果品成本；锁定期间不能再提交其他终局急策，被锁定果品不能用于其他动作 |
| 窗口败北、平局、保护处理未开始、目标失效，或绑定动作正式开始前被拒绝 | 解除锁定，不消耗急策次数和果品成本 |
| 窗口胜出 | 胜方开始绑定动作的保护处理、攻坚结算或宫门验核处理时，正式扣除已锁定的急策次数和果品成本 |
| 绑定动作已经正式开始 | 之后处理失败、中断或冻结好果被清算，已消耗的急策次数和果品成本不返还 |

若破关令成本用坏果支付，锁定时从可用坏果中暂扣；若用好果支付，锁定时计入冻结好果。冻结好果被鲜度清算扣掉时，按 3.5 和 4.2 的冻结好果被清算（COST_BANKRUPT）处理。

攻坚破卡绑定破关令时，本次攻坚声明投入优先占用好果 / 坏果；破关令只能使用剩余果品支付，且仍按坏果优先、好果兜底判断。任一成本不足，整个动作返回资源不足（RESOURCE_NOT_ENOUGH），不结算攻坚，不进入休整，不消耗终局急策次数或果品。

宫门验核绑定破关令时，只检查破关令自身成本；若进入宫门窗口（GATE），按上表的窗口锁定和扣除规则处理。

# 6. 结算规则

## 6.1 交付（DELIVER）条件

提交交付（DELIVER）时，必须同时满足以下条件：

| 条件 | 不满足时反馈 |
|---|---|
| 当前位置（currentNodeId）必须为 S15 兴庆宫 | 未到终点（DELIVER_NOT_AT_TERMINAL） |
| 已验核状态（verified）必须为 true | 未验核（DELIVER_NOT_VERIFIED） |
| 已交付状态（delivered）必须为 false | 动作拒绝 / 已交付（ACTION_REJECTED / ALREADY_DELIVERED）；不触发交付后违规惩罚 |
| 好果数量（goodFruit）必须大于 0 | 交付条件不满足（DELIVER_REQUIREMENT_NOT_MET） |
| 鲜度（freshness）必须大于 0 | 交付条件不满足（DELIVER_REQUIREMENT_NOT_MET） |
| 队伍不能正在移动、窗口争夺、休整、强制通行、通用处理或宫门验核 | 按当前状态处理，不进入交付结算；移动中返回 MOVING_ACTION_FORBIDDEN，休整中返回 RESTING_ACTION_FORBIDDEN，读条中继续推进原读条，窗口中跳过主动作 |

---

## 6.2 分项得分

最终总分由六项正向分数减去惩罚分得到：

```text
最终总分 = max(0, 送达基础分 + 好果数量分 + 鲜度品质分 + 用时分 + 皇榜任务分 + 破关悬赏分 - 惩罚分)
```

普通任务基础分累计（finalTaskScoreRaw）按本局已完成的普通皇榜任务模板分值相加：T01、T02、T04、T06、T08、T11 每个 30 分，T12、T13、T14 每个 15 分。任务模板详见 5.1。

破关悬赏原始分（bountyScoreRaw）按本局已获得的破关悬赏基础分相加：普通悬赏 10 分，关键关隘悬赏 18 分。悬赏类型和领取条件详见 5.4。

普通任务基础分累计不是单独的一项最终得分。它只影响送达基础分、用时分和皇榜任务分。

本节公式是当前规则配置展开后的固定写法；若送达分满分任务基准、送达分保底系数或用时分满分任务基准调整，必须同步更新本节公式。

| 分数维度 | 计算口径 |
|---|---|
| 送达基础分 | 已交付时计算。普通任务基础分累计越高，送达基础分越高；达到 90 后拿满 240 |
| 好果数量分 | 按交付时的好果数量计算 |
| 鲜度品质分 | 按交付时的鲜度计算 |
| 用时分 | 先按交付帧计算原始用时分，再按普通任务基础分累计折减 |
| 皇榜任务分 | 按普通任务基础分累计计入，并在 60 / 90 / 110 时获得里程碑奖励 |
| 破关悬赏分 | 按破关悬赏原始分计算 |
| 惩罚分 | 按非法动作和交付后违规动作扣分 |

任务与悬赏计分边界：

| 规则点 | 说明 |
|---|---|
| 计分条件 | 只有完成普通皇榜任务或破关悬赏目标才计分，普通经过任务点或悬赏相关节点不计分 |
| 分项关系 | 皇榜任务分和破关悬赏分是两个独立分项，分别封顶，分别计入最终总分 |
| 上限关系 | 皇榜任务分不包含破关悬赏分；破关悬赏分不占用皇榜任务分上限 |

已交付 / 未交付计算路径总览：

```mermaid
flowchart TD
  A["比赛结束，生成 over.scoreDetail"] --> B{"是否完成交付"}

  B -- "未交付" --> N1["送达基础分、好果数量分、鲜度品质分、用时分 = 0"]
  N1 --> N2["皇榜任务分 = min(finalTaskScoreRaw, 80)<br/>不应用里程碑奖励"]
  N2 --> N3["破关悬赏分 = min(bountyScoreRaw, 25)<br/>不应用完成额外奖励"]
  N3 --> Z["最终总分 = max(0, 六类正向分数 - 惩罚分)"]

  B -- "已交付" --> C["读取交付快照<br/>交付帧 / 交付好果 / 交付鲜度"]
  B -- "已交付" --> D["计算普通任务基础分累计<br/>finalTaskScoreRaw"]
  B -- "已交付" --> E["读取破关悬赏原始分<br/>bountyScoreRaw"]

  C --> F["好果数量分 = floor(交付好果 / 100 × 180)"]
  C --> G["鲜度品质分 = floor(交付鲜度 / 100 × 180)"]
  C --> H["原始用时分<br/>rawTimeScore = floor((600 - 交付帧) / 600 × 70)"]

  D --> I["送达基础分<br/>= min(240, 120 + floor(finalTaskScoreRaw × 4 / 3))"]
  D --> J["任务系数<br/>= min(finalTaskScoreRaw, 90) / 90"]
  H --> K["用时分<br/>= floor(rawTimeScore × 任务系数)"]
  J --> K
  D --> L["皇榜任务分<br/>= min(180, finalTaskScoreRaw + 里程碑奖励)<br/>里程碑奖励：小于60为0 / 60-89为15 / 90-109为35 / 110及以上为50"]
  E --> M["破关悬赏分<br/>bountyScoreRaw > 0 时：min(bountyScoreRaw, 80) + 20<br/>否则为 0"]

  L --> Z
```

送达基础分：

未交付为 0 分；已交付可按以下公式计算送达基础分：

```text
送达基础分 = min(240, 120 + floor(finalTaskScoreRaw × 4 / 3))
```

比如：普通任务基础分累计为 0 时，送达基础分为下限 120；达到或超过 90 时，送达基础分为上限 240。

好果数量分与鲜度品质分：

这两项只在已交付时计算，使用交付成功时锁定的交付快照；未交付时均为 0。

```text
好果数量分 = floor(交付好果 / 100 × 180)
鲜度品质分 = floor(交付鲜度 / 100 × 180)
```

鲜度小数处理：

| 规则点 | 说明 |
|---|---|
| 比赛过程 | 每个结算帧按 3.4 计算本帧鲜度扣除值，并从当前鲜度中扣除；扣减后的鲜度作为下一结算帧的当前鲜度，保留小数 |
| 交付快照 | 交付成功时，系统锁定当时的好果数量和鲜度，用于计算好果数量分与鲜度品质分 |
| 计分取整 | 计算好果数量分和鲜度品质分时，都按上方公式执行 `floor` |
| 示例 | 交付鲜度为 76.5 时，鲜度品质分为 137 |

用时分：

未交付为 0 分；已交付先按交付帧计算原始用时分，再按普通任务基础分累计（finalTaskScoreRaw）折减。交付帧指交付成功所在的结算帧编号。

```text
原始用时分 = floor((600 - 交付帧) / 600 × 70)
用时分 = floor(原始用时分 × min(finalTaskScoreRaw, 90) / 90)
```

比如：普通任务基础分累计为 0 时，用时分为 0；达到或超过 90 时，用时分不再被任务基础分折减。

皇榜任务分：

未交付时，不应用里程碑奖励，皇榜任务分最高只计入 80：

```text
皇榜任务分 = min(finalTaskScoreRaw, 80)
```

已交付时，皇榜任务分按普通任务基础分累计（finalTaskScoreRaw）和里程碑奖励计算，最高 180 分：

| 普通任务基础分累计 | 里程碑奖励 |
|---:|---:|
| 小于 60 | 0 |
| 60-89 | 15 |
| 90-109 | 35 |
| 110 及以上 | 50 |

```text
皇榜任务分 = min(180, finalTaskScoreRaw + 里程碑奖励)
```

破关悬赏分：

未交付时，不应用悬赏完成额外奖励，破关悬赏分最高只计入 25：

```text
破关悬赏分 = min(bountyScoreRaw, 25)
```

已交付时，破关悬赏分按破关悬赏原始分（bountyScoreRaw）计算；若原始分大于 0，再获得 20 分完成奖励：

```text
破关悬赏分 = bountyScoreRaw > 0 ? min(bountyScoreRaw, 80) + 20 : 0
```

未交付处理汇总：

| 分项 | 未交付时处理 |
|---|---|
| 皇榜任务分 | 最高只计入 80 分，不应用里程碑奖励 |
| 破关悬赏分 | 最高只计入 25 分，不应用悬赏完成额外奖励 |
| 送达基础分 | 0 |
| 好果数量分 | 0 |
| 鲜度品质分 | 0 |
| 用时分 | 0 |

## 6.3 惩罚项

惩罚分分为两类：普通非法动作惩罚和交付后违规惩罚。两类惩罚分别计数、分别封顶；同一个动作只进入其中一类，不重复扣分。

| 惩罚类型 | 适用阶段 | 扣分规则 | 上限 |
|---|---|---|---:|
| 普通非法动作惩罚（INVALID_ACTION） | 队伍未交付前，或动作不属于交付后违规规则时 | 前 5 次不扣分；第 6 次起每次扣 1 分 | 20 |
| 交付后违规惩罚（POST_DELIVER_PENALTY） | 队伍已交付后，提交等待、空动作心跳、系统等待、重复交付以外的动作 | 每次扣 5 分 | 30 |

普通非法动作惩罚和交付后违规惩罚互不占用上限。已交付队伍的违规动作走交付后违规惩罚，不再计入普通非法动作次数。

普通非法动作惩罚（INVALID_ACTION）：

| 次数 | 扣分 |
|---|---:|
| 前 5 次 | 0 |
| 第 6 次起 | 每次扣 1 分 |
| 上限 | 20 分 |

普通非法动作不按具体动作名称逐个列举，而按校验失败类别判定。动作提交只要落入下表任一类别，就记录为普通非法动作（INVALID_ACTION）；不在下表类别中的业务拒绝，不进入普通非法动作计数。

| 判定类别 | 判定条件 | 示例提交 | 服务端反馈 |
|---|---|---|---|
| 动作类型不存在 | 提交的动作类型不在规则支持的动作集合中 | 提交未知 actionType | 非法动作类型（INVALID_ACTION_TYPE） |
| 当前阶段禁止 | 动作类型存在，但当前比赛阶段不允许提交 | NORMAL 阶段提交疾行令；NORMAL 阶段提交宫门验核；单独提交破关令 | 非法动作类型（INVALID_ACTION_TYPE） |
| 必填参数缺失 | 动作缺少规则要求的必要字段 | 移动缺少目标节点；处理皇榜任务缺少任务编号 | 参数非法（INVALID_PAYLOAD）或对应字段错误码 |
| 参数类型或取值非法 | 字段类型不对，或取值不在允许范围内 | targetNodeId 不是合法节点编号；窗口牌不在允许枚举中 | 参数非法（INVALID_PAYLOAD）或对应字段错误码 |
| 移动目标无路线边 | 移动目标节点存在，但当前节点到目标节点没有本局路线边 | MOVE 到非相邻节点 | 非法移动（MOVE_EDGE_NOT_FOUND） |
| 同类动作超上限 | 同一结算帧提交超过规则允许数量的同类动作 | 同一动作包同时提交移动和领取资源；同时提交两个小分队动作 | 同类动作冲突（INVALID_ACTION_CONFLICT） |

以上类别统一计入普通非法动作次数；第 6 次起每次扣 1 分，普通非法动作扣分上限为 20 分。动作包不属于当前结算帧，或超过本帧接收截止才到达时，接入层返回动作过晚（ACTION_TOO_LATE）；该动作包不进入本帧动作列表，不增加普通非法动作次数。交付后违规惩罚单独计算，见下文“交付后违规惩罚（POST_DELIVER_PENALTY）”。

业务拒绝不扣惩罚分，也不增加普通非法动作次数。业务拒绝按下表类别判定：

| 业务拒绝类别 | 判定条件 | 处理 |
|---|---|---|
| 公共对象已被占用 | 目标任务、资源、宫门、处理点、障碍或通行对象已被占用，且规则没有触发窗口争夺 | 动作不生效，无惩罚 |
| 公开状态不满足动作条件 | 队伍位置、处理状态、验核状态、休整状态或移动状态不满足该动作条件；不包含当前阶段禁止的动作，也不包含已交付后的违规提交动作 | 动作不生效，无惩罚；休整拒绝不重置休整倒计时 |
| 资源或成本不足 | 队伍资源、资源库存或动作成本不足；CLAIM_RESOURCE 缺资源类型或目标资源库存不足；USE_RESOURCE 缺资源类型或队伍没有该资源 | 动作不生效，无惩罚 |
| 公开参数范围越界 | SET_GUARD.extraGoodFruit、BREAK_GUARD.goodFruit 或 BREAK_GUARD.badFruit 不在 0-2 范围内 | 返回 ACTION_REJECTED / PARAM_OUT_OF_RANGE；动作不生效，无惩罚，不截断参数 |
| 公开目标不可处理 | 情报超出距离、目标不在处理节点、任务不可处理、处理点不可用、资源当前不可生效等公开业务条件不满足 | 动作不生效，无惩罚 |
| 重复完成类动作 | 已完成验核后重复验核，或已交付后重复交付 | 动作不生效，无惩罚；重复交付不触发交付后违规惩罚 |
| 平局冷却或保护期拒绝 | 对象处于重复平局冷却，或任务处于窗口胜方保护期 | 动作不生效，无惩罚 |

交付后违规惩罚（POST_DELIVER_PENALTY）：

队伍进入已交付（DELIVERED）后，按下表判断是否扣交付后违规惩罚：

| 情况 | 动作结果 | 是否扣交付后违规惩罚 |
|---|---|---|
| 等待（WAIT） | 动作有效 | 否 |
| 空动作心跳（actions: []） | 计为有效心跳 | 否 |
| 本帧未收到动作包，由系统等待 | 按系统等待处理 | 否 |
| 重复交付（DELIVER） | 返回已交付拒绝，不重复结算 | 否 |
| 除以上情况外的任一提交动作 | 动作不生效 | 是，每次扣 5 分，上限 30 分 |

交付后违规动作不计入普通非法动作，按本类惩罚独立扣分。达到 30 分上限后，后续违规动作仍不生效，只是不再增加本类惩罚分。

已交付队伍不再主动参与通行窗口。若该队伍交付前留下的设卡后来触发通行窗口，系统直接将该队伍本拍按弃权（ABSTAIN）结算，不扣交付后违规分。若该队伍交付后主动提交窗口出牌（WINDOW_CARD），该提交属于交付后违规动作。

## 6.4 失联与退赛

断线只表示队伍当前离线，不直接判退赛。失联计数和退赛判定只适用于未交付队伍：收到动作包时，失联计数清零；未收到动作包时，失联计数增加 1 个结算帧。已交付队伍不再累计失联退赛，只处理等待、空动作心跳、重复交付容错和交付后违规惩罚。

| 情况 | 本帧处理 | 失联计数 |
|---|---|---|
| 未收到动作包，且不在窗口出牌拍 | 系统执行兜底处理；路线边上的主车队继续向下一目标节点前进 | 增加 1 个结算帧 |
| 未收到动作包，且处于窗口出牌拍 | 本拍按弃权（ABSTAIN）结算 | 增加 1 个结算帧 |
| 收到空动作心跳（actions: []） | 按心跳规则处理 | 清零 |
| 收到可识别的本局动作包，但动作被拒绝或规则校验失败 | 按对应拒绝、非法动作或惩罚规则处理 | 清零 |

主动提交等待（WAIT）表示本帧已收到动作包，会清零失联计数。队伍在路线边上主动提交等待时，主车队停在当前位置，已走移动量不增不减。

未交付队伍连续 10 个结算帧未收到动作包，记录失联警告（DISCONNECT_WARNING）。未交付队伍连续 60 个结算帧未收到动作包时，系统会在本帧逐队执行主动作前判定该队进入已退赛（RETIRED），并按退赛规则结束本局。判定前本帧已经完成的持续效果、风化、任务、悬赏、小分队和窗口处理不回滚。

退赛（RETIRED）处理：

队伍进入已退赛后，从该队本帧退赛判定点开始，不再继续结算该队本帧主动作、鲜度损耗和后续收益，并清理该队伍仍在进行或留在地图上的内容：

| 清理对象 | 处理 |
|---|---|
| 主车队 | 从地图移除 |
| 未完成动作、处理中流程、窗口争夺 | 立即结束，不再结算后续收益或结果 |
| 小分队在途队列 | 清空，不再产生效果 |
| 本方设卡 | 防御值（defense）归 0 |
| 后续得分 | 不再获得后续分数 |

退赛清理后，本局按退赛结果结束；双方都未退赛时，才按最终总分判断胜负：

| 退赛情况 | 比赛结果 | over 字段 |
|---|---|---|
| 只有一方进入已退赛 | 退赛方判负，未退赛方获胜；当前结算帧生成 `over` | `resultType = "FORFEIT"`；`overReason = "SINGLE_RETIRED"`；`winnerPlayerId = 未退赛方玩家编号` |
| 双方在同一结算帧进入已退赛 | 本局无效，按无胜方处理；当前结算帧生成 `over` | `resultType = "INVALID"`；`overReason = "BOTH_RETIRED"`；`winnerPlayerId = null` |

退赛不会把总分或分项分数清零。退赛时，双方按比赛结束帧已有状态生成总分和分项分数；未交付队伍的送达基础分、好果数量分、鲜度品质分和用时分仍为 0。退赛局的分数只用于结果展示、回放和统计，不参与胜负判断。

# 7. 公平性与兜底规则

## 7.1 同一结算帧公平结算

服务端在当前结算帧（round）截止前收集双方动作包（action）。截止后，服务端基于结算帧开始状态同时校验双方动作。

同一结算帧争夺同一资源、任务、公开处理点、宫门验核或障碍清理时，比赛进入对应窗口争夺。公开处理点以本局 `gameplay.processNodes` 和处理对象键（objectKey）为准；双方同帧提交同一种处理时进入窗口争夺，不按阵营、玩家编号或动作到达顺序分配处理权。资源领取流程被后手争抢时，第 1 次打断创建资源窗口；同一份资源第 2 次起返回对象忙（OBJECT_BUSY），不再打断原领取流程。强制通行遇到敌方有效设卡时，按通行窗口（PASS）规则生成窗口；只有道路障碍的强制通行不生成 PASS 窗口。

服务端禁止按以下顺序直接分配权益：

| 禁止依据 | 含义 |
|---|---|
| 队伍标识顺序（teamId） | 不得固定红方或蓝方优先 |
| 玩家编号（playerId） | 不得按玩家编号大小优先 |
| 玩家列表顺序（players） | 不得按数组顺序优先 |
| 动作到达顺序（action） | 不得按谁先到服务端优先 |
| 网络包到达顺序（TCP） | 不得按底层网络包先后优先 |

公平裁决分为两层：

1. 普通稳定裁决：用于主动作遍历、消息派发、窗口牌扫描等一般排序。普通稳定裁决基于 seed、结算帧、结算阶段、对象键和无序玩家集合生成槽位顺序；同一对象、同一节奏反复出现时应轮换先手，避免高编号或低编号玩家连续获得节奏优势。
2. 独占冲突公平账本：用于对象锁、小分队清障 / 增援 / 削弱等会让一方获得独占收益的真实争用。服务端按“全局胜出次数少者优先；仍相同时，同阶段胜出次数少者优先；仍相同时，同对象胜出次数少者优先；仍相同时，再看普通稳定裁决”的规则排序。账本 key 只使用结算层级、结算阶段、争用对象键和无序玩家集合，不包含阵营顺序、连接顺序或玩家编号大小。

普通稳定裁决槽位生成规则：

| 输入 | 用途 |
|---|---|
| 本局随机种子（seed） | 保证同一局 replay 可复现 |
| 结算帧（round） | 参与槽位轮转，避免固定节奏长期偏向同一身份 |
| 结算阶段（phase） | 区分主动作、资源、任务、窗口牌、对象锁、小分队等不同阶段 |
| 争用对象键（objectKey） | 区分不同资源、任务、处理点、宫门验核或通行对象 |
| 无序玩家集合 | 只表达“参与本次排序的是哪批玩家”，不表达玩家编号大小、阵营或连接顺序 |

服务端实现公平裁决时，不得采用“先按 `playerId` 升序排列，再按奇偶整体翻转”的方式。该方式在镜像策略、固定节奏和重复同帧争用中仍可能让高编号或低编号玩家长期获得节奏先手。

服务端也不得为单个 `playerId` 生成身份盐后直接比较排序分。`playerId` 可以进入无序玩家集合 key，用于表达“这批玩家是谁”，但不能形成“大编号更容易先手”或“小编号更容易先手”的稳定偏置。

独占冲突公平账本只在真实冲突产生胜者后写入，不因日志输出、状态快照、普通等待或无冲突动作写入。一次真实冲突会同时写入三层账本：

| 层级 | key 示例 | 作用 |
|---|---|---|
| 全局玩家对 | `GLOBAL|5:25` | 防止早期一次清障、设卡或任务先手跨对象滚雪球 |
| 阶段玩家对 | `PHASE|OBJECT_LOCK|5:25` | 防止同类冲突在多个对象之间连续偏向一方 |
| 对象玩家对 | `OBJECT|OBJECT_LOCK|TASK:T_001|5:25` | 防止同一对象重复争用连续偏向一方 |

当前应写入账本的业务场景包括：

| 场景 | 对象键示例 | 写入时机 |
|---|---|---|
| 非窗口独占读条锁 | 以对应业务规则的对象键为准 | 服务端选出允许启动读条的一方后 |
| 同目标小分队清障 | `SQUAD:CLEAR_OBSTACLE:S10` | 障碍被实际清除后 |
| 同目标小分队增援 / 削弱 | `SQUAD:GUARD_DEFENSE_DELTA:S10` | 设卡防守值被实际改变后 |

同一空节点同帧设卡（SET_GUARD）属于不可窗口化的独占对象冲突。服务端按独占冲突公平账本选出一方进入设卡读条，其余方返回对象忙；本次真实冲突会写入独占冲突公平账本，用于后续同类争用轮换先手。

## 7.2 同类动作冲突

同一结算帧内动作类别上限：

| 类别 | 上限 |
|---|---:|
| 主车队动作 | 1 |
| 小分队动作 | 1 |
| 窗口出牌动作 | 1 |
| 终局急策动作 | 1 |

同一类别动作数量超过 1 时，该类别全部判定为非法。服务端不从中挑选合法动作。

同一结算帧内不同类别动作共享同一类资源时，服务端按 1.7 结算顺序校验、预占和扣除资源；后序动作在轮到自身结算时资源不足，按该动作的成本不足规则失败。资源数量不得变成负数。

若队伍同一结算帧同时参与多个窗口，仍然只允许提交 1 个窗口出牌（WINDOW_CARD）。该动作绑定的窗口编号（contestId）正常结算，其他未出牌窗口按弃权（ABSTAIN）处理；这种情况不算同类动作冲突。

绑定破关令（BREAK_ORDER）虽然跟随主车队动作提交，也占用终局急策类别额度。

处理：

| 冲突类别 | 处理 |
|---|---|
| 主车队类别冲突 | 主车队本结算帧按系统等待（WAIT）处理，并记录同类动作冲突（INVALID_ACTION_CONFLICT） |
| 小分队类别冲突 | 本结算帧不执行小分队动作，并记录同类动作冲突 |
| 窗口出牌类别冲突 | 本次窗口出牌按弃权（ABSTAIN）处理，并记录同类动作冲突 |
| 终局急策类别冲突 | 本结算帧不执行终局急策，并记录同类动作冲突 |

## 7.3 隐藏信息错误码

当前规则不维护红蓝双方独立隐藏视图。资源库存、节点设卡、道路障碍、当前任务、当前悬赏和当前天气均公开。

以下信息仍不在正式比赛实时协议中公开：

| 不公开信息 | 拒绝方式 |
|---|---|
| 完整随机种子（seed） | 动作拒绝（ACTION_REJECTED） |
| 完整未来天气序列 | 动作拒绝 |
| 未刷新的未来皇榜任务 | 动作拒绝 |
| 敌方未提交动作 | 动作拒绝 |
| 未来回放帧 | 动作拒绝 |

这里的动作拒绝是协议层或安全层拒绝消息，不等同于规则结算中的非法动作扣分事件。服务端不得通过错误码泄露完整未来天气、未来任务、隐藏随机种子和敌方未提交动作。

## 7.4 回放可见性

实时比赛期间，参赛程序不得读取回放文件（replay.txt）。服务端不得通过实时接口下发完整回放。

正式比赛实时状态只通过查询消息（inquire）下发。

正式比赛普通（debugVisibility=normal）可见性下，查询消息中禁止包含：

| 禁止内容 |
|---|
| 完整随机种子 |
| 完整天气序列 |
| 完整未来皇榜刷新结果 |
| 敌方未公开动作 |
| 未来回放帧 |

查询消息中的调试字段（debug）只用于开发排查。完整随机种子（seed）只在本地 / client-debug 启动模式下可见；正式或比赛模式即使开启调试可见性，也只允许下发 seedHash 和必要调试摘要，不下发完整 seed。参赛程序不能依赖 debug 中的 seed、事件快照或状态快照。

服务端生成回放文件。回放文件包含本局随机种子、完整天气、完整事件和最终结算。

赛前公开样例和开发回放只用于开发和回放验证，不得复用正式比赛将使用的随机种子、天气序列和任务序列。赛后公开的本局回放可以包含本局完整随机种子、完整天气序列、完整事件和最终结算。

本地运行模式固定为三类：

| 中文模式 | 模式 | 回放文件生成规则 |
|---|---|---|
| 调试模式 | DEBUG_MODE | 边跑边写回放文件 |
| 模拟模式 | SIMULATION_MODE | 边跑边写回放文件，比赛结束后包含完整对局 |
| 正式模式 | OFFICIAL_MODE | 边跑边写回放文件，参赛程序进程无读取权限 |

## 7.5 随机种子可见性

| 场景 | 下发内容 |
|---|---|
| 实时开始消息（start） | 只下发种子哈希（seedHash），不下发完整随机种子（seed） |
| 种子哈希用途 | 只用于赛后校验，不用于实时推算 |
| 回放开始帧 | 下发完整随机种子 |
| 查询调试字段（debug） | 正式 / 比赛模式不下发完整 seed；普通可见性下为空对象或只含必要摘要，summary/full 也只能包含 seedHash 和调试快照。本地 / client-debug 启动模式可包含完整随机种子和调试快照 |

实时开始消息（start）面向参赛程序的必需字段包括 `matchId`、`rulesVersion`、`seedHash`、`round`、`durationRound`、`players`、`nodes`、`edges`、`resources` 和 `taskTemplates`。当前服务端同时下发 `tick`、`map` 和 `routePaths`：`tick` 在 start 中为 0，只用于兼容定位；`map` 是本局地图配置回显；`routePaths` 是路线渲染折线。

顶层 `start.resources` 和 `start.taskTemplates` 是系统应用本局地图配置后生成的有效静态表；`start.map.gameplay` 保留地图玩法点位绑定，用于理解点位来源和复核地图配置，不是另一套运行时资源或任务表。

参赛程序判断合法相邻节点、路线类型、基础逻辑距离、站点类型、资源初始投放和任务模板时，应使用本局 `start` 缓存；判断资源库存、障碍、设卡、处理类型和处理时间时，以每帧 `inquire.nodes` 为准。`inquire.edges` 是每帧路线边同步副本，某帧缺失时才回退使用 `start.edges`。`tick`、`map` 和 `routePaths` 不参与动作合法性、移动结算或胜负结算。实时 start 不下发完整 `seed`，也不下发完整天气序列；实时天气只通过 `inquire.weather.active` 和 `inquire.weather.forecast` 公开。查询调试字段（debug）的本地调试例外不改变正式比赛的信息可见性。

## 7.6 防死锁规则

- 相邻目标节点存在敌方有效设卡或道路障碍时，必须可以通过强制通行（FORCED_PASS）处理；目标无阻挡时不能提交强制通行；
- 道路障碍必须允许主车队清障（CLEAR）、小分队清障（SQUAD_CLEAR）；强制通行（FORCED_PASS）只允许本队本次通过，不解除障碍；
- 窗口固定 3 拍，3 拍结束必须立刻给出胜、负或平局（DRAW），不得悬挂未决；
- 同一窗口编号（contestId）关闭后不得重复触发；
- 设卡只产生延误，不产生永久阻塞；
- 未交付队伍在兴庆宫（S15）时，未验核只能等待（WAIT）或返回 S14；已验核且满足交付条件时可以交付（DELIVER）；已验核但不满足交付条件时只能等待或返回 S14；
- 已交付队伍不罚的提交只有等待（WAIT）、空动作心跳、系统等待和重复交付（DELIVER）；其他动作不生效，并按交付后违规惩罚（POST_DELIVER_PENALTY）处理；
- 未完成验核（verified = false）的队伍不能从 S14 正常进入兴庆宫；验核完成并在下一结算帧生效后，才允许从 S14 前往 S15。若兼容状态中未验核队伍已经位于兴庆宫，只允许通过返回 S14 的移动回到朱雀门；该返回移动无视 S14 设卡和道路障碍，但不清除阻挡；
- 0 防守值节点不阻挡通行；
- 断线先标记离线，不直接退赛；连续缺动作 10 个结算帧触发警告，连续缺动作 60 个结算帧进入退赛；
- 单方退赛立即判负并结束比赛；双方同帧退赛时本局无效且无胜方；双方都未退赛时才按最终总分判断胜负；
- 主车队重叠不产生碰撞阻挡。

# 8. 静态地图配置规范

## 8.1 配置结构

单局地图配置为：

```text
map_config.json
```

包含配置段：

```text
schemaVersion
mapId
mapName
designVersion
grid
map
layers
legend
nodes
edges
gameplay
routePaths
weatherRegionRule
assetMapping
dynamicRenderContract
```

本局配置来源说明：

```text
map_config.json 是单局地图与地图玩法点位绑定来源。
grid、map、layers、legend、nodes、edges、routePaths、weatherRegionRule 参与地图加载和回放展示。
资源投放点、流程节点、任务候选点、路线任务桶节点和道路障碍候选点以 gameplay 为准；本轮正式地图保持 S01 起点、S14 宫门、S15 终点。
计分、动作效果、天气生成策略、窗口克制、资源效果、惩罚和退赛等通用规则仍以 lychee-rule-set.json 为准。
```

服务端加载地图时，如果当前地图 JSON 存在 `gameplay`，会先把 `gameplay.resources`、`gameplay.processNodes`、`gameplay.taskCandidates`、`gameplay.routeTaskBuckets`、`gameplay.obstacleCandidateNodeIds` 和 `gameplay.roles` 应用到运行态规则中。开局下发的 `start.resources`、`start.taskTemplates` 以及后续结算，均以应用地图后的运行态规则为准。顶层 `start.resources`、`start.taskTemplates` 是参赛程序直接使用的有效表；`start.map.gameplay` 是地图点位绑定来源，不与顶层表竞争结算优先级。

地图字段闭环规则：

```text
设计文档中凡是描述“地图 JSON 字段”的内容，必须使用当前 `map_config.json` 真实存在的字段名。
当前地图 JSON 不存在的字段，不得写成地图字段；若确实需要新增字段，必须先更新地图 JSON / schema，再更新本文档和服务端加载校验。
运行时状态字段写在同步协议章节；通用规则参数写在 lychee-rule-set.json 或规则配置章节；两者都不能伪装成 map_config.json 字段。
```

不同地图配置可用于不同局比赛。任一局比赛开始后，本局地图与规则配置保持静态固定，不做局内热更新。

### 8.1.1 地图变体边界

地图变体允许改变：

- 路线边清单（`edges[]`），包括路线边数量、端点、路线类型、逻辑距离和双向标记；
- 路线逻辑距离（`edges[].distance`）；
- 站点坐标（`nodes[].x / nodes[].y`），所有正式站点坐标均以本局地图为准；
- 路线显示路径（`routePaths[].points`）；
- 地图总览格子（`map.data`）；
- 地形格子（`layers.terrainData.data`）；
- 站点对象格子（`layers.objectData.data`）；
- 天气区域格子（`layers.weatherRegionData.data`）；
- 流程节点绑定（`gameplay.processNodes`）；
- 资源投放清单（`gameplay.resources`）；
- 任务候选点（`gameplay.taskCandidates`）；
- 路线任务桶（`gameplay.routeTaskBuckets`）；
- 障碍候选点（`gameplay.obstacleCandidateNodeIds`）。

地图变体不允许仅靠地图文件改变：

- 节点编号集合，当前固定为 S01-S15 共 15 个节点；
- 当前正式规则中的核心角色语义：S01 起点、S14 宫门、S15 终点；
- S01-S15 的站点编号、编码、站点名、类型和图标；
- 正式路线类型集合及其结算含义；调测图和 A/B/C 只使用 ROAD、WATER、MOUNTAIN、BRANCH；
- 处理类型机制，例如 TRANSFER、BOARD、WATER_TRANSFER、PASS_TRANSFER、PALACE_TRANSFER、VERIFY 的规则含义；
- 资源效果机制，例如冰鉴、马类、过所、官凭、船权、情报的使用效果；
- 任务类型、任务分值和任务处理帧数；
- 天气类型和天气生成规则；
- 分数、资源效果、动作效果、窗口克制关系和惩罚规则；
- 路线类型机制，例如 ROAD / WATER / MOUNTAIN / BRANCH 的结算含义；
- 主车移动、任务、资源领取、清障、强制通行、设卡、窗口争夺、验核、交付、计分等核心规则机制；
- 动作枚举、错误码和协议字段。

`gameplay.roles` 必须与固定核心节点口径一致：S01 为起点，S14 为宫门，S15 为终点。改变宫门、终点或新增多终点属于规则机制变更，不能只通过地图变体完成。

### 8.1.2 gameplay 点位绑定

`gameplay` 用于声明当前地图上哪些站点承担玩法职责。

```text
roles.startNodeId：起点。
roles.terminalNodeIds：终点；当前规则固定为 S15。
roles.gateNodeId：宫门验核点；当前规则固定为 S14。
roles.reverifyNodeId：需要重新验核时返回的站点；当前规则固定为 S14。
roles.rushExcludedNodeIds：终段交锋节点。第 390-449 结算帧内，队伍位于这些节点时，不会仅因“接近终点”提前触发宫宴冲刺；到达宫门 S14 或第 450 结算帧仍会正常触发。
resources：资源初始投放清单；地图可以声明投放站点、资源类型、数量和领取帧数，但资源效果仍按固定规则结算。
processNodes：流程节点绑定；地图可以声明处理站点、处理类型、处理帧数和是否可窗口争夺，但处理类型含义和 PROCESS 动作协议不变。
taskCandidates：各任务模板可刷新的候选站点。
routeTaskBuckets：按 ROAD、WATER、MOUNTAIN 分组的任务供给节点集合；BRANCH 只作为转线和交锋位置调整使用，不作为默认稳定任务供给桶。
obstacleCandidateNodeIds：道路障碍候选点列表。
```

gameplay 点位绑定规则：

```text
结算使用 gameplay 中的地图点位绑定。
资源点、处理点、任务候选点、路线任务桶节点、道路障碍候选点、宫门和终点均必须能在当前地图节点中找到。处理点的处理类型必须属于服务端已支持类型；处理点挂载站点、处理帧数和是否可窗口争夺以当前地图 `gameplay.processNodes` 为准。
```

### 8.1.3 本局配置读取

每局启动时必须读取并绑定以下配置：

| 文件 / 来源 | 是否每局动态选择 | 结算用途 | 局内是否热更新 |
|---|---|---|---|
| `map_config.json` 或被选择的地图变体 JSON | 是 | 读取地图网格、节点、路线边、路线折线、天气区域和 gameplay 点位绑定；校验节点 / 边 / 路径引用；下发本局地图数据 | 否 |
| `lychee-rule-set.json` | 可由比赛启动参数指定，默认线上固定 | 读取计分、动作效果、天气生成策略、窗口、资源效果、惩罚、退赛等通用规则 | 否 |
| 比赛启动参数 / match config | 是 | 指定本局使用的地图文件、规则集文件、随机种子或 seedHash、队伍信息 | 否 |

`map_config.json` 是空间、可视和地图点位绑定来源；`lychee-rule-set.json` 是通用玩法参数来源。结算规则不得从展示文件、PNG 预览图或 Excel 导出文件反推。

地图点位绑定优先级如下：

1. 若当前局地图 JSON 中存在 `gameplay`，资源投放、流程节点、任务候选点、路线任务桶、道路障碍候选点、宫门、终点和安全区等点位绑定以 `gameplay` 为准。
2. `lychee-rule-set.json` 中同类点位字段只作为旧地图或缺失 `gameplay` 时的兼容兜底；正式地图不应依赖这些旧点位兜底来表达地图差异。
3. 计分公式、动作效果、天气类型、天气生成策略、窗口克制、资源效果、惩罚和退赛等通用规则仍以 `lychee-rule-set.json` 为准，不允许通过地图 JSON 改变这些机制。

默认地图文件存放在服务端工程 `server/src/main/resources/maps/map_config.json`，默认规则配置 `game-default.yaml` 指向 `classpath:maps/map_config.json`。线上启动时如果不传地图参数，服务端使用这个默认地图；如果需要换地图，可以在启动命令传入 `-m` 或 `--map` 指定地图 JSON，例如：

```bash
java -jar lychee-arena-server.jar --map /opt/lychee/maps/map_config_medium.json
```

被指定的地图文件仍必须符合本章 `map_config.json` 结构，并通过地图校验。换地图可以改变路线边数量、路线端点、路线距离、路线类型、双向标记、S02-S13 坐标、路线显示路径、地图总览格子、地形格子、站点对象格子、天气区域格子、流程节点、资源投放清单、任务候选点、路线任务桶和障碍候选点；不得通过地图文件新增动作、协议字段、资源效果、错误码、天气类型、窗口牌型或核心结算机制。

Excel 文件仅作为策划交付、人工审阅或 QA 辅助产物。当前服务端可以保留 `.xlsx` 地图加载兼容入口，用于本地开发、旧工具验证或人工验图；线上比赛、赛题交付和正式换图应使用 JSON 地图文件，并以启动参数传入的 `map_config*.json` 为准。

当前局加载完成后：

- 主车到站所需移动量由当前局 `edges[].distance` 和路线耗时系数决定；
- 小分队距离以当前局 `nodes[].x/y` 换算切比雪夫距离为准；
- 资源投放站点、流程节点、任务候选点、路线任务桶、道路障碍候选点以当前局 `map_config.json` 的 `gameplay` 为准；
- 资源效果、任务模板、天气类型与生成规则以固定规则为准；
- 地图与回放展示以当前局 `routePaths.points`、节点坐标和图层为准。

## 8.4 layers.weatherRegionData 与 weatherRegionRule

当前 JSON 字段：


| 天气类型 | 天气区域代码（weatherRegionCode） | 渲染方式（renderMode） |

## 8.6 edges 配置段

字段固定为：

```text
edgeId
fromNodeId
toNodeId
routeType
distance
bidirectional
pathId
```

说明：

- distance 是路线距离；
- distance 不等于地图格子数量；
- 地图表现按 `edges[].edgeId`、运行时 `routeEdgeId` 和 `routePaths[].edgeId` 对齐路线折线；`pathId` 只作为地图配置内的保留字段，实时 `start.edges` 或 `inquire.edges` 即使下发该字段，也只用于展示兼容、路线分组或 UI 标识，不参与动作合法性、移动结算、收益判定或胜负结算；
- 主线、支路、码头、水路、终段关隘等策略含义由 `routeType`、节点类型和 `gameplay` 点位共同确定，不另设策略标签字段；
- 不同地图允许在保持拓扑骨架一致的前提下调整 distance；
- 主车队到站所需移动量必须使用当前局 `edges[].distance` 计算；
- `routePaths.points` 只用于路线绘制和主车队位置表现，不参与移动结算。

## 8.7 resources 配置段

资源点位写在 `gameplay.resources[]`。字段固定为：

```text
nodeId
resourceType
count
claimRound
```

`claimRound` 是该资源自己的领取帧数。正式地图应为每个资源项配置该字段；缺失时系统才回退使用通用资源领取帧数。

## 8.8 taskCandidates 配置段

任务候选点写在 `gameplay.taskCandidates`。它是任务编号到候选节点列表的映射，不是数组。

```text
T01: ["S03"]
T08: ["S04", "S05"]
T04: ["S06", "S08"]
T02: ["S07", "S10"]
T06: ["S09", "S04", "S06"]
T11: ["S08", "S10", "S11"]
T12: ["S11", "S13"]
T13: ["S13", "S09", "S12"]
T14: ["S10", "S11", "S12"]
```

任务时限、处理帧数和分数不是地图 JSON 字段；它们属于通用规则配置。

---

## 8.9 routeTaskBuckets 配置段

路线任务桶写在 `gameplay.routeTaskBuckets`。它是路线桶名称到候选节点列表的映射，不是数组。

`map_config.json` 调测地图默认配置：

```text
ROAD: ["S03", "S07", "S09", "S11", "S13"]
WATER: ["S04", "S05", "S09", "S10", "S12", "S13"]
MOUNTAIN: ["S06", "S08", "S10", "S11", "S12"]
```

规则：

- 路线任务桶只影响任务刷新目标选择，不改变路线通行规则；
- 刷新配置写入 `routeBuckets` 时，系统按该顺序为本批任务分配路线桶；
- 动态补位刷新同样使用路线任务桶；存在路线供给欠账时优先补欠账路线，否则优先补当前可直接处理任务较少的路线；“可直接处理”不包含窗口争夺中、胜方保护中、平局休整冻结中、重复平局冷却中、已完成、已失败或已过期任务；
- 每个任务目标必须同时属于对应任务模板候选点和对应路线任务桶；
- 没有配置 `routeBuckets` 或路线桶为空时，按任务模板轮询刷新。

## 8.10 天气事件规则配置（非地图 JSON 字段）

以下字段不属于 `map_config.json`。它们属于天气规则配置，用来生成每局天气事件：

```text
weatherPolicy.pool
avoidConsecutiveSame
weatherPolicy.windows[].eventIndex
weatherPolicy.windows[].startMin
weatherPolicy.windows[].startMax
weatherPolicy.windows[].durationRound
weatherPolicy.windows[].warningRound
```

天气事件结算帧窗口当前固定配置：

| eventIndex | startMin | startMax | durationRound | warningRound |
|---|---:|---:|---:|---|
| 1 | 80 | 120 | 60 | 30 |
| 2 | 200 | 240 | 60 | 30 |
| 3 | 320 | 360 | 60 | 30 |
| 4 | 440 | 480 | 60 | 30 |

天气序列生成当前固定配置：

| 配置项 | 当前值 | 说明 |
|---|---|---|
| `weatherPolicy.pool` | `HOT, HOT, HEAVY_RAIN, MOUNTAIN_FOG` | 天气池分布；不随实时协议下发；系统先按池子构造 4 个天气槽位，再洗牌生成事件顺序 |
| `avoidConsecutiveSame` | `true` | 若洗牌结果出现相邻同类天气，必须重新洗牌或调整顺序；最终天气序列不得相邻重复 |

`warningRound = 30` 表示系统固定提前 30 个结算帧下发天气预告。正式配置中 4 个天气窗口的 `warningRound` 均为 30，因此服务端可以按统一预告提前量对客户端公开天气预告。若后续希望不同天气窗口使用不同预告提前量，需要在规则配置和服务端实现中同时明确逐事件预告口径；本规则口径不建议配置成不同数值。

## 8.11 validation 配置段

地图加载前必须通过以下校验：

- S01 唯一；
- S14 唯一；
- S15 唯一；
- 节点集合必须为 S01-S15，不得新增或删除节点；
- 每个核心站点在 `layers.objectData.data` 中出现一次；
- 所有 `nodes[]` 坐标与 `layers.objectData.data` 一致；
- S01、S14、S15 的功能语义固定；本轮 A/B/C 中三者坐标分别保持 (5,50)、(76,18)、(78,18)；
- 所有 edge 端点存在；
- 路线边编号不得重复；
- 路线距离必须为正数；
- 路线类型必须属于正式路线类型集合；正式地图只使用 ROAD、WATER、MOUNTAIN、BRANCH；
- 调测图、A、B 的 `bidirectional` 均为 true；C 的 E22 为单向 `S08 -> S11`；移动合法性按当前地图 `edges[].bidirectional` 校验；
- 每条 routePaths 路线折线必须对应当前地图中一条真实存在的 edge；
- `routePaths[].points` 可以随地图变体变化，但必须覆盖当前地图所有 edge；
- `gameplay.processNodes` 的节点必须存在，处理类型必须是服务端已支持的处理类型；
- `gameplay.resources[]` 的节点必须存在，资源类型必须是服务端已支持的资源类型；
- 起点到任一终点存在合法路径；
- 官道、水路、山路三条主路径均存在；
- 策略支路以当前地图 `routeType = BRANCH` 的路线边为准，不要求每张地图都包含同一组历史支路编号；
- 任意起点到终点合法路径必须经过至少 2 个可交锋节点；
- 本版正式地图交付前必须经过宫门 S14；改变宫门、终点或新增多终点属于规则机制变更，不能只通过地图变体完成；
- 所有资源挂载节点存在；
- 同一节点同一资源类型的可争夺资源 count 必须为 1；
- 所有任务候选节点存在；
- S15 不挂载争斗功能；
- `weatherRegionRule` 中必须声明 HOT、HEAVY_RAIN、MOUNTAIN_FOG 三类天气展示规则；
- `layers.weatherRegionData.data` 中必须包含天气区域展示所需的区域编码；
- obstacleCandidateNodeIds 作为道路障碍候选点列表，节点必须存在，且可通过主车队清障（CLEAR）、小分队清障（SQUAD_CLEAR）解除；强制通行（FORCED_PASS）只允许本队本次通过，不解除障碍；
- edges 计算预算通过压测检查；
- 多地图场景下，每张地图均需独立通过地图校验；
- 每张地图的节点、路线距离、路线折线和天气区域均以当前局 `map_config.json` 独立生效；
- 资源投放点、任务候选点和道路障碍候选点以当前局 `map_config.json` 的 `gameplay` 为准，并必须通过当前局地图节点存在性校验；宫门和终点必须分别固定为 S14、S15。

运行时协议、动作结算顺序、马类增益覆盖和小分队同帧结算等规则验收见 11.1。本节只作为地图加载校验清单。

校验失败时，本局比赛不能启动。

over 回放帧字段说明：

| 字段 | 中文名 | 说明 |
|---|---|---|

| overRound | 结束结算帧 | 比赛结束时的结算帧 |

整局胜负只看退赛状态和最终总分。只有一方退赛时，未退赛方为胜方；双方同一结算帧退赛时，本局无胜方。双方都未退赛时，按最终总分直接比较；最终总分相同时，本局为平局，`resultType = "DRAW"`，`overReason = "SCORE_TIE"`，`winnerPlayerId = null`。同分直接平局，不比较阵营、playerId、交付先后、分项明细或 TCP 到达顺序。

## 10.6 回放规则

- 回放不重新计算规则；
- 前端只播放服务端已结算状态；
- 回放必须包含 seed；
- 回放必须包含完整天气序列；
- 回放必须包含最终结算；
- replay.txt 用于公开回放；
- debug_replay.txt 用于裁判审计；
- debug_replay.txt 不进入正式实时环境；
- 回放 round 的 players 复用实时状态中的主车队位置、鲜度、好坏果和分数字段，但 round 回放帧本身不要求与 inquire.msg_data 字段完全一致；
- 回放文件使用节点和路线边字段表达主车队位置。

| score_good_fruit | 好果分 | 好果数量折算结果 |

| player_name | 玩家名称 | registration 中的玩家名称 |

# 11. 验收标准

## 11.1 后端验收

后端必须满足：

- 加载当前局 map_config.json；
- 校验当前局地图；
- 支持使用 `map_config.json` 调测地图和符合 schema 的地图变体启动比赛；
- 换图后，主车到站所需移动量必须使用当前局 `edges.distance` 和路线耗时系数计算；
- 换图后，主车移动结算、坐标距离、路线折线和天气区域必须基于当前局 `map_config.json` 生效；
- 天气生效帧必须能通过 `WEATHER_EFFECT_EVAL` 审计日志区分“天气发生但未命中”和“天气实际影响队伍”，并记录命中的路线边或处理点、路线成本倍率、鲜度倍率和处理加时；
- 换图后，资源投放点、流程节点、任务候选点、路线任务桶和道路障碍候选点必须基于当前局 `map_config.json` 的 `gameplay` 生效；本轮 A/B/C 保持 S01 起点、S14 宫门、S15 终点；
- 道路障碍阻止普通移动直接进入目标节点；主车队清障（CLEAR）或 T04 任务处理允许从目标障碍节点或相邻节点发起，完成后不自动进入目标节点；
- 创建比赛；
- 接收 registration；
- 下发 start；
- 接收 ready；
- 每个结算帧下发 inquire；
- 接收 action；
- 执行服务端结算；
- 拒绝非法动作；
- 生成 replay.txt；
- 生成 over；
- 生成 data.csv，并输出路线统计字段。路线统计只用于赛后分析，不参与最终得分；
- 路线统计按服务端真实结算记录生成：ROAD 归为官道，WATER 归为水路，MOUNTAIN 归为山路，BRANCH 归为支路；
- main_route 按路线任务分最高确定。没有路线任务分时，按路线资源领取次数最高确定。仍没有路线收益时，按移动结算帧数最高确定；
- 同一 seed 下结果完全一致；
- 运行时协议使用 currentNodeId、nextNodeId、routeEdgeId、moveDirection、edgeProgressPermille、edgeProgressMs 和 edgeTotalMs 表达主车队位置；moveProgress、moveProgressRound 和 currentEdgeCost 仅为兼容字段；
- 每个结算帧推进移动时只看本帧正在生效且实际命中的天气；本帧天气只在命中当前移动点且路线类型匹配时通过路线成本倍率影响每帧新增移动量，天气结束后的结算帧按无天气影响的路线成本倍率计算，已经走过的移动量不回算；天气鲜度系数按天气区域命中判断，暴雨区域内移动鲜度 ×1.3；
- USE_RESOURCE 与 DELIVER 在结算帧第 15 步主动作结算时处理；
- 冰鉴（ICE_BOX）能在本结算帧天气损耗前生效；
- 鲜度小于等于 0 时，使用冰鉴（ICE_BOX）返回资源不可用（RESOURCE_NOT_USABLE），不消耗冰鉴，也不能恢复交付资格；
- 好果总量为 0 时，鲜度记为 0；坏果保留，但不记录鲜度；
- 交付（DELIVER）成功后本结算帧不再结算鲜度损耗；
- 马类增益同一时刻只保留 1 个，新马类消耗资源并覆盖旧马类；
- SQUAD_REINFORCE 与 SET_GUARD 同一结算帧完成时按小分队先结算规则处理；
- defense 降至 0 的设卡会从有效设卡集合移除，不能被 SQUAD_REINFORCE 重新激活；
- 破关悬赏条件一按“同一归属设卡防守值大于 0 连续存在 30 个结算帧”判定，创建悬赏时仍要求风化后 defense > 0；
- 宫宴冲刺触发时不生成额外得分任务，只开放终局急策、S14 宫门验核和终段压力；
- 已验核队伍重复提交宫门验核（VERIFY_GATE）返回已验核拒绝（ALREADY_VERIFIED），不创建宫门窗口（GATE）、不锁宫门对象；
- 主动等待（WAIT）能暂停已走移动量（edgeProgressMs）；缺失动作或空动作心跳按系统等待续行，继续向 nextNodeId 前进；
- 路线边上不能原路返回递减 edgeProgressMs；路线边上改道会放弃旧路线边已走进度，并从 currentNodeId 重新出发；
- 窗口争夺能冻结任务到截至帧的倒计时；RESOURCE 窗口只冻结本次库存分配，不涉及资源自然过期。
- 资源领取打断必须中断原领取流程，胜方从头开始领取；同一份资源最多允许 1 次资源领取打断，第 2 次起返回对象忙；
- TASK 窗口平局后，双方 RESTING 的 3 个结算帧内暂停任务对象到截至帧的倒计时；若达到重复平局上限并进入平局冷却，则冷却期间继续暂停该任务的过期倒计时，冷却结束后按剩余有效期恢复；
- GATE 窗口平局触发双方 RESTING 3 个结算帧；同一连续争夺周期内累计 2 次 GATE DRAW 后，宫门对象进入 6 个结算帧短冷却，冷却期内 VERIFY_GATE 返回 WINDOW_DRAW_RETRY_LIMIT；
- 破关令进入窗口争夺时只锁定成本，胜出并开始绑定动作处理时才正式扣除；
- 通行窗口（PASS）守方因自己的设卡被强制通行而被动参战；PASS 不改变守方主车队状态，也不打断守方正在进行的移动、处理、强制通行、休整、已交付状态或原窗口；守方不能出牌或未为该 contestId 提交有效 WINDOW_CARD 时，本拍按弃权（ABSTAIN）结算；
- 强制通行按整体倒计时结算；强制通行开始或通行窗口攻方胜出时，按当帧路线耗时和时间税算出本次总需求帧数；
- 强制通行期间若锁定阻挡失效，剩余时间税按仍有效的锁定阻挡对象重新计算；已经过的结算帧会抵扣重新计算后的总需求；
- 普通任务刷新上限分为当前任务池容量和可直接处理任务上限：已完成、失败、过期且非活跃的历史任务不占用当前任务池容量；窗口争夺中、胜方保护中、平局休整冻结中、重复平局冷却中的旧任务不占用可直接处理任务上限；
- 探路标记按同队同节点 FIFO 队列消耗，单次处理最多消耗 1 个；
- 天气事件按 `weatherPolicy.pool` 构造整局天气池，洗牌生成 4 次事件顺序；`avoidConsecutiveSame` 必须为 `true`，相邻天气不得同类。
- RESTING 状态只允许 WAIT 或 actions: [] 心跳，其他动作返回 RESTING_ACTION_FORBIDDEN；该拒绝不延长、不重置休整，本帧休整倒计时正常减少；
- DELIVER 必须满足 goodFruit > 0 且 freshness > 0；
- MOVE_BLOCKED_BY_GUARD 不累计破关悬赏，有效防守事件只统计攻坚值大于 0 且未攻破的攻坚，或强制通行被守住 / 失败；
- 无护卫行动点时，YAN_DIE、QIANG_XING、XIAN_GONG 仍形成循环克制，不存在无敌窗口牌。

| 直冲放大 | 无普通任务、低交锋、队伍只走最快路线完成交付 | 记录纯直冲最终分，与完成 2-3 个普通任务后交付的路线对比 | 纯直冲不得稳定超过做任务路线；宫门验核只在宫宴冲刺后开放，只解锁交付，不提供任务分 | 只允许调整路线距离、任务候选点、路线任务桶、资源投放站点或道路障碍候选点；任务收益、宫门窗口和终局急策数值不属于地图变体回调 |
| 探路 FIFO | 同队同节点连续添加 2 个 INTEL 探路标记 | 连续完成 2 次适用处理 | 每次处理最多减 3 个结算帧，按 FIFO 每次消耗 1 个标记，不叠加减时 | 不允许多个探路标记叠加到同一次处理 |
| INTEL 近距离范围 | 队伍持有 INTEL，分别选择距离 15 内和距离 15 外的目标节点 | 提交 USE_RESOURCE:INTEL | 距离 15 内目标成功添加己方探路标记；距离 15 外目标返回 TARGET_NOT_REACHABLE 且不消耗 INTEL | 不允许 INTEL 变成全图探路 |
| 强制通行非捷径 | 目标节点存在设卡或道路障碍，且阻挡未提前失效 | 同一条边分别执行普通 MOVE 与 FORCED_PASS | FORCED_PASS 的总需求按本次通行路线耗时和当前应付 timeTax 计算；天气或速度变化不回算本次总需求 | 只允许调整路线距离或道路障碍候选点；timeTax 和强制通行计算方式不属于地图变体回调 |
| 强制通行阻挡重算 | 强制通行期间 40 个结算帧设卡税失效，但 8 个结算帧道路障碍仍存在 | 继续推进强制通行 | 已支付时间税不返还；剩余时间税按仍有效阻挡的最高 timeTax 重新计算，已经过的结算帧抵扣新的总需求 | 不属于地图变体回调；剩余 timeTax 处理属于规则集变更 |
| PASS 旁路参战 | 守方正在 PROCESSING、VERIFYING 或其他窗口，攻方强制通行守方远处设卡 | 创建通行窗口并观察守方主状态 | 守方主状态不得被 PASS 打断；若守方当前状态允许窗口出牌，则可按规则出牌或弃权；若守方处于处理、验核、强制通行、休整、已交付或已退赛状态，本 PASS 拍自动按 ABSTAIN 结算 | 不允许 PASS 自动切换守方主状态 |
| 冰鉴不能恢复荔枝鲜度 | 队伍 freshness <= 0 且持有 ICE_BOX | 提交 USE_RESOURCE: ICE_BOX 后再尝试 DELIVER | ICE_BOX 返回 RESOURCE_NOT_USABLE，不消耗资源；DELIVER 仍因 freshness <= 0 被拒绝 | 不允许 0 鲜度通过冰鉴恢复交付资格 |
| 鲜度归零报废 | 队伍 freshness > 0，且仍有可支配好果或冻结好果 | 通过等待、移动或处理使本帧鲜度扣除后 freshness 降为 0 | 本次首次低于的数值先触发好果转坏；剩余好果全部报废，不增加坏果；若包含冻结好果，对应处理进入冻结好果被清算（COST_BANKRUPT） | 不允许 0 鲜度继续保留好果 |
| 坏果破防回调 | 目标为 defense = 7 的 KEY_PASS 满防设卡 | 只投入 2 篓 badFruit 攻坚 | attackValue = 6，不能单独攻破满防关键关隘 | 不属于地图变体回调；坏果攻坚系数、设卡防守上限和破关令加成属于规则集变更 |
| 护果令有效性 | 酷暑或山路高损耗场景 | 对比不开护果令与开启护果令 30 个结算帧的最终鲜度和得分 | 护果令应产生可观察鲜度收益，且不消耗好果，只消耗急策次数 | 不属于地图变体回调；护果令持续帧数和鲜度倍率属于规则集变更 |
| 窗口无敌牌 | 一方护卫行动点（guardActionPoint）= 0，另一方连续使用 YAN_DIE | 双方在 TASK / RESOURCE 窗口中轮流提交 YAN_DIE、QIANG_XING、XIAN_GONG | 非兵争三牌形成循环克制，YAN_DIE 不能稳定不败 | 不属于地图变体回调；窗口克制表属于规则集变更 |
| 弃权结算 | 一方出有效窗口牌，另一方 ABSTAIN；双方都 ABSTAIN | 分别结算单拍胜点 | 有效牌对 ABSTAIN 获得本拍胜点；ABSTAIN 对 ABSTAIN 为平点 | 不允许把有效牌对弃权结算成平点 |
| 撞墙刷悬赏 | 目标节点存在敌方有效设卡 | 同一方连续提交 MOVE 撞向设卡，再检查 bounties | MOVE_BLOCKED_BY_GUARD 不累计有效防守事件，不创建破关悬赏 | 不属于地图变体回调；有效防守事件定义属于规则集变更 |
| T04/CLEAR 同障碍锁 | 一方提交 T04 CLAIM_TASK，另一方同帧提交同障碍 CLEAR | 观察窗口、锁定和目标状态 | 两者按同一障碍争夺或对象占用处理，CLEAR 不能绕过 T04 锁直接让任务目标丢失 | 不允许按行动顺序让普通 CLEAR 低成本暗杀 T04 |
| 同节点设卡占用 | 双方在同一空节点同帧提交 SET_GUARD | 观察 guard 状态、事件和三层公平账本 | 服务端按独占冲突公平账本选出一方进入设卡读条，其余方返回 OBJECT_BUSY；读条完成后只生成一个 guard | 不允许同节点双 guard；不允许按阵营、playerId、连接顺序或包到达顺序选边 |
| 退赛判胜 | 一方退赛、双方同帧退赛、双方都未退赛 | 生成 over | 单方退赛时未退赛方直接获胜；双方同帧退赛时无胜方；双方都未退赛时按最终总分判断胜负 | 退赛状态优先于分数 |
| 同总分 over | 双方都未退赛，且最终总分相同 | 生成 over | winnerPlayerId = null，记录平局 | 分数相同即平局 |
| 已交付空心跳 | 队伍已交付（DELIVERED） | 提交等待（WAIT）、空动作心跳（actions: []）、重复交付（DELIVER）、普通动作各一次 | 等待、空动作心跳、系统等待、重复交付不罚；其他动作只触发交付后违规惩罚（POST_DELIVER_PENALTY）且不生效 | 不允许空心跳被交付后罚分 |
| RESTING 期任务过期 | 高价值任务距离截至帧很近，短于 TASK DRAW 后双方 RESTING 帧数 | 连续制造 TASK DRAW 触发双方 RESTING 和重复平局冷却 | 双方 RESTING 的 3 个结算帧内任务到截至帧的倒计时暂停，不能在 RESTING 冻结期过期；若进入重复平局冷却，冷却期间继续冻结任务剩余有效期；普通任务在重复平局冷却期间不占用可直接处理普通任务刷新名额 | 不属于地图变体回调；RESTING 冻结、重复平局冷却和刷新名额统计口径属于规则集变更 |
| 零果交付 | 队伍 goodFruit + frozenGoodFruit = 0，或 freshness = 0，且到达 S15 | 提交 DELIVER | 系统拒绝交付并返回交付条件不满足（DELIVER_REQUIREMENT_NOT_MET）；若好果总量为 0，freshness 应为 0 | 不允许无好果或无鲜度交付 |
| RESTING 越狱 | 队伍处于 RESTING | 提交 MOVE、CLAIM_RESOURCE、USE_RESOURCE、SQUAD_* 等非 WAIT 动作 | 服务端返回 RESTING_ACTION_FORBIDDEN，状态仍为 RESTING，休整帧数正常减少且不重置 | 不允许非 WAIT 动作中断 RESTING |
| 路线边上暂停与改道 | 队伍在路线边推进到 90% 位置后主动等待（WAIT），再提交 currentNodeId 的其他合法相邻节点 | 观察推进方向（moveDirection）、已走移动量（edgeProgressMs）和到达结算帧 | 主动等待时 moveDirection 为 PAUSED，edgeProgressMs 保持不变；改道后旧路线边进度清空，新路线从 0 重新累计；缺失动作或空动作心跳继续向 nextNodeId 前进 | 不允许保存旧前进位置，也不允许零帧跃迁 |

平衡验收聚焦当前机制。地图变体回调范围包括路线边清单、路线端点、路线距离、路线类型、双向标记、S02-S13 坐标、路线显示路径、地图总览格子、地形格子、站点对象格子、天气区域格子、流程节点绑定、资源投放站点、任务候选点、路线任务桶和道路障碍候选点。动作、协议字段、资源效果、错误码、天气类型、窗口牌型、计分公式和核心结算机制属于规则集变更，不作为地图变体回调。

## 11.3 前端验收

前端必须满足：

- 播放 replay.txt；
- 连接实时服务；
- 根据实时 `start.map`、`start.routePaths` 或回放 start 中的 `map`、`routePaths` 渲染地图和路线；根据实时 `start.nodes`、`start.edges` 渲染节点和可通行路线；
- 切换地图后，坐标、路线折线和资源显示必须随当前局地图同步更新；
- 根据 currentNodeId、nextNodeId、routeEdgeId、moveDirection、edgeProgressPermille、edgeProgressMs 和 edgeTotalMs 渲染主车队移动；
- 渲染天气；
- 渲染窗口三拍；
- 渲染小分队事件；
- 渲染宫门验核；
- 渲染交付结算；
- 渲染当前地图配置或回放 start 中的全部 routePaths；策略支路按当前地图 `edges[].routeType = BRANCH` 识别，不按固定边号识别；
- 只负责表现服务端已下发的结算结果。

## 11.4 参赛程序 验收

参赛程序 必须满足：

- 连接 TCP 服务；
- 处理 5 位长度前缀；
- 发送 registration；
- 接收 start；
- 发送 ready；
- 接收 inquire；
- 停靠在节点时，根据 `currentNodeId` 和 `start.edges` / `inquire.edges` 推导合法相邻 `targetNodeId`；移动或主动等待在路线边上时，根据 currentNodeId、nextNodeId、routeEdgeId 和 moveDirection 判断继续前进、暂停或改道；
- 以本局 `start.nodes`、`start.edges`、`start.resources`、`start.taskTemplates`、每帧 `inquire.nodes` 和 `inquire.edges` 理解当前地图、资源、任务和动态站点状态；某帧缺失 `inquire.edges` 时才回退使用 `start.edges`；
- 使用 currentNodeId、nextNodeId、routeEdgeId、moveDirection、edgeProgressPermille、edgeProgressMs 和 edgeTotalMs 理解移动状态；
- 提交 action；
- 处理协议级 error；action 包未进入规则结算时，以 error 为准；
- 处理下一帧 `inquire.actionResults` 和 `inquire.events`；`actionResults.accepted = true` 不等于动作收益已经获得，业务拒绝以 `events[].type = "ACTION_REJECTED"` 和 `payload.errorCode` 为准；
- 使用下一帧 `players`、`nodes`、`tasks`、`contests` 和 `scorePreview` 更新本地状态；
- 接收 over，并以 `resultType`、`winnerPlayerId` 和 `players[].totalScore` 读取本局结果；
- 完成一局无异常运行。
