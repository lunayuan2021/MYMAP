## 批次三：小分队播报 + 3D 信标时机（本次）

### 1. 小分队播报太长 — `Systems/LycheeHudExtensions.cs` `SquadFeedLabel`
- 「红队 小分队 在 潼关驿 完成 清障」→ 压缩：派出=「回合N 红队 小分队→潼关驿 清障」；完成=「…小分队·潼关驿 清障完成」；失败=「…清障失败」
- **勿误改**：别再加回「在/出发/执行」等虚词把它撑长（代码有注释）。

### 2. 3D 信标时机（最终：马延到上路才冒，冰鉴用即冒） — `Systems/LycheeConvoyVfx.cs`
> 历程：先改「用即冒(方案A)」→ 用户复议「延到上路才冒其实更好，能错开」→ **最终恢复马的延后**。
- **最终行为**：
  - **冰鉴(ICE_BOX)**：`RESOURCE_USE` 当场冒（停站保鲜、无骑行语义）。
  - **快马/短驿马**：`RESOURCE_USE` 时先挂起（`QueueOrPlayHorse`），等车队【真正上路行进】那刻由 `OnRoundApplied` 冒 3D 信标——与"停站/获取"错开，读作"骑马赶路"。
  - `ConvoyVfxRig` 恢复 `onEdge/pendingHorse/pendingHorseFast/pendingHorseArmedRound` 字段；`QueueOrPlayHorse`/`IsPlayerOnEdgeNow`（按当前帧实时判在路段，不吃缓存脏值）恢复。
  - 保留 A2 `IsApplyingForcedFrame` 拦截（seek/force 补演历史帧不凭空冒活信标）。
  - 配合去掉"获取中央卡"（见本批 #4），获取时不再有任何 pop，只剩"上路骑马"这一次信标。
- **勿改回"用即冒"**（代码有 ★ 决策注释）。马是停站用的，延到上路冒才能错开。

### 4. 3D 信标"获取冒一次、使用冒一次"（真正根因） — `LycheeReplayPlayer.cs` `ShowKeyEventIllustration`
- **背景**：车队头顶 3D 信标(GetEventModel/EventIconRoutine) **只在 RESOURCE_USE 冒**（已核实全工程唯一 3D 事件模型创建点）。但用户看到"获取时也冒一次"——真凶是**另一个系统**：中央事件卡白名单里 **RESOURCE_CLAIM 在、RESOURCE_USE 不在**（`ShowKeyEventIllustration` 第 ~2186 行）。于是：获取→弹一张"资源获取"中央卡；使用→冒 3D 信标。观众看到"获取一次(卡)、使用一次(信标)"。
- **改动**：从中央卡白名单去掉 `RESOURCE_CLAIM` → 资源只在使用时由 3D 信标表现，获取不再弹中央卡（左侧事件流仍有"获得XX"文字，不丢信息）。`else if (type=="RESOURCE_CLAIM")` 分支变为不可达死代码，保留未删（方便日后需要时再启用）。
- **勿误改**：别把 `RESOURCE_CLAIM` 加回该白名单（代码有 ★ 注释）。

### 3. 3D 特效比播报慢半拍 — `Systems/LycheeConvoyVfx.cs` `EventIconRoutine`
- 淡入/弹入/模型缩放入场 由「按 duration≈6s 比例」（原 ~0.84s 才亮）改成【绝对时间】：`inT=Ease01(elapsed/0.12)`、`pop` 用 `elapsed/0.14`、`envIn` 用 `elapsed/0.14` → 信标 ~0.12–0.14s 内快速冒到全亮，和播报同帧
- 淡出仍按 duration 比例（最后 28%），不动
- **勿误改**：入场三处用 `elapsed`(绝对秒) 不是 `t`(=elapsed/duration)；改回 `t` 会又慢半拍。
