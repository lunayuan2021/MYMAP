# 交接：WebGL 回放包「替换 replay.txt 后报找不到」根因与修复（2026-07-02）

## 一句话

现场（Windows）替换 `StreamingAssets/replay.txt` 后页面报「找不到回放文件」，服务器日志报
`使用"3"个参数调用"Write"时发生异常:"指定的网络名不再可用"`。**真因不是文件缺失，是 6.4MB 的
replay.txt 下载超过客户端 12 秒超时被 Unity 主动掐断**（机器消化慢：刚加载完 500MB 资源、远程桌面、
杀毒软件）。换磁盘（C/E 盘）无效，瓶颈不是盘。已在**构建器层面永久修复**并产出新包。

## 排查过程（为什么绕了几轮）

客户端把「404 / 超时 / 空文件」三种失败**全显示成同一句「找不到 replay.txt」**，无法区分，所以：

1. 第一轮以为是**权限/大小写**（Linux/Mac 场景）：Python 服务器对无读权限文件回 404、Linux 区分大小写、
   Mac 下载目录文件带 com.apple.macl 锁。→ 现场是 Windows，NTFS 不区分大小写、无此类锁，不适用。
2. 第二轮加了**服务器请求日志**（现场急救 ps1 v1），让现场把日志发回来。关键那行：
   `ERR /...replay.txt... :: 使用"3"个参数调用"Write"时发生异常:"指定的网络名不再可用"`
   —— 这行**没有记 404，而是进到了"发送文件"阶段才失败**，证明文件被找到、服务器开始发、发到一半
   浏览器把连接断了（"指定的网络名不再可用" = Win32 ERROR_NETNAME_DELETED = 对端断连）。
3. 定位到真因：旧包客户端 `UnityWebRequest.timeout = 12` 秒，6.4MB 在慢机器上 12s 传不完 → Unity abort
   → TCP 断 → 服务器下一次 `OutputStream.Write` 抛这个异常。日志时间戳也印证：manifest 与 replay ERR
   间隔远超 12s。

## 最终解法：服务器 gzip

replay.txt 是 JSON 文本，gzip 压缩率极高：**6,492,369 → 116,066 bytes（1.8%，约 1/56）**。
服务器对 `.txt/.json` 按 `Accept-Encoding: gzip` 压缩后再发，浏览器自动解压，Unity 拿到的仍是原文。
传输量降 50 多倍，12 秒超时问题根除（换磁盘之所以无效，因为瓶颈是传输量+慢消费端，不是磁盘读取）。

## 具体改动（全部在 `Assets/LycheeReplayDemo/`）

### 客户端 `LycheeReplayPlayer.cs`
- `FetchReplayUrl`：`request.timeout` 12s → **60s**；诊断串加 `bytes=` 和 `url=`。
- `ParseReplay` 找不到时的报错文案：区分权限/大小写/超时，附「加载记录」（含 HTTP 状态码）。
- `OnGUI` 报错面板高度 260 → **340**（容下新增诊断行）。
- 判据：报错框 `response=404`=文件名/权限、`error=timeout`=太大太慢、`200 bytes=0`=空文件。

### 构建器 `Editor/LycheeWebGLBuild_20260612.cs`（生成两套本地服务器 + README）
两套服务器都加了 **gzip（白名单 `.txt/.json`）** 和 **请求日志**：
- **PowerShell**（`start_local_server.ps1`，Windows `start.bat` 走这个）：
  - `.txt/.json` 用 `IO.Compression.GZipStream`（两参 CompressionMode 构造，PS 5.1 免 Add-Type）压缩后发。
  - 请求日志 `.lychee_web_server_requests.log`：每行含字节数、耗时；404 行记服务器解析出的真实磁盘路径。
  - 健壮性（经两个独立代理审查后修）：
    - 绑定 `127.0.0.1` 失败（HTTP.SYS 非管理员拒绝）→ 自动回退绑 `localhost`。
    - `Start-Process`（开浏览器）套 try —— 否则 `$ErrorActionPreference='Stop'` 下开浏览器失败会拖死服务器。
    - 请求循环整体套 try/catch —— 否则单次异常（文件被 WPS/记事本占用、客户端中断）让服务器**静默退出**
      （窗口最小化看不见），之后全 404，这是旧版 ps1 的实锤 bug。
    - `.unityweb` 分支的 gzip 头移到 `OpenRead` 成功之后 —— 否则文件被占用时 500 明文顶着 gzip 头，浏览器解码错误。
- **Python**（`lychee_server.py`，Linux `start.sh` / 黄区部署走这个）：
  - `do_GET` 覆写：`.txt/.json` 且客户端支持 gzip 时 `gzip.compress` 后发。
  - `translate_path` 拆出 `_resolve_path` 并记 `self._last_full`；`log_request` 写同名日志、404 带解析路径；
    `log_error` 跳过 404（避免每次 miss 重复两行）。
- **README_使用说明.txt**：加「替换回放文件」（全小写/无需重启/别放网络盘U盘）+「排查日志」章节。

## 未来怎么排查（现场自助）

1. 让现场打开包根目录的 `.lychee_web_server_requests.log`，找 replay.txt 那行：
   - 正常：`200 ... (6492369 -> 116066 bytes gzip, XX ms)` ← gzip 生效。
   - `ERR ... (after ≈12000 ms)`：还是超时 → `?quality=performance`、别用远程桌面、退杀软、多刷两次走缓存。
   - `ERR ... (after 很小 ms)`：不是超时，是杀软/安全卫士切断 localhost → 退出或加白名单。
   - `404 ... -> 磁盘路径`：路径目录不对=起错目录/旧服务器串台；路径对仍 404=真名不是 replay.txt
     （Windows 隐藏扩展名，常见 `replay.txt.txt`，CMD `dir StreamingAssets\replay*` 看真名后 `ren` 改回）。
2. 页面红色报错框也会显示「加载记录」含 HTTP 状态码，判据同上。
