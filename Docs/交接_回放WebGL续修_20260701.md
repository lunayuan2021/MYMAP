## 用户最新未解决问题（优先级最高）

### 1. 同一事件在车队上方叠出两个 3D 模型

用户澄清：不是 3D 模型和 2D 徽章叠加，而是同一个事件、同一个车队上方出现两个重叠的 3D 模型。只保留一个。

重点定位：

- `Assets/LycheeReplayDemo/Systems/LycheeConvoyVfx.cs`
  - `OnReplayEvent()` 订阅 `LycheeReplayPlayer.ReplayEventRaised`，对 `RESOURCE_USE` / `RESOURCE_CLAIM` 调 `PlayResourceVfx()`，对 `GOOD_TO_BAD` 调 `PlaySpoilVfx()`。
  - `PlayIceBoxVfx()` / `PlayHorseVfx()` / `PlaySpoilVfx()` 每次都会 `StartCoroutine(EventIconRoutine(...))`，当前没有同车队同事件去重。
  - `EventIconRoutine()` 每次创建一个 `GameObject("LycheeEventIcon")`，当前没有先清掉同 key 的 active icon。
  - `EventIconRoutine()` 里 `modelCap = CreatePlaqueText(...)` 被写了两遍，这会导致文字叠影；这不是两个 3D 模型的主因，但应顺手删掉重复行。
- `Assets/LycheeReplayDemo/LycheeReplayPlayer.cs`
  - `EmitSyntheticGoodToBadEvents()` 会根据好果减少/坏果增加合成 `GOOD_TO_BAD` 事件。要确认 replay 里是否本来已有 `GOOD_TO_BAD`，如果有，可能同一回合被真实事件和合成事件触发两次。
- `Assets/LycheeReplayDemo/Systems/LycheeReplaySceneBootstrapper.cs`
  - `Ensure<LycheeConvoyVfx>()` 会挂组件；`LycheeConvoyVfx` 自己也有 `[RuntimeInitializeOnLoadMethod] Bootstrap()`。两边都有已存在保护，但仍建议在 WebGL 控制台打一次实例/订阅诊断，确认不是多个 `LycheeReplayPlayer` 或多个 `LycheeConvoyVfx` 同时响应。

建议修法：

- 在 `ConvoyVfxRig` 里加同事件 key 的 active/debounce 状态，例如 `Dictionary<string, float> lastEventIconAt` 或 `Dictionary<string, Coroutine> activeEventIcons`。
- 同一 `playerId + eventKey` 在很短窗口内重复触发时跳过；如果要替换，就先销毁旧 `LycheeEventIcon` 再创建新的。
- 对 `GOOD_TO_BAD` 特别检查真实事件和 synthetic 事件是否重复，必要时 `EmitSyntheticGoodToBadEvents()` 对同回合已有 `GOOD_TO_BAD` 的玩家跳过。

### 2. 红蓝队头像没有，开场 VS 页面头像也没有

用户截图里底部 HUD 只剩棕色头像占位，开场 VS 页面也是大色块/圆形，没有真正头像。

重点定位：

- `Assets/LycheeReplayDemo/LycheeReplayRuntimeHud.cs`
  - `BuildTeam()` 里创建 `RawImage avatarRaw`，调用 `SetRawImageSprite(widgets.avatarRaw, ResolveTeamAvatar(...))`。
  - `ResolveTeamAvatar()` 目前如果 `requested != null` 就直接返回，没验证 `requested.texture` 是否存在。
  - `SetRawImageSprite()` 在 `sprite == null || sprite.texture == null` 时会 `image.enabled = false`，于是只剩头像底板。
- `Assets/LycheeReplayDemo/Systems/LycheeOpeningShowcase.cs`
  - `BuildTeamPanel()` 仍用 `Image avatarImage` + `Mask` 做开场头像。WebGL 下如果 `LycheeWebGLImageSpriteGuard` 或 Sprite secondary texture 路径干预，可能导致 Image/Sprite 不显示。

建议修法：

- `ResolveTeamAvatar()` 不要无条件接受 `requested`，要判断 `requested.texture != null`。
- 若主题图没及时加载，必须保证生成 fallback 头像可见，不要禁用 RawImage。
- 开场 VS 页建议统一改成 `RawImage` 路径，直接显示 `team_red_emblem.png` / `team_blue_emblem.png` 的 texture；不要只依赖 `Image.sprite`。
- 修完要同时检查底部 HUD 与开场 VS 两处头像。

- `Assets/LycheeReplayDemo/Systems/LycheeOpeningShowcase.cs`

### 4. 短视频播完后不会自动播放，必须手点播放

重点定位：

- `Assets/LycheeReplayDemo/Systems/LycheeVideoInterlude.cs`
  - `RunInterlude()` 第 176 行左右先 `IsPresentationActive = true`。
  - `LycheeReplayPlayer.ShouldForcePresentationPause()` 会看到 presentation active 并把 replay 置为暂停。
  - `RunInterlude()` 第 209 行左右才 `bool wasPlaying = player.IsPlaying;`，此时可能已经被外部暂停，所以 `wasPlaying == false`，视频结束后不会恢复播放。

建议修法：

- 在 `RunInterlude()` 最开始就缓存 `bool wasPlayingBeforeInterlude = player != null && player.IsPlaying;`。
- 或者把 `IsPresentationActive = true` 移到视频准备完成、真正开始淡黑播放前。
- 视频结束后用最早缓存的 `wasPlayingBeforeInterlude` 恢复，而不是用已经被 presentation pause 改过的状态。
- 验证：播放短视频前 replay 在播放，短视频结束后必须自动继续。

### 5. 出发状态的徽章太多，建议去掉

- 如果仍需要提示，使用文字条而不是地图上方 2D 徽章。

### 6. 下方提示条和重播条边框比文字窄，内容溢出

用户反馈屏幕下方提示条、左上重播/播放控制条的边框宽度跟不上文字，很多文字内容溢出。

重点定位：

- `Assets/LycheeReplayDemo/Systems/LycheeHudExtensions.cs`
  - `TickerWidth = 960f`、`TickerHeight = 44f`。
  - `BuildMechanicTicker()` 里 ticker 背景宽度固定，`tickerText` 允许 horizontal overflow，通过 `RectMask2D` 滚动。
  - `BuildControls()` 控制条固定 `500 x 104`，按钮、速度下拉和 `RoundLabel` 固定布局。
- `Assets/LycheeReplayDemo/LycheeReplayRuntimeHud.cs`
  - `BuildToast()` 右侧小分队提示条固定 `520 x 46`，也可能出现文字和边框不匹配。

建议修法：

- 控制条整体宽度和内部布局要按最长文本重新算，不能只扩大文字。
- Ticker 背景要比可见文字区域更宽，或改成完整滚动裁切但边框覆盖范围必须包含文字可见区域。
- 对不同窗口宽高做响应式约束，不能只按 1920 宽度调。
- 修完要在 1280x720、1600x900、全屏三个尺寸截图验证文字不压边、不溢出边框。

### 7. 右侧事件卡片红队完成事件底部色块错成黄色

用户补充：右侧事件卡片窗口里，红队完成的事件下面色块不是红色，而是黄色；蓝队完成事件下面色块能正确显示蓝色。

重点定位：

- `Assets/LycheeReplayDemo/LycheeReplayRuntimeHud.cs`
  - 右侧事件卡底部色块是 `combatResultBanner`。
  - `ApplyCombatResultStyle()` 通过 `CombatWinnerHint(title, subtitle, score)` 判断队伍，`winner == 0` 才给红色，`winner == 1` 给蓝色，否则 fallback 到 `neutral` 暗金/黄色。
  - `CombatWinnerHint()` 目前只显式识别 `"红队胜"`、`"红队 得势"`、`"红队成功"`、英文 `RED WIN` 等；不一定识别 `"红队完成"`、`"完成 目标点"`、`"完成 T_..."`、`"红队 #2002 ... 完成 ..."` 这类任务完成文案，所以红队完成事件容易落到 neutral 黄色。

建议修法：

- 扩展 `CombatWinnerHint()` 的红/蓝队完成类关键词，例如红队/红方/RED + `完成`、`获得`、`刷新`、`清障`、`目标点`、`任务`；蓝队同样保持一致。
- 如果事件 payload 有 `playerId/teamId/winner`，优先用结构化队伍字段，不要只靠中文字符串猜。
- 验证红队和蓝队的“皇榜任务完成/资源获取/目标点任务完成/清障任务”右侧卡片底部色块都按队伍色显示，红队红色、蓝队蓝色，不应出现红队黄色。
