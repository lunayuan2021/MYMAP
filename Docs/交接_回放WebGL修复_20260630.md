## ⚠️ 最重要的流程教训（先读这条）

1. **用户反复测到的是旧包 → 每次必须自己先在 preview 里自测新包、用截图证明，再交给用户。** 别再说"这是旧包"让用户自己换——要么自己验证，要么给出确切路径+如何确认不是缓存旧包。用户已明确："你就新构建一个然后测，不然这就是不对啊。"
2. **WebGL 自测法（这套跑通了，很值）**：
   - `.claude/launch.json` 配 `python3 -m http.server 8090 --directory <buildDir>`；用 preview_start。
   - **build 的 `index.html` 有 `<base href="/litchi_delivery_replay/">`，根路径服务会 404 → 必须改成 `<base href="./">`**（改自己的 build 副本，"./"对 lychee_server.py 路径也兼容）。
   - `preview_resize` 设 **1280x800 landscape**（默认 panel 是竖的 portrait，UI 会按错误宽高比 reflow、误导判断）。canvas 会变 2560x1600。
   - `preview_screenshot` 看画面；`preview_console_logs level=error/warn` 看崩溃/异常。UnityCache 按 URL+buildStamp 缓存，新包=新 buildStamp=自动重下。
   - preview server 会自己停（崩溃/超时）；重 start 即可，缓存命中后加载快。
3. **别用 MCP 跑阻塞 Unity 构建**（会失控循环）。用 **request-marker 异步构建**：`echo ... > LycheeWebGLBuild_20260616.request`，编辑器轮询后构建，完成写 `LycheeWebGLBuild_20260616.done`。构建器 `Assets/LycheeReplayDemo/Editor/LycheeWebGLBuild_20260612.cs`，默认场景 Map_medium + replay.txt。
4. **MCP relay 卡座**（"Unity not detected"/"Connection revoked"）：`pkill -9 -f "relay_mac_arm64 --mcp"; pkill -9 -f "RelayApp~/relay"; sleep 8; osascript -e 'tell application id "com.unity3d.UnityEditor5.x" to activate'`。
5. **RunCommand 沙箱禁 System.Reflection**；公有方法/字段可直接调。

## 已修复（在代码里，需新包验证）

1. **崩溃：回放放到最后、出结算页那一下 `RuntimeError: null function` → Halting program。**【⚠ 尚未真正修好，见下】
   触发点：`LycheeReplayPlayer` line 720 `MatchOverRaised?.Invoke(OverFrame)` → `LycheeSettlementScreen.HandleMatchOver`。
   - **第一猜（错）**：以为是 `BuildVictoryVideo` 的 `VideoPlayer`(RenderTexture+Prepare)。**已在 WebGL 关掉视频改静态背景**（`#if UNITY_WEBGL` 里 `victoryVideoFailed=true; return;`）。
   - **2026-06-30 自测 170914 包结果（preview 截图为证）**：**静态胜利背景正常显示了**（说明视频确实关掉了、视频不是病根），**但结算页仍 `null function` 崩**（func≈149950，和关视频前的 149947 几乎同一处）。所以**真凶不是 VideoPlayer，是结算 build 里 `BuildBackground` 之后的某个子步骤**（EnsureBuilt 后续/Populate/PlayIntroSequence 里的某个值类型泛型或 WebGL 不安全调用）。崩时画面只剩背景、没有比分/横幅/MVP，说明崩在背景之后、内容显示之前。
   - **2026-06-30 已符号化定位（重大进展）**：出了 `debugSymbolMode=Embedded` 符号包 `Builds/LycheeReplay_WebGL_20260630_172630_Linux`，**离线解析 wasm name 段**把崩溃栈映射成 C#（解析脚本思路：gunzip `.wasm.unityweb`→找 custom section "name"→subsection 1 函数名表→按 wasm-function 索引查名）。**崩溃调用链（已确认是结算页 Canvas 重建）**：
     `Canvas.SendWillRenderCanvases → CanvasUpdateRegistry.PerformUpdate → Graphic.Rebuild → Image.UpdateMaterial → Image.SetSecondaryTextures → Image.CheckSecondaryTexturesChanged → Sprite.GetSecondaryTextures → Sprite_CUSTOM_GetSecondaryTextures`，最内层 trap 在 `vector<ShaderVariantCollection::VariantInfo>::assign_range → StringStorage::grow → malloc → MemoryManager::Allocate`。
   - **关键排除**：`stripEngineCode: 0`（引擎裁剪**关着**）→ 不是裁剪导致 GetSecondaryTextures 原生绑定被剥（也解释了为何回放 HUD 的 sprite Image 不崩）。所以**真凶是结算页这个 uGUI 重建路径里某个特例**，不是全局裁剪。
   - **首要假设**：`BuildBackground`(line 642) 给背景容器加了 **`RectMask2D`** → 被遮罩的 Image 材质走 **masked UI shader 变体**（UNITY_UI_CLIP_RECT），该变体在 WebGL 里 warm（ShaderVariantCollection）时命中 null function；回放 HUD 不用 RectMask2D 所以不崩。次要假设：结算 Image+runtime Sprite 的 `GetSecondaryTextures` 这条具体 sprite 触发。
   - **下一步（preview 工具恢复后，一次验证）**：候选修法逐个试+preview 跑到结算验证——(a) 去掉结算背景容器的 `RectMask2D`（最小、最可能）；(b) 把 masked UI 变体（UI/Default 带 UNITY_UI_CLIP_RECT/_ALPHACLIP）加进 AlwaysIncludedShaders 或一个 ShaderVariantCollection 预热；(c) 若是 GetSecondaryTextures，把结算的 `Image`+Sprite 换成 `RawImage`+Texture（RawImage 不调 GetSecondaryTextures）。改完务必把 `debugSymbolMode` 改回 Off、`exceptionSupport` 改回 ExplicitlyThrownExceptionsOnly。
   - ⚠ **本会话未应用上述修法**（preview 工具断连无法自测，且用户明确反感未验证的瞎猜）——符号化定位已交接，新会话带 preview 验证后再改。
2. **左上角"多一层"** = 上面三套 HUD 的第①套旧 IMGUI 叠在第②套 uGUI 控制条上。**已删 OnGUI 旧 HUD 绘制**。
